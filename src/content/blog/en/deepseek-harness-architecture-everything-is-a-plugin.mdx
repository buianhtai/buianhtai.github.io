Imagine asking an agent to investigate a broken build. It reads files, calls a shell tool, sees a failed test, adjusts a patch, and tries again. Halfway through, the browser disconnects. The user reconnects and wants to know **which commands ran, what the model saw, and why the agent chose its next step**.

That sounds like a model problem. It is mostly a **runtime architecture problem**.

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) takes a notably different approach from a hard-coded agent runner: almost every capability around the model is a replaceable plugin. The model adapter, tool registry, agent loop, prompt construction, session persistence, and even much of the UI participate in the same composition system.

The result is an interesting case study in **building a programmable agent runtime**, rather than merely building one agent.

<Callout color="teal">
  **Thesis:** DeepSeek Harness's most useful ideas are **composition through services**, **reversible plugin lifecycles**, and **a durable session log as the source of model-visible context**. Its agent loop is important, but it is not the unusual part.
</Callout>

## 1. What is DeepSeek Harness, and why does a harness matter?

An LLM returns tokens. An agent must also manage its surroundings: assemble context, choose and enforce tools, maintain state, run multiple steps, respond to cancellation, keep a UI updated, and recover useful history after the user leaves.

DeepSeek describes the relationship as **agent = model + harness**. The harness is everything that turns a model invocation into repeatable software behavior.

A minimal agent might look like this:

```ts
// Illustrative, not DeepSeek Harness source.
while (true) {
  const answer = await model.complete(messages, tools);
  if (!answer.toolCalls?.length) break;
  for (const call of answer.toolCalls) {
    messages.push(await runTool(call));
  }
}
```

This works for a demo. It hides the decisions that matter in production: Who validates a tool call? What if the same tool is hot-swapped? How is a failed attempt distinguished from an accepted assistant message? Where is the cancellation boundary? How does the UI recover after a disconnect? How can a team replace the loop *without forking everything else*?

**DeepSeek Harness makes these into explicit extension contracts.** That choice is the architecture.

The central mechanism is [Cordis](https://github.com/cordiverse/cordis), a plugin framework that contributes services, typed events, and managed registration lifetimes to a shared context. Instead of importing a concrete implementation everywhere, consumers access services through stable keys.

| Logical component | Responsibility | Typical contract |
| --- | --- | --- |
| `core/agent` | Agent identity, lifecycle and event vocabulary | `ctx.agents` |
| `core/agent-loop` | Turns, steps, model attempts and tool continuation | `ctx.agentLoop` |
| `core/system-prompt` | Prompt sections and tool-schema assembly | `ctx.systemPrompt` |
| `llm/llm` | Adapter selection, model request and stream vocabulary | `ctx.llm` |
| `core/tools` | Scoped tools, guards, approvals, execution hooks | `ctx.tools` |
| `core/session` | Model-visible history and append-only events | `ctx.sessions` |
| `core/scope` | Per-agent registrations and scoped lifetimes | Library primitive |
| Persistence providers | Store and load sessions independently from the loop | `ctx.sessionPersistence` |

This map is derived from the repository's [architecture documentation](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/docs/architecture.md). It is **not** saying that each package needs its own container, database, or HTTP API.

### Why this matters

A normal application often has one central agent class with direct dependencies on one provider, one storage adapter, and one tool executor. Changing any one of them reaches into unrelated code. DeepSeek Harness instead creates **capability seams**: a service interface, one or more providers, and consumers that should depend on the interface.

That can make experimentation cheap *architecturally*, even when execution is still costly. You can test different capability implementations without rewriting your entire agent product.

## 3. What makes it different? Six architectural decisions

### 3.1 Even the agent loop is a plugin

The loop itself is replaceable. This is more radical than making only external tools pluggable.

A tool plugin adds an action *inside* a fixed execution model. A replaceable loop lets a developer change the execution model: how turns progress, which policy events run, or how continuation is handled—without requiring other components to adopt a new vendor-specific base class.

The trade-off is that a stable event vocabulary and capability interfaces become critical. If plugins silently depend on private loop details, the abstraction collapses.

### 3.2 Registrations have reversible lifecycles

Cordis treats listeners, providers, prompt sections and tool registrations as **effects** associated with a plugin's lifetime. A plugin can mount its registrations; when it unloads, the runtime unwinds them.

That is useful for hot reloads, configuration experiments, tenant-specific compositions, and plugin testing. It is also stricter than simply registering callbacks into a global singleton: the owner and cleanup are first-class concerns.

See the [Cordis primer](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/docs/cordis-primer.md) for `inject`, `apply(ctx)`, `ctx.effect()`, and event dispatch modes.

### 3.3 Configuration is layered composition, not a pile of flags

A profile composes ordered bundles and user or environment patches into a plugin tree. The documented profiles include `web`, `headless`, `sdk`, `sdk-minimal`, and `acp`. An override can change a particular plugin's configuration rather than editing source code.

The distinction matters:

- **Bundle:** a reusable set of configured plugins.
- **Profile:** a named runnable composition.
- **Patch:** an explicit override of a plugin row.
- **Service:** the contract consumers use after composition.

For local inspection, the architecture docs provide:

```bash
dsh --profile web --dump-config
```

Use this to understand **what was actually mounted**, not just what packages are installed.

### 3.4 Durable truth is different from live UI progress

The system distinguishes three kinds of activity:

| Domain | Examples | Lifetime |
| --- | --- | --- |
| **Durable session facts** | `turn/start`, `user/message`, `assistant/message`, `tool/call`, `tool/result` | Stored and reconstructable |
| **Live agent events** | `agent/status`, `agent/pre-step`, `agent/request`, `agent/assistant-stream` | Coordination and transient streaming |
| **Capability hooks** | `tools/pre-execute`, `tools/execute`, `tools/post-execute` | Interception and policy composition |

A live streaming token is not automatically a committed assistant message. DeepSeek Harness settles a successful streamed attempt into a durable `assistant/message`; failed or retried settled attempts can be recorded as `assistant/attempt`.

**Why separate them?** A disconnected browser can reconstruct a transcript from durable facts, while the running UI can still receive low-latency incremental updates. The failure boundary also becomes explicit: an unrecovered process crash *before durable settlement* is not proof that the missing stream was committed.

### 3.5 Policies wrap tools rather than hiding inside the loop

The tool pipeline is not simply `tool.execute(args)`. It contains interception, guards, approval, execution, result projection and finalization. This places permission enforcement at the capability boundary where it applies to *every caller*, not inside a prompt.

### 3.6 Runtime modes are compositions for different jobs

The project offers Standard, Code, Minimal and Creator experiences. Standard is a fuller coding-agent composition; Code mode permits model-generated code to coordinate tool operations; Minimal reduces the tool surface; Creator focuses on experimenting with and composing plugins.

The insight is **one extensible runtime, multiple deliberately shaped products**. Do not read this as a guarantee that every mode is equally safe or production-ready.

## 4. How it actually works: follow one request through the source

The most revealing code is in `packages/core/agent-loop/src/agent.ts`. It is worth separating a **turn** from a **step**:

- A *turn* is the unit of user work, which may contain zero or several model steps.
- A *step* is one accepted model request and the resulting tool work.
- Retries and next-step input do not necessarily require a new turn.

An illustrative *reading trace* looks like this:

```text
Agent.followup(message)
  -> Inbox queues input
  -> Agent driver claims and admits work
  -> prepareRequest() -> LLM adapter preparation
  -> stream(request) -> transient assistant frames
  -> durable assistant/message or assistant/attempt
  -> executeToolCalls() when tool-call blocks exist
  -> guarded scheduler dispatch
  -> durable tool/result linked to tool/call
  -> next step or turn/end
```

**Important:** This is a logical source walkthrough, not a captured runtime trace or an assertion that every line runs on every turn. A blocked input may spend **zero model calls**; a tool-free answer skips tool execution; a retry can occur inside an open step.

## 5. Why the tool pipeline is more important than the tool registry

Giving a model a `deleteFile` or `runShell` function is easy. Giving it *controlled authority* is hard.

The order is not incidental. [The tool pipeline](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/docs/tool-execution-pipeline.md) describes pre-execute waterfall hooks, monotonic guards, approval prompts, execution wrappers, post-execute transformations, normalized outcomes and a final event. In `tool-calls.ts`, the scheduler prepares a call before dispatch, and records ordered results with references back to the original call.

**What to learn:** treat the tool boundary like an API security boundary. The model may propose an action; an independent policy layer authorizes it. A system prompt saying "do not delete files" is not an authorization mechanism.

## 6. The session log is a design choice, not just storage

One of the strongest ideas is **model-visible means logged**.

The session is not merely a list of chat bubbles. It records the inputs that shape the request: accepted user messages, prompt reconciliation, attempt outcomes, tool calls, tool results and relevant context projections. Model history is *derived* from this event stream.

That changes how you reason about recovery:

| Scenario | A naive chat-history agent | Session-log-centered architecture |
| --- | --- | --- |
| User refreshes the browser | May lose intermediate detail | Can rebuild accepted history from durable events |
| Provider fails after partial streaming | Risk treating partial output as final | Separate transient frames from settled attempts |
| Tool returns an error | May append ambiguous text | Records call and result facts with linkage |
| Need to understand a bad decision | Prompt is often assembled invisibly | Can inspect logged, model-visible surfaces |
| Need a new provider | Request logic may be coupled to one API | An adapter seam can preserve loop semantics |

**Caveat:** An append-only log alone does not make side effects exactly-once, guarantee safe replay of commands, or solve distributed concurrency. Durable state and external effects are separate problems. If an agent invokes a payment API or edits a remote system, the platform still needs idempotency, credentials, reconciliations, and outcome-unknown handling.

## 7. Real use cases: when does this architecture make sense?

### Use case A — A coding agent that can explain its own actions

A user asks for a refactor. The agent reads source, proposes an edit, runs tests, and reports progress. The architectural requirements are a tool registry, file/shell execution provider, session log, stream of UI events, and cancellation.

**Why DeepSeek Harness fits:** these capabilities are separate plugins. You can swap execution environments and examine a single turn's visible context without redesigning the agent loop.

### Use case B — A tool provider that must work across modes

Suppose your organization wants a custom repository-search capability. A plugin can offer the tool through the shared tool service. You should not have to write four separate implementations for the Web app, SDK runner, background process, and another agent preset.

**Design goal:** one capability provider, multiple compositions. The exact permissions and deployment method still need review for each mode.

### Use case C — An auditable troubleshooting assistant

An internal assistant receives a trace identifier, queries approved log/search tools, and suggests a diagnosis. You want the decision to show which evidence was retrieved and which tool calls ran.

**Useful patterns:** keep evidence-producing tool calls and outcomes as durable facts; give the UI transient progress; enforce access through the tool pipeline rather than assuming the model remembered policy.

**What you still build yourself:** identity propagation, tenant isolation, redactable audit exports, data-retention policy, authorized log access, and human escalation. DeepSeek Harness's plugin composition does not automatically supply all of these enterprise controls.

### Use case D — Evaluating alternative models or runtime policies

You want to compare two model adapters or two continuation policies on a common set of test tasks. Instead of forking the application, compose different profiles and evaluate outcomes under the same task harness.

**What to measure:** accepted tasks, tool failures, intervention frequency, tokens per successful task, attempt/retry rates, p95 latency, and session-recovery quality. The sources studied do not justify claiming a particular speedup or cost saving.

### Use case E — A pluggable agent platform

A platform allows customers to choose models, tools, workspace policies, and retrieval sources. The transferable lesson is **define stable service/provider boundaries and a compilation step from declarative configuration into a runtime composition**.

Do **not** blindly copy a local Node.js plugin tree into a distributed multi-tenant SaaS control plane. Distributed worker leasing, per-tenant credentials, cost budgets, deployment isolation, and authorization may need independent services and stronger governance boundaries.

## 8. Trade-offs: where the architecture gets difficult

| Decision | Advantage | Cost or failure mode |
| --- | --- | --- |
| Everything is a plugin | Extreme replaceability and reuse | Harder dependency graph, lifecycle debugging |
| Dynamic mounting and reversible effects | Hot-swapping and controlled teardown | Leaked registrations and order-sensitive cleanup if misused |
| Event waterfalls | Policies can intercept calls without modifying loop source | Hidden ordering, short-circuit surprises and difficult tracing |
| Session as durable model context | Better replay and inspectability | Schema evolution, storage amplification and privacy retention |
| Multiple profiles/bundles | Different products from one runtime | Configuration precedence becomes operational complexity |
| Streaming plus settlement | Responsive UI with durable truth | Two temporal views that must agree after failure |
| Tool policy seams | Consistent authorization hooks | One bypassed provider can undermine policy |

It is important not to confuse **extensibility** with **production readiness**. The project's [safety notice](https://github.com/deepseek-ai/deepseek-harness/blob/1517a4dbca0a2789ff1d41ba439600f8547d23fa/SAFETY.md) explicitly says this developer-preview software has not undergone a security audit. Its permissions and sandbox measures do not guarantee isolation. Use disposable environments and least-privilege access for experiments.

## 9. What should an architect learn from it?

These are the patterns I would carry into a platform design—even if I never deploy DeepSeek Harness itself.

**Lesson 1 — Model adapters are ports; policies are separate ports.** A model provider, tool provider, session store and approval provider should have independent contracts. Otherwise a provider swap changes unrelated business logic.

**Lesson 2 — Make runtime composition inspectable.** An operator should answer: Which plugins were mounted? Which version and configuration won? Which dependency injected this service? A dump of the effective tree is a debugging tool, not just a development convenience.

**Lesson 3 — Treat extension registration as a resource with a lifetime.** Event handlers, tools, caches, scopes and prompt sections need ownership and disposal. Especially important for long-running runtimes and hot reloads.

**Lesson 4 — Distinguish durable state, ephemeral signals, and irreversible effects.** A streaming chunk is ephemeral; a settled assistant message is durable; an external command is an effect that may need reconciliation. These cannot share one ambiguous "message" type.

**Lesson 5 — Log the inputs that explain behavior.** Trace IDs help you find a request; model-visible state, tool inputs and policy decisions help you explain *why* an agent behaved a certain way. Protect that audit data because it may contain sensitive context.

**Lesson 6 — Put permissions at execution boundaries.** Prevent a model from bypassing restrictions through an alternate tool or background caller. Guards must be independent of the generated text.

**Lesson 7 — Separate architectural dependencies from runtime calls.** A TypeScript import does not prove an HTTP request. A plugin service access does not prove a new process. A nice-looking diagram should make edge semantics explicit.

**Lesson 8 — Prefer measurable, replaceable experiments.** Profile composition makes A/B comparisons practical, but only evaluation data can establish improvements in reliability, latency or cost.

### A practical reference design to borrow

For a generic enterprise agent platform, I would borrow the **in-process capability pattern** but surround it with explicit platform governance:

```text
Agent Definition + Version
    -> Configuration compiler / validator
    -> Runtime profile (model, tools, context, policy)
    -> Agent runner (turns and steps)
         -> Model adapter
         -> Authorized tool dispatcher
         -> Session events and stream
    -> UI / audit / observability consumers

Independent platform services:
    identity + tenant policy
    secret broker + network egress rules
    job queue + leases + durable checkpoints
    evaluation + usage budgets + billing
    approval + idempotency + external-effect reconciliation
```

This is a **design recommendation informed by the code**, not a claim that DeepSeek Harness ships that exact distributed architecture.

## 10. How to study the implementation, step by step

To get value from the [interactive explorer](/en/labs/deepseek-harness-clarity/), follow a deliberate path:

1. **Full model:** identify entry/composition, execution core, model providers and session state. Do not mistake conceptual boundaries for deployments.
2. **Focus:** select `agent-loop`, inspect its incoming and outgoing *declared dependencies*, then drill into its source files.
3. **Code path:** follow inbox claim → request preparation → model stream → tool execution → durable events. Each stage has a pinned file and line.
4. **Code reader:** open `agent.ts` and `tool-calls.ts`. See where the real method calls happen, not just where modules import each other.
5. **Agent turn flow:** compare the code calls with the editorial lifecycle; ask what happens when input is rejected, the model fails, tools are denied, or the UI disconnects.
6. **Validate one extension:** imagine replacing the LLM adapter or adding an authorization guard; identify the service, event, registration lifetime, configuration row and test boundary.

If you can explain **who owns the state, who can intercept an operation, what becomes durable, and what happens after a failure**, you understand far more than the boxes in the architecture diagram.

## 11. Questions worth testing before adopting this approach

- Can the runtime be shut down and restarted without leaking listeners or losing accepted session context?
- What is the authoritative state if a tool executed but the process crashed before its result was persisted?
- Can a plugin intercept an authorization decision in the wrong order?
- Does replacing a model provider preserve prompt and tool-schema semantics?
- Which parts of a transcript can be redacted or deleted without breaking audit/recovery requirements?
- Can a long-running workload continue through process changes, not just browser reconnects?
- What are the measured costs of event logging, profile initialization and token-heavy retries?

Those questions turn a repository tour into an architecture review.

## The takeaway

DeepSeek Harness teaches a valuable distinction: **an agent is not just a model inside a while-loop**. It is a composed runtime with state, policies, capabilities, event contracts, lifecycles and observable failure boundaries.

Its *everything-is-a-plugin* design is compelling because it makes the runtime itself an extension surface. Its append-only, model-visible session history gives developers a stronger explanation of behavior than chat messages alone. But its complexity, rapidly evolving interfaces and developer-preview security posture are real costs.

The best lesson is not to copy DeepSeek Harness wholesale. **Borrow its explicit seams, owned lifecycles, durable-vs-live separation, and source-grounded observability; then add whatever governance and distributed execution your own system requires.**
