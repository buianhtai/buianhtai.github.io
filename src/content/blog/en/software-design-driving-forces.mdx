Before you can talk about *how* to design software, you need to know *why* software exists. The answer sounds obvious when stated plainly — and it turns out to be more powerful than it appears. Every design debate I've seen that drags on for hours could usually be resolved in minutes by returning to this single question: what is this software actually *for*?

## <Label color="teal">1</Label> The Purpose of All Software

The most foundational principle in software design:

> **The purpose of software is to help people.**

What counts as "people"? Users, obviously. But also: programmers using your library, accountants using your accounting tool, scientists using your data processing pipeline. Software that helps animals or plants is really helping the people who care for them. Software that "helps the computer" is nonsense — computers don't need help. Even the most deep system software ultimately exists because some person benefits from it.

What about software built "to make money"? Making money is a valid goal for an *organization*, but it should not be the *purpose of the software itself*. The empirical observation: the amount of money a software company makes is directly tied to how much the software helps people. So even from a pure business perspective, centering on users is the right strategy.

## <Label color="teal">2</Label> Applying the Purpose to Feature Decisions

The purpose statement turns into a practical filter immediately. For any proposed feature, ask: **How does this help [our users] do [what they're trying to do]?**

## <Label color="teal">3</Label> The Three Goals of Software Design

From the purpose, three concrete goals follow:

**Goal 1**: Allow us to write software that is as helpful as possible.
The immediate goal — being helpful now.

**Goal 2**: Allow our software to continue to be as helpful as possible.
The longitudinal goal — staying helpful over time, not degrading.

**Goal 3**: Design systems that can be created and maintained as easily as possible by their programmers, so that they can be — and continue to be — as helpful as possible.
The instrumental goal — the traditional "make it maintainable" framing, but now grounded in *why*: because unmaintainable software eventually stops being helpful.

Goal 3 is what most people think software design is about. But without Goals 1 and 2, Goal 3 loses its anchor. Maintainability is not a virtue in itself — it is the means by which software continues to help people over time.

<Callout color="amber">
When goals 1 and 3 conflict — when making software more helpful makes it harder to maintain — favor helpfulness, but keep it in check. The phrase "as easily as possible" in Goal 3 is not a license to abandon maintainability; it just means you don't sacrifice user value for premature abstraction.
</Callout>

## <Label color="teal">4</Label> What the Purpose Rules Out

Centering on "helping people" rules out several common but corrosive design goals:

- **"Show off how intelligent I am"** — Leads to code that impresses the author and baffles everyone else
- **"Use the latest technologies"** (as a purpose, not a means) — Introduces complexity in service of novelty, not users
- **"Be cute"** or **"have an edgy design"** — Marketing goals that should not drive technical decisions
- **"Expand the feature set"** arbitrarily — The word processor that also reads email is violating its own purpose

This is the *software's* purpose, not the *organization's* purpose. Organizations can legitimately want to make money, gain market share, or impress investors. But when those organizational goals start directing what the software itself does, the software's purpose gets corrupted — and so does its quality.

Sticking to one clear purpose is not a commercial limitation. Soap cleans things. Salt makes things salty. Light bulbs light things up. Each has supported enormous corporations for decades without scope creep.
