Chapter 4 of *Head First Design Patterns* is about the word `new`. Every time you write `new ConcreteThing()`, you create a dependency on that concrete type — and when requirements change, that dependency becomes a liability. The chapter walks through three progressively more powerful patterns for managing object creation, anchored by a pizza store that grows from a single shop to a national franchise with regional ingredient suppliers.

## <Label color="teal">1</Label> The Problem with `new`

`new` is not wrong. It is a fundamental Java operator. The problem is what it implies: a hard dependency on a specific concrete class, baked into the source at compile time.

```java
Pizza orderPizza(String type) {
    Pizza pizza;
    if (type.equals("cheese"))    pizza = new CheesePizza();
    else if (type.equals("clam")) pizza = new ClamPizza();
    else if (type.equals("veggie")) pizza = new VeggiePizza();

    pizza.prepare();
    pizza.bake();
    pizza.cut();
    pizza.box();
    return pizza;
}
```

The pizza ordering logic — `prepare`, `bake`, `cut`, `box` — is stable. It will not change. The concrete pizza types are volatile: new types get added, old ones are retired, regional variations appear. Every time the type set changes, this method must be reopened and edited. The Open-Closed Principle is violated at the object creation site.

The solution in all three factory patterns is identical in spirit: **identify the part that varies (which concrete type to create), extract it, and encapsulate it.**

## <Label color="teal">2</Label> Simple Factory — Centralizing `new`

The Simple Factory is not a Gang-of-Four design pattern. HFDP calls it a programming idiom and gives it an "Honorable Mention." It earns its place because it is the first step toward clean creation logic and the most common factory-shaped code you will encounter in real codebases.

The idea: extract the conditional creation block into a dedicated class whose only job is making pizza objects.

```java
public class SimplePizzaFactory {
    public Pizza createPizza(String type) {
        Pizza pizza = null;
        if (type.equals("cheese"))    pizza = new CheesePizza();
        else if (type.equals("clam")) pizza = new ClamPizza();
        else if (type.equals("veggie")) pizza = new VeggiePizza();
        return pizza;
    }
}

public class PizzaStore {
    SimplePizzaFactory factory;

    public PizzaStore(SimplePizzaFactory factory) {
        this.factory = factory;
    }

    public Pizza orderPizza(String type) {
        Pizza pizza = factory.createPizza(type);
        pizza.prepare();
        pizza.bake();
        pizza.cut();
        pizza.box();
        return pizza;
    }
}
```

`orderPizza` no longer contains a single `new ConcreteType()`. The creation logic lives in one place: `SimplePizzaFactory`. If three other classes also need pizzas created — a `PizzaShopMenu`, a `HomeDelivery` class — they all use the same factory. There is now one place to edit when the type set changes.

The limitation: `SimplePizzaFactory` is a concrete class. You cannot subclass it to vary behavior without introducing your own hierarchy. It solves the "one place to change" problem but not the "different creation behavior per context" problem.

<Callout color="teal">
A static factory method (`public static Pizza create(String type)`) is a common variant. It has the same centralization benefit, but you cannot subclass it to swap behavior — the method is bound at compile time. Use the instance-based factory when you need the flexibility to substitute implementations.
</Callout>

## <Label color="teal">3</Label> Factory Method — Subclasses Decide

The franchise scenario forces the design to evolve. New York and Chicago franchisees both make pizza, but they follow different regional styles. The process — prepare, bake, cut, box — is the same. The type of pizza produced differs by location.

The Factory Method Pattern solves this by moving the creation decision into subclasses:

> **Factory Method Pattern:** Define an interface for creating an object, but let subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses.

```java
// Creator — abstract
public abstract class PizzaStore {
    // The factory method — subclasses implement this
    protected abstract Pizza createPizza(String type);

    // The template — same for all franchisees
    public Pizza orderPizza(String type) {
        Pizza pizza = createPizza(type);  // subclass decides what this is
        pizza.prepare();
        pizza.bake();
        pizza.cut();
        pizza.box();
        return pizza;
    }
}

// Concrete Creator
public class NYPizzaStore extends PizzaStore {
    protected Pizza createPizza(String type) {
        if (type.equals("cheese")) return new NYStyleCheesePizza();
        if (type.equals("clam"))   return new NYStyleClamPizza();
        return null;
    }
}

// Another Concrete Creator
public class ChicagoPizzaStore extends PizzaStore {
    protected Pizza createPizza(String type) {
        if (type.equals("cheese")) return new ChicagoStyleCheesePizza();
        if (type.equals("clam"))   return new ChicagoStyleClamPizza();
        return null;
    }
}
```

`orderPizza()` is defined once in `PizzaStore` and never modified. The "which concrete Pizza class" decision is entirely owned by the subclass through `createPizza()`. The superclass controls the process; the subclass controls the product.

The key structural insight: Factory Method creates a **parallel class hierarchy**. For every ConcreteCreator, there is a corresponding ConcreteProduct. The mechanism is inheritance — the subclass relationship is what makes the factory method overridable.

## <Label color="teal">4</Label> Dependency Inversion Principle

The Factory Method Pattern is an expression of the **Dependency Inversion Principle**:

> **Depend on abstractions. Do not depend on concrete classes.**

Without factories, high-level policy code (`orderPizza`) directly depends on low-level implementation classes (`NYStyleCheesePizza`). The dependency arrows point from abstraction down to concretions. Dependency Inversion flips this: `PizzaStore` depends on the abstract `Pizza` type, and concrete stores depend on concrete pizza types — but the high-level module never touches the low-level modules directly.

Practical guidelines that follow from DIP:
- No variable should hold a reference to a concrete class (use factories to avoid `new ConcreteType()`).
- No class should derive from a concrete class — derive from abstractions (interfaces or abstract classes).
- No method should override an implemented method of any of its base classes.

These are guidelines, not absolutes. You will break all three in any real codebase. The value is in applying them at the volatile parts of a design — the parts most likely to require extension.

## <Label color="teal">5</Label> Abstract Factory — Families of Objects

The franchise grows further. The franchisee problem was about which *style* of pizza to create. A new problem emerges: ingredient suppliers. NY uses thin crust, marinara sauce, and Reggiano cheese. Chicago uses thick crust, plum tomato sauce, and Mozzarella. The ingredient sets are *families* of related objects that must be used together.

The **Abstract Factory Pattern** defines an interface for creating a family of related objects without specifying their concrete classes.

```java
// Abstract Factory
public interface PizzaIngredientFactory {
    Dough createDough();
    Sauce createSauce();
    Cheese createCheese();
    Veggies[] createVeggies();
    Pepperoni createPepperoni();
    Clams createClam();
}

// Concrete Factory — NY
public class NYPizzaIngredientFactory implements PizzaIngredientFactory {
    public Dough createDough()       { return new ThinCrustDough(); }
    public Sauce createSauce()       { return new MarinaraSauce(); }
    public Cheese createCheese()     { return new ReggianoCheese(); }
    // ...
}

// Concrete Factory — Chicago
public class ChicagoPizzaIngredientFactory implements PizzaIngredientFactory {
    public Dough createDough()       { return new ThickCrustDough(); }
    public Sauce createSauce()       { return new PlumTomatoSauce(); }
    public Cheese createCheese()     { return new MozzarellaCheese(); }
    // ...
}
```

The `Pizza` class receives the factory and uses it during `prepare()`:

```java
public class CheesePizza extends Pizza {
    PizzaIngredientFactory ingredientFactory;

    public CheesePizza(PizzaIngredientFactory ingredientFactory) {
        this.ingredientFactory = ingredientFactory;
    }

    void prepare() {
        dough  = ingredientFactory.createDough();
        sauce  = ingredientFactory.createSauce();
        cheese = ingredientFactory.createCheese();
    }
}
```

Now `CheesePizza` is ingredient-agnostic. Inject an `NYPizzaIngredientFactory` and you get a NY-style cheese pizza. Inject a `ChicagoPizzaIngredientFactory` and you get a Chicago-style cheese pizza — same class, different factory, different product family.

The fundamental distinction HFDP draws: Factory Method uses **inheritance** — the subclass relationship is the extension mechanism. Abstract Factory uses **object composition** — the factory interface is injected, and swapping the concrete factory swaps the entire product family. Both patterns hide concrete type creation from client code; they differ in the axis along which variation is expressed.

<Callout color="green">
Abstract Factory is often implemented using Factory Methods internally — each method on the factory interface (`createDough()`, `createSauce()`) is itself a factory method. The patterns are complementary, not competing.
</Callout>

**Key takeaways from Chapter 4:**

- `new ConcreteThing()` creates a hard dependency. Factories centralize and encapsulate that dependency so client code depends only on abstractions.
- **Simple Factory** is an idiom — one class, one job, one place to change. Not a GoF pattern but practically useful.
- **Factory Method** defines the creation interface in a superclass and defers the decision to subclasses. Extension happens by adding a new subclass, not modifying the existing one.
- **Abstract Factory** provides an interface for creating a *family* of related products. Swapping the factory implementation swaps the entire product family — no client code changes.
- The **Dependency Inversion Principle** is the theoretical grounding: high-level modules should not depend on low-level modules; both should depend on abstractions.
- Factory Method = inheritance. Abstract Factory = composition. Know which axis of variation your design needs before choosing.
