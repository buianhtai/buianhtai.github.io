Every previous chapter has been building toward one payoff: because Rust already tracks ownership and borrowing precisely, it can extend the exact same rules across thread boundaries — and catch a whole category of concurrency bugs at compile time that Java can only catch by getting lucky in testing or unlucky in production.

## Explain it simply

Picture a shared office kitchen with a sign taped above the sink: "please wash your mug before leaving." It works — as long as everyone reads the sign, remembers it, and actually complies every single time. If one person is rushing to a meeting and skips it, nothing stops them. The sign has no enforcement mechanism; it's a request, not a rule.

Now picture a kitchen where the cabinet holding the good mugs is physically locked, and the only key hangs on a hook that can hold exactly one key at a time. If you're holding the key, you can open the cabinet. If you're not, you physically cannot — there's no way to skip the rule by accident, because the door itself won't open without it.

Java's thread safety is the sign. Rust's is the lock.

## Find the crack

```java
class Counter {
    private int count = 0;
    void increment() { count++; }        // NOT thread-safe — no lock here
    int get() { return count; }
}
```

Nothing about this class's *type* tells you it's unsafe to share across threads. It compiles fine. It might even pass tests that don't happen to trigger the race. The unsafety is a fact about how the class is *used*, not something the type system tracks — and `synchronized` fixes it only if every caller remembers to reach for it, everywhere, forever, including three years from now when someone adds a new access path during a refactor.

## Formalize it precisely

## <Label color="teal">1</Label> `Send` and `Sync` — compiler-checked, not documentation-checked

- **`Send`**: a type can be safely *moved* to another thread.
- **`Sync`**: a type can be safely *shared* (via `&T`) across threads.

These aren't annotations you write — they're automatically derived based on what a type contains, and the compiler refuses to compile code that violates them:

```rust
use std::thread;
use std::rc::Rc;

fn main() {
    let shared = Rc::new(5);
    let handle = thread::spawn(move || {
        println!("{shared}"); // error: `Rc<i32>` cannot be sent between threads safely
    });
    handle.join().unwrap();
}
```

`Rc<T>` (Chapter 6) is deliberately *not* `Send` — its reference count isn't safe to update from multiple threads at once without extra coordination. The fix isn't a runtime patch; it's using the thread-safe equivalent, `Arc<T>` (atomic reference counting), instead.

## <Label color="green">2</Label> `Arc<Mutex<T>>` — shared, safe, mutable state across threads

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = Vec::new();

    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut value = counter.lock().expect("mutex not poisoned");
            *value += 1;
        }));
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("total: {}", *counter.lock().unwrap()); // always 4, never a race
}
```

`Arc` is `Rc`'s thread-safe sibling. `Mutex<T>` wraps the value itself — you can't even get at the `i32` inside without going through `.lock()` first, and `.lock()` returns a guard that releases automatically when it goes out of scope. There's no way to accidentally read or write the value without holding the lock, because the type itself doesn't expose the data any other way. Compare that to Java's `Counter` above, where `count` is a plain `int` field anyone can touch with or without `synchronized`.

## <Label color="amber">3</Label> Channels — sharing by passing, not by holding a lock

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        for i in 1..=3 {
            tx.send(i).unwrap();
        }
    });

    for received in rx {
        println!("got: {received}");
    }
}
```

Instead of multiple threads reaching into the same shared memory, ownership of each message *moves* through the channel — Chapter 1's move semantics, applied to cross-thread communication. Java's `BlockingQueue` offers a similar pattern, but again as a convention you opt into, not something the type system requires when data crosses a thread boundary.

<Callout color="rose">
  Rust does not eliminate deadlocks or logical races — you can still design a program that locks two mutexes in inconsistent order and deadlocks itself. What Send/Sync eliminate is a *specific, common* bug class: unsynchronized shared mutable state slipping past code review because nothing forced anyone to notice it.
</Callout>

## Teach it back

1. Why is `Rc<T>` not `Send`, and what type would you reach for instead if you need the same shared-ownership pattern across threads?
2. In the `Arc<Mutex<T>>` example, what actually stops two threads from reading and writing `counter`'s inner value at the same time — is it a convention, or something the type enforces?
3. What's the practical difference between Java's `synchronized` keyword and Rust's `Mutex<T>` in terms of what happens if a caller forgets to use them correctly?
4. Does Rust's Send/Sync system prevent deadlocks? If not, what specific class of bug does it actually prevent?
