You are running Claude Code, OpenCode, Codex, or Cursor. Each one is good at executing tasks. None of them remember yesterday. A loop that burned 40,000 tokens on Tuesday will burn 40,000 tokens again on Wednesday. A tool sequence that always fails for a specific file type will be tried again next session. The agent that got stuck on a permissions error yesterday has no record of it.

This is not a model capability problem. It is an infrastructure problem.

## <Label color="rose">1</Label> The Stateless Agent Problem

<Card>

Modern coding agents are stateless across sessions by design. Each run loads its instructions, receives your message, and executes. When the session ends, the execution state is gone. The next run starts fresh.

This is a reasonable default for simple tasks. It becomes a compounding liability for complex, repeated, or multi-day work.

Consider what actually happens over a week of heavy agent use:

- Monday: agent loops on `read_file` for 12 consecutive calls. Claude's loop detector force-stops it. You note the pattern, move on.
- Tuesday: same agent, same codebase, similar task. Loop happens again. Same force-stop. Same wasted tokens.
- Wednesday: you add a note to AGENTS.md manually. The loop doesn't happen Thursday.

The fix worked — but it required a human to observe the pattern, diagnose it, and write the fix. The agent had all the evidence it needed to do this itself. It just had nowhere to put it.

</Card>

<Callout color="amber">
The agents are not broken. They are doing exactly what they were designed to do. The missing piece is the persistent learning layer that sits between sessions.
</Callout>

## <Label color="teal">2</Label> What "Learning" Actually Means Here

<Card>

Learning in this context is not model fine-tuning. It is not RAG over conversation history. It is something simpler and more actionable:

**After a run fails, extract a structured lesson. Before the next run starts, inject that lesson into context.**

That is the entire loop. The mechanism is boring on purpose — write to a SQLite database, surface via an MCP tool call. No vector databases. No model updates. No infrastructure beyond SQLite and a small Node.js process.

The intelligence is in what gets extracted and how it gets written. A lesson that says "be careful" is useless. A lesson that says "when reading from `src/generated/`, stop after 3 consecutive reads of the same directory — the content does not change between calls" is actionable.

The difference is failure classification. Without knowing *why* a run failed, you cannot write a useful lesson. With classification, the lesson writes itself.

</Card>

<Card>

The v0.1 integration story is straightforward: evolvr ships as an MCP server (`@evolvr/mcp`) and a CLI hook handler (`@evolvr/cli`). Claude Code connects to the MCP server via `~/.claude/mcp.json`. Three `settings.json` hooks — PreToolUse, PostToolUse, Stop — feed every tool call into the journal via `evolvr hook`. The MCP `evolvr_get_lessons` tool lets the agent pull relevant lessons at the start of any session.

The result is full observability and lesson injection with two config changes and no code modifications to the agent.

## <Label color="amber">4</Label> Why Existing Tools Don't Solve This

<Card>

The obvious objection: isn't this just memory? Don't mem0, MemGPT, and LangSmith already do this?

No. Here's the distinction:

**Memory systems** store conversation content — what was said, what was written. They let the agent recall past context. They do not classify failures. They do not extract lessons. They do not modify AGENTS.md.

**Observability tools** (LangSmith, Phoenix, Langfuse) record traces and spans. They surface what happened to a human operator. They do not act on what they see. The human is still the learning loop.

**evolvr** is a learning system. The output is not stored conversations and not dashboards — it is structured lessons delivered to the agent as MCP tool responses. The agent behaves differently next run because it receives specific, evidence-backed guidance before starting. Autonomously, with a review gate.

</Card>

## <Label color="violet">5</Label> The Three Systems

<Card>

evolvr ships as three packages that compose into the learning loop:

**`@evolvr/core`** — Types, SQLite (via libsql) and PostgreSQL adapters, the rule-based failure classifier, and the `Evolvr` class. The core logic. No CLI, no HTTP, no MCP.

**`@evolvr/cli`** — The `evolvr` CLI. Handles `init`, `status`, `tasks`, `lessons`, and the `hook` command that Claude Code's settings.json hooks invoke. The hook command is the write path: every tool call lands here.

**`@evolvr/mcp`** — An MCP server built on `@modelcontextprotocol/sdk`. Exposes four tools: `evolvr_record_tool_call`, `evolvr_session_end`, `evolvr_get_lessons`, `evolvr_get_status`. This is the read path: agents call `evolvr_get_lessons` before starting work and receive relevant lessons as structured text.

</Card>

<Callout color="violet">
The learning loop: run fails → failure classified → lesson extracted → lesson stored → next run calls evolvr_get_lessons → lesson injected into context → mistake doesn't recur. The entire loop is evidence-gated and operator-reviewable at every step.
</Callout>

## <Label color="teal">6</Label> What the Loop Looks Like End-to-End

<FlowStep step="1" color="teal" title="Agent run starts">
Agent calls `evolvr_get_lessons` via MCP (or Claude Code hook fires `evolvr hook --event start`). Relevant lessons for the current task are returned as structured text and prepended to the agent's context.
</FlowStep>

<FlowStep step="2" color="green" title="Tool calls are recorded">
Each PreToolUse and PostToolUse hook invocation fires `evolvr hook --event pre-tool / post-tool`. Args are hashed, results are hashed and summarized, latency is recorded. No raw content is stored.
</FlowStep>

<FlowStep step="3" color="amber" title="Session ends — classifier runs">
The Stop hook fires `evolvr hook --event stop`. The core classifier runs over the completed task record: rule-based detectors check for loop patterns (exact repeat, read-only streak, same-result cycling). If a pattern is found, a lesson is extracted.
</FlowStep>

<FlowStep step="4" color="violet" title="Lesson stored with confidence">
If confidence ≥ 0.6, the lesson is written to the journal with trigger pattern, recommendation text, and agent scope. Evidence count increments. Lessons below threshold go to a review queue.
</FlowStep>

<FlowStep step="5" color="rose" title="Next session starts smarter">
`evolvr_get_lessons` returns the top 5 relevant lessons. The agent reads them as part of its context. The mistake that caused the lesson does not recur.
</FlowStep>

## <Label color="sky">7</Label> MVP Scope — What Ships in v0.1

<Card>

Version 0.1 is deliberately minimal — deterministic classifiers only, no LLM required:

1. **`@evolvr/core`** — SQLite (libsql) + Postgres adapters, task journal, rule-based classifier (3 detectors), lesson store
2. **`@evolvr/cli`** — `evolvr init`, `evolvr status`, `evolvr tasks`, `evolvr lessons`, `evolvr hook`
3. **`@evolvr/mcp`** — MCP server with 4 tools for agent integration
4. **Claude Code integration** — PreToolUse/PostToolUse/Stop hooks via `settings.json`
5. **Any MCP-compatible agent** — works with Cursor, Windsurf, or any tool that speaks MCP

Everything else — LLM-based semantic classifier (v0.2), auto-promotion to AGENTS.md (v0.3), OpenCode plugin and Codex adapter (v0.4) — is roadmap. The MVP proves the loop before adding intelligence to it.

</Card>
