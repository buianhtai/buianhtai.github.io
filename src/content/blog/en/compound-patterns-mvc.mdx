No pattern exists in isolation. Real systems combine them — and the combinations develop their own character. The most important compound pattern in software is MVC: Model, View, Controller. It bundles Observer, Strategy, and Composite into an architectural pattern that cleanly separates state, display, and input handling.

| Pattern | Role in MVC |
|---|---|
| **Observer** | Model notifies View(s) of state changes. Multiple views can observe one model. Model never imports the view. |
| **Strategy** | The controller is the view's strategy for responding to user input. Swap the controller and the view behaves differently without a line change in the view itself. |
| **Composite** | Complex views are trees of nested UI components (panels, buttons, text fields). Each implements the same display interface. |

## <Label color="teal">3</Label> A Concrete MVC Example: BPM Controller

A BPM (beats per minute) controller: a Model generates a heartbeat at a configurable BPM, a View displays controls and current BPM, a Controller translates button clicks into model calls.

**Model** exposes:
```java
public interface BeatModelInterface {
    void initialize();
    void on(); void off();
    void setBPM(int bpm);
    int getBPM();
    void registerObserver(BeatObserver o);
    void removeObserver(BeatObserver o);
}
```

**View** registers as an Observer. On notification it pulls current BPM and redraws:
```java
public void updateBPM() {
    int bpm = model.getBPM();
    bpmOutputLabel.setText("Current BPM: " + bpm);
}
```

**Controller** receives user input and calls the model:
```java
public void actionPerformed(ActionEvent event) {
    if (event.getSource() == setBPMButton) {
        model.setBPM(Integer.parseInt(bpmTextField.getText()));
    } else if (event.getSource() == increaseBPMButton) {
        model.setBPM(model.getBPM() + 1);
    }
}
```

The Model never mentions `bpmOutputLabel`. The View never contains business logic. The Controller never reaches into `bpmOutputLabel` directly. Three clean boundaries.

The model changes → observers are notified → views pull the updated state → display updates. The controller is just a pass-through; it handles no display logic. The view handles no business logic.

## <Label color="teal">5</Label> MVC and the Web

Web MVC (Spring MVC, Rails, Django, Laravel) follows the same structure:

| Desktop MVC | Web MVC |
|---|---|
| View: Swing panel | View: HTML template |
| Controller: ActionListener | Controller: HTTP handler (servlet, action) |
| Model: Java object | Model: database-backed domain object |
| Observer notification | HTTP redirect / re-render |

The Observer mechanism is replaced by the request-response cycle (the browser re-requests the page), but the separation of concerns is identical. The controller receives the request, calls the model, then tells the view to render with the updated model state.

<Callout color="teal">
MVC is old — it originated in Smalltalk in the late 1970s — and it is still the dominant architecture for interactive applications because the separation it enforces is genuinely correct. Keeping model state, display logic, and input handling in separate layers means you can change any one without touching the others. That's not a pattern; it's a fact about the independence of those concerns.
</Callout>
