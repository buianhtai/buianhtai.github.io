Batch processing (Ch10) assumes bounded input: a job reads a fixed dataset, transforms it, and terminates. But most real-world data is unbounded — it arrives continuously and never "finishes." Users generate events today, tomorrow, and indefinitely. Waiting until end-of-day to process them introduces latency that many applications can't tolerate.

**Stream processing** eliminates the artificial batch boundary: process each event as it arrives. Chapter 11 explores how to build correct, fault-tolerant, and low-latency stream processing systems — and why "correct" is much harder than it sounds when time, event order, and consumer failures all conspire against you.

## <Label color="teal">1</Label> Events, Producers, Consumers, Topics

A **stream** is a sequence of **events** — small, immutable, timestamped records describing something that happened (a user clicked a button, a temperature sensor read 23°C, a payment was submitted). Events flow from **producers** (publishers) to **consumers** (subscribers). Related events are grouped into **topics** or **streams**.

The fundamental question: how do producers and consumers communicate reliably?

## <Label color="teal">2</Label> Log-Based Message Brokers (Kafka)

Kafka's core insight: treat the message broker as a **durable, append-only log** rather than a queue that deletes messages after delivery.

**Key properties of log-based brokers:**
- **Ordering within a partition**: events within a partition are totally ordered; events across partitions are not ordered relative to each other
- **Consumer offset**: each consumer group tracks its position as an offset number; if a consumer crashes and restarts, it resumes from its last committed offset
- **Replay**: because messages are never deleted (until retention window expires), a consumer can rewind its offset to reprocess historical events
- **High throughput**: sequential disk writes (append) + sequential disk reads (scan) approach disk bandwidth limits; much faster than random-access storage

**Throughput scaling**: a topic is split across multiple partitions; each partition is a separate append log on a separate node. Writing scales by writing to more partitions; reading scales by adding more consumer instances (one per partition).

<Callout color="teal">
The fundamental difference between a queue and a log: a queue deletes a message once it's been consumed; a log retains it. This makes the log replayable and decouples producer speed from consumer speed.
</Callout>

## <Label color="teal">3</Label> Databases and Streams: CDC and Event Sourcing

Kleppmann argues that databases and event streams are two views of the same underlying concept. Every write to a database is an event — a record of a fact that happened at a point in time.

**Change Data Capture (CDC)** makes this explicit: capture every row-level change (insert, update, delete) from a database's write-ahead log and publish it as a stream of events. Downstream consumers (search indexes, caches, analytics systems, other databases) subscribe and maintain their own derived state.

CDC solves the dual-write consistency problem: there is one authoritative source of truth (the database WAL); all derived views are eventually consistent projections of the same event stream.

**Event Sourcing** takes this further: instead of storing current state (mutable rows), store only the immutable log of events that led to the current state. Current state is *derived* by replaying the log.

**Benefits of event sourcing:**
- Full audit history — every change is recorded, not overwritten
- Temporal queries — reconstruct the state at any past point in time by replaying to that offset
- New projections — add new derived views by replaying the entire log from the beginning
- Debugging — diagnose exactly what happened by reading the event sequence

**Costs of event sourcing:**
- Consumers are asynchronous — "read your own writes" consistency requires care
- Log compaction required for long-lived topics (otherwise unbounded growth)
- Deletion is hard — GDPR "right to be forgotten" conflicts with immutable event logs (requires cryptographic deletion or compaction that removes specific events)

## <Label color="teal">4</Label> Processing Streams: Time, Windows, and Joins

### Event Time vs. Processing Time

An event has two timestamps:
- **Event time**: when the event actually occurred (recorded in the event payload)
- **Processing time**: when the stream processor processes the event

These diverge in practice: a mobile client generates events offline and batches them; they arrive hours late. A network partition delays a batch of events by minutes. A slow consumer falls behind and processes old events.

**Most interesting stream analytics are based on event time** (e.g., "clicks per minute during the promotion window"). But stream processors see events in processing order. An event with an old event time may arrive after a window based on that time has already "closed."

<Callout color="amber">
Correct event-time windowing requires deciding: how long do you wait for late events before closing a window? There is no universally correct answer. Kleppmann calls this the "straggler problem" — you must choose a point at which you declare the window closed and emit results, accepting that some late events will be missed or trigger corrections.
</Callout>

## <Label color="teal">5</Label> Fault Tolerance: Exactly-Once Processing

Batch processing achieves fault tolerance by retrying failed tasks from immutable inputs — safe because mappers are deterministic and idempotent.

Stream processing is harder: the stream is ongoing. If a consumer fails, it resumes from its last committed offset — but some events may have been processed without the offset being committed (at-least-once delivery). Or offsets may be committed before events are processed (at-most-once delivery).

**Approaches to exactly-once semantics:**

    { Approach: "Microbatch", Mechanism: "Divide the stream into small time-based batches; apply batch semantics (at-least-once within batch + idempotent output). Latency ~ batch size.", "Used by": "Spark Structured Streaming" },

/>

In practice, **at-least-once delivery + idempotent consumers** is the most pragmatic approach for most applications. True exactly-once semantics requires distributed transactions or careful checkpointing and adds significant complexity. Choose based on whether duplicates are tolerable (usually yes for analytics; usually no for payment processing).

## <Label color="teal">6</Label> The Log as the Database: Turning the Database Inside Out

One of Kleppmann's most thought-provoking arguments: the traditional database model (mutable state + query interface) is actually derived from a more fundamental primitive — the **immutable event log**. He quotes Martin Fowler: "The truth is the log. The database is a cache of a subset of the log."

The stream processing architecture inverts the traditional architecture:

This is the essence of **CQRS** (Command Query Responsibility Segregation): separate the write model (commands → events appended to log) from the read model (events projected into optimized read structures). Each read model is optimized for its consumers; none is "the database" — they are all derived views.
