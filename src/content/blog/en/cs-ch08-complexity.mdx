If Chapter 7 is about what simplicity is and how to achieve it, Chapter 8 is about what complexity is and how it accumulates. The horror stories that open the chapter — "we've been working on this for five years and it's still not done," "we can't ship fast enough to keep up" — are not caused by bad luck or difficult requirements. They are caused by complexity building on complexity, compounding non-linearly until forward progress becomes nearly impossible.

## <Label color="teal">1</Label> Why Complexity Compounds

Adding one new feature to a system with 10 features doesn't cost 10% more. It costs *interacting* with all 10 existing features. If the feature takes 10 hours to implement, it may take another 10 hours to ensure it interacts correctly with everything else. The more features already present, the higher the cost of the next one.

This is why complexity is not linear. A simple project that takes one month becomes a three-month project when you add complexity, and a nine-month project when you make each piece of that more complex. The compound effect of complexity is the mechanism behind "The Never-Shipping Product" pattern that kills so many software efforts.

<Callout color="amber">
Some projects start so complex that they never get a first version out. If you're in that situation: trim features. A first version that ships and helps users is worth infinitely more than a theoretically complete version that never ships.
</Callout>

A technology scores well if: it has survival potential, interoperates cleanly, demonstrates attention to quality, and allows exit.

## <Label color="teal">4</Label> When Reinvention Is Justified

The book is explicit: you should almost never build your own version of a foundational dependency (web server, protocol, database, major library) unless it is your *product*. The four valid exceptions:

1. What you need doesn't exist yet
2. All existing solutions are bad technologies that would lock you in
3. Existing solutions are fundamentally incapable of handling your needs
4. Existing solutions aren't maintained and you can't take over their maintenance

All four are rare in practice. Most reinvention is driven by a preference for control or a belief that "we'll do it better" — both of which produce complexity without proportionate benefit.

---

## <Label color="teal">5</Label> Complexity and Purpose

Even within a well-defined purpose, violations produce complexity:

- Adding features that serve a *different* purpose than the primary one creates an incoherent user interface and a maintenance burden where two unrelated concerns must be kept in sync
- Optimizing for metrics that are not your user's goals (page views, ad impressions) when the user's goal is something else creates adversarial design — complexity that actively works against the user

The test: can your software's purpose be stated in one sentence? If not, it's probably trying to do too many things.

## <Label color="teal">6</Label> When to Rewrite

The book gives three conditions that together justify a rewrite:

<FlowStep steps={[
  { title: "The system is completely unmaintainable", body: "Not 'hard to maintain' — unmaintainable. Changes require understanding so much of the system simultaneously that even experienced developers make constant mistakes when touching it." },
  { title: "A redesign won't fix it", body: "Incremental redesign is always preferred to a full rewrite. If the fundamental design is so wrong that no amount of refactoring can fix it — if the problem is architectural, not cosmetic — a rewrite becomes the only path forward." },
  { title: "You can write the new system incrementally", body: "Rewrites that replace a running system all at once are extremely high-risk. The viable path is replacing pieces while the old system remains in service — a strangler fig migration. If you can't do this, reconsider whether a rewrite is actually feasible." },
]} />

All three conditions must hold. A system that is merely complex but maintainable doesn't qualify. A system where redesign would fix the core problems doesn't qualify. A rewrite that requires a "big bang" cutover is not a solution — it just defers the reckoning.
