Fair warning before we start: everything in Chapters 1-7 was one connected idea — ownership, applied consistently, all the way down to threads. Async is not that. It's a genuinely separate concept bolted on top, and understanding ownership perfectly will not make async click on its own. Budget real time for this one.

## Explain it simply

In a restaurant, when you place an order with a waiter, the waiter immediately walks your ticket to the kitchen and a chef starts cooking. That's a Java `CompletableFuture` — the moment you create it, work begins.

Now imagine a different restaurant: you write your order on a ticket and set it down on the counter. Nothing happens. The ticket just sits there — until a chef, whenever they get around to it, picks it up off the counter and starts cooking. If no chef ever walks by, your food never gets made, no matter how long the ticket sits there. That's a Rust `Future`: creating it writes down *what should happen*, but nothing happens until something (a runtime) actually picks it up and drives it forward.

## Find the crack

Java's model works because there's always a chef in the building — the JVM's thread pool or executor is just there, running, ready to pick up work. Rust's standard library deliberately ships with **no chef at all**. If you write `async fn` and never bring in a runtime, your "orders" just accumulate on the counter forever. You have to explicitly choose and add a chef — and in the Rust ecosystem, that chef is almost always **Tokio**.

```java
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> fetchUser());
// work is already running on some thread right now
```

```rust
async fn fetch_user() -> String {
    // ...
}

fn main() {
    let future = fetch_user(); // NOTHING has happened yet — this is just a value
    // future.await;           // can't even .await outside an async context
}
```

That second snippet doesn't even compile as written — `.await` needs an async context, and running an async context needs a runtime. This is the single most common "why doesn't my Rust async code do anything" confusion, and it comes directly from the eager-vs-lazy gap above.

## Formalize it precisely

## <Label color="teal">1</Label> `#[tokio::main]` supplies the chef

```rust
#[tokio::main]
async fn main() {
    let result = fetch_user().await;
    println!("{result}");
}

async fn fetch_user() -> String {
    // pretend this awaits a real network call
    String::from("Ada")
}
```

`#[tokio::main]` is a macro that wraps your `async fn main()` in a Tokio runtime setup — it's the thing that finally puts a chef in the kitchen. Without it (or an equivalent manual runtime setup), `.await` has nothing driving it and won't compile at the top level at all.

## <Label color="amber">2</Label> Spawning concurrent tasks

```rust
#[tokio::main]
async fn main() {
    let task_one = tokio::spawn(async {
        fetch_user().await
    });
    let task_two = tokio::spawn(async {
        fetch_user().await
    });

    let (a, b) = (task_one.await.unwrap(), task_two.await.unwrap());
    println!("{a} and {b} both resolved");
}
```

`tokio::spawn` hands a `Future` to the runtime and says "run this concurrently with everything else." This is conceptually close to Java's `supplyAsync` submitting work to an executor — the difference is entirely in *when* the work actually starts: Java's starts on submission, Tokio's starts on the next time the runtime chooses to poll it.

## <Label color="rose">3</Label> The gotcha: blocking code inside async code starves the runtime

```rust
async fn do_work() {
    std::thread::sleep(std::time::Duration::from_secs(2)); // BLOCKS the whole runtime thread
    // use tokio::time::sleep(...).await instead — that one yields control back
}
```

Tokio typically runs many `Future`s cooperatively on a small pool of threads. A genuinely blocking call (a synchronous sleep, a blocking file read, a CPU-heavy loop) inside an `async fn` doesn't just block itself — it can freeze *every other task* sharing that thread, because nothing ever yields control back to the runtime. This is loosely analogous to blocking a Java NIO event-loop thread, but Rust's compiler won't warn you about it the way some frameworks try to — it's on you to know which calls are async-aware and which aren't.
