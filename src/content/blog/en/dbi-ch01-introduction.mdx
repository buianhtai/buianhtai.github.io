A database management system is not a monolith — it is a stack of cooperating components. The path of a query through a DBMS:

The **storage engine** is the focus of Part I of the book. It has five sub-components:

- **Transaction manager**: schedules transactions; ensures no logically inconsistent state
- **Lock manager**: locks database objects to ensure concurrent operations don't violate physical integrity
- **Access methods**: data structures (B-Trees, LSM Trees, heap files) that organize data on disk
- **Buffer manager**: caches pages in memory to amortize disk I/O cost
- **Recovery manager**: maintains operation logs; restores system state after failure

Transaction manager and lock manager together handle **concurrency control** — guaranteeing logical and physical integrity while maximizing concurrent throughput.

A common misconception: in-memory databases don't use disk at all. In fact, they typically use disk for durability — write-ahead logs, periodic snapshots, or both. The difference is that the primary working set is always in RAM; disk is only used for recovery, not for regular reads.

Durability in memory-based stores requires that on restart, the system can reconstruct its in-memory state. This is done by replaying the write-ahead log from a snapshot. The design challenge is minimizing replay time while keeping snapshot overhead low.

<Callout color="amber">
"In-memory" vs "disk-based" is not a binary. Many systems (Redis with AOF, SQLite WAL, RocksDB with block cache) operate on a spectrum — the working set is partially or fully cached in memory, but durable state lives on disk. The important axis is where the *primary access path* lives, not where data *can* live.
</Callout>

## <Label color="teal">3</Label> Row-Oriented vs Column-Oriented Layout

The physical organization of data on disk has profound effects on read performance for different workload shapes.

**Row-oriented (OLTP)**: all fields for one row are stored contiguously. A single page contains complete records. Reads and writes of whole records are efficient; scanning one field across all records requires reading entire pages.

```
Page: [id=1, name="Alice", age=30] [id=2, name="Bob", age=25] ...
```

**Column-oriented (OLAP)**: all values for one column are stored contiguously. A page contains only one field from many rows. Scanning or aggregating one column reads minimal data; fetching a complete row requires multiple page reads.

```
id column:   [1, 2, 3, 4, ...]
name column: ["Alice", "Bob", "Carol", ...]
age column:  [30, 25, 28, ...]
```

**Wide column stores** (Cassandra, HBase) are often confused with column-oriented stores. They are not the same. Wide column stores store data in row-key-sorted order but allow flexible schemas per row. They are column-*family* stores, not column-*oriented* stores. The distinction matters: analytical column scans are not their strength.

## <Label color="teal">4</Label> Data Files and Index Files

Most storage engines separate data storage from index storage:

- **Data files (heap files)**: records stored in insertion order or by primary key. Searching without an index requires a full scan.
- **Index files**: data structures (B-Trees, hash indexes) that map keys to record locations. Allow O(log N) lookup instead of O(N) scan.

**Primary index as indirection**: in many systems, the primary key index stores a pointer to the actual record location in a heap file. This separates key ordering from record location, allowing the heap to be append-only while the index stays sorted.

In **index-organized tables** (InnoDB, SQLite), the primary index *is* the table — records are stored directly in the B-Tree leaf nodes, ordered by primary key. Secondary indexes store the primary key as their value rather than a heap pointer.

## <Label color="teal">5</Label> The Three Core Properties

The book introduces three properties that characterize all storage structures — a useful lens for comparing and reasoning about any design:

**Buffering**: Does the structure batch writes in memory before flushing to disk? Buffering amortizes write I/O at the cost of durability risk and memory usage.

**Immutability**: Does the structure write data in place (mutable) or always append new versions (immutable)? Immutable structures simplify concurrency and crash recovery at the cost of space amplification and compaction overhead.

**Ordering**: Does the structure maintain sorted order of keys? Ordered structures support efficient range scans; unordered structures offer faster writes but require full scans for ranges.

Every storage structure in the book — B-Trees, LSM Trees, Bw-Trees, Bitcask, WiscKey — can be described using these three properties. They are the vocabulary for Part I.
