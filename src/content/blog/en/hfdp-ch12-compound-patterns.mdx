MVC bundles three patterns into a single architectural pattern:

| Pattern    | Role in MVC |
|------------|-------------|
| **Observer**   | Model notifies View(s) of state changes. Multiple views can observe the same model. The model never imports the view. |
| **Strategy**   | The controller is the view's strategy for responding to user input. Swap the controller and the view behaves differently. |
| **Composite**  | Complex views are trees of nested UI components (panels, buttons, text fields). Each component implements the same display interface. |

## <Label color="teal">3</Label> The DJView Running Example

The book implements a BPM (beats per minute) controller: a Model that generates a heartbeat at a configurable BPM, two Views (one graphical + one beat display), and a Controller that translates button clicks into model calls.

**BeatModelInterface** — what the model exposes:

```java
public interface BeatModelInterface {
    void initialize();
    void on();
    void off();
    void setBPM(int bpm);
    int getBPM();
    void registerObserver(BeatObserver o);
    void removeObserver(BeatObserver o);
    void registerObserver(BPMObserver o);
    void removeObserver(BPMObserver o);
}
```

Two observer interfaces are used because the view needs to react to two different events: a beat firing (BeatObserver) and the BPM number changing (BPMObserver). The model implements both notification loops.

**ControllerInterface** — what the controller exposes to the view:

```java
public interface ControllerInterface {
    void start();
    void stop();
    void increaseBPM();
    void decreaseBPM();
    void setBPM(int bpm);
}
```

The view calls `controller.start()` when the user clicks Start. The controller calls `model.on()`. The model fires the beat loop. The beat fires observers. The observers call `view.updateBeat()`. The view updates the display. The model never touched the view.

## <Label color="teal">4</Label> Adapter Extending MVC

The book adds a `HeartController` that drives the same DJView using a heart-monitor model (`HeartModel`) instead of a beat generator. The `HeartModel` has a completely different interface — it uses `getHeartRate()` not `getBPM()` and fires its own observer protocol.

An `HeartAdapter` wraps `HeartModel` and implements `BeatModelInterface`. Now `HeartController` can pass the adapter to the existing `DJView` with zero changes to the view or the heart model. The pattern combination: **Adapter wraps HeartModel, MVC wires it to the existing View**.

```java
public class HeartAdapter implements BeatModelInterface {
    HeartModel heart;

    public HeartAdapter(HeartModel heart) { this.heart = heart; }

    public int getBPM()   { return heart.getHeartRate(); }
    public void on()      { heart.startMonitor(); }
    public void off()     { heart.stopMonitor(); }

    // observer bridge: heart fires HeartObserver → adapter notifies BeatObserver
    public void registerObserver(BeatObserver o) {
        heart.registerObserver((HeartObserver) bpm -> o.updateBeat());
    }
    // ...
}
```

## <Label color="teal">5</Label> Why MVC Endures

<Callout color="teal">
MVC is not a GoF pattern. It is a compound pattern — a combination of patterns at the architectural level. The reason every web framework (Rails, Django, Spring MVC, ASP.NET, Ember, Angular) converges on MVC is that the separation of concerns it enforces maps directly onto the natural decomposition of interactive applications: there is always state to maintain, presentation to render, and input to translate.
</Callout>

The three invariants that make MVC robust:

1. **Model knows nothing about View or Controller.** It exposes state and fires notifications. Any view can observe it. Swapping the view (CLI → GUI → JSON API) does not touch the model.

2. **View knows nothing about the Model's internals.** It calls `model.getBPM()` — it doesn't know whether BPM is a field, a computation, or a remote call. It registers as an observer and reacts to notifications.

3. **Controller translates without deciding.** It maps user gestures to model calls. It enforces pre-conditions (don't call `setBPM(-1)`). It does not own state — the model does.

These invariants are why MVC scales to large codebases: each layer can be developed, tested, and replaced independently.

## What Compound Patterns Teach

- **Patterns layer on orthogonal concerns.** Observer handles notification. Strategy handles algorithmic substitution. Composite handles tree structure. They don't conflict because they solve different problems.
- **The combination is stable.** MVC has been in production since Smalltalk-80. Its longevity comes from the clean separation its three constituent patterns enforce, not from any single clever trick.
- **Adapter is the universal joint.** Whenever two well-designed subsystems need to talk and their interfaces don't match, an adapter makes them compatible without modifying either side. In the DJView example, a five-method adapter class lets a heart-monitor drive a beat-controller UI.
- **Start with patterns, not architecture.** The Duck Simulator shows that you don't design the compound structure upfront — you apply patterns one at a time as requirements arrive, and the compound emerges naturally.
