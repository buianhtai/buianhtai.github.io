The B-Tree is brilliant for reads. For high-throughput writes, it has a fundamental problem: in-place updates require seeking to the right page and rewriting it. Every write is a random write. Random writes are the slowest operation on any storage medium.

The Log-Structured Merge Tree (LSM Tree) asks: what if we just never did random writes at all? What if every write was a sequential append? You pay a cost — reads become more complex — but you gain write throughput that B-Trees can't match. This is the trade used in LevelDB, RocksDB, Cassandra, HBase, and many others.

## <Label color="teal">1</Label> LSM Tree Structure

An LSM Tree has two classes of components:

**Write path**: Client writes → WAL (for durability) → memtable (sorted in-memory). When the memtable reaches a size threshold, it is frozen, written as an immutable SSTable (Sorted String Table) to Level 0 on disk, and a new empty memtable takes over.

**SSTable**: an immutable, sorted file of key-value pairs. Each SSTable has an index block (sparse index of key → block offset within the file) and a data block (actual sorted records). Once written, SSTables are never modified — only created, read, and deleted.

---

## <Label color="teal">2</Label> Reads, Updates, and Deletes

**Reads**: check memtable first (most recent data). If not found, check Level 0 SSTables in recency order. If not found, check Level 1, Level 2, ... A key might exist in multiple SSTables (from prior writes); the most recent version wins.

**Updates**: not in-place modifications. A new record with the same key is appended. The old record survives in an older SSTable until compaction. During reads, the newest version is returned; old versions are invisible.

**Deletes**: written as **tombstone records** — a special marker saying "this key is deleted." Tombstones propagate downward through compaction and are removed when they reach the bottom level.

<Callout color="amber">
A delete in an LSM Tree is a write, not a removal. This has an important consequence: a deleted key continues to consume space in SSTables until compaction reaches the level where all prior versions have been merged. Under aggressive delete workloads (time-series expiry, GDPR deletion), space amplification can be significant before compaction catches up.
</Callout>

## <Label color="teal">3</Label> Compaction Strategies

Compaction reads multiple SSTables, merges them (resolving duplicates and applying tombstones), and writes new, smaller SSTables. It is the maintenance cost LSM Trees pay for their write-optimal design.

**Leveled compaction** (LevelDB, RocksDB default):
- Level N SSTables are exactly 10× the size of Level N-1
- Non-overlapping key ranges within each level (except L0)
- Compaction picks one L1 SSTable and all overlapping L2 SSTables, merges them, writes result back to L2
- Predictable read amplification (at most 1 SSTable per level to check for a point read)
- Higher write amplification — data moves through each level in sequence

**Size-tiered compaction** (Cassandra default):
- SSTables of similar size are merged together
- No level structure; files are grouped by size
- Lower write amplification (fewer merge passes for each byte written)
- Higher read amplification (many SSTables of varying sizes must be checked per read)

## <Label color="teal">4</Label> The RUM Conjecture

The RUM Conjecture (2016) formalizes the trade-off space for storage structures:

> **You cannot simultaneously optimize Read overhead, Update overhead, and Memory overhead. Optimizing any two degrades the third.**

- **B-Trees**: optimize Read and Memory (sorted structure, no extra copies) at the cost of Update overhead (in-place writes require finding the record and rewriting the page)
- **LSM Trees**: optimize Update (sequential appends) and Memory efficiency at the cost of Read overhead (must check multiple files)
- **Hash indexes**: optimize Update and Read (O(1) operations) at the cost of Memory overhead (need to store all keys in memory for range scans)

Every storage structure design is a point in this three-dimensional trade-off space. Understanding where your workload falls determines which direction to optimize.

## <Label color="teal">5</Label> Bloom Filters

**Bloom filters**: a probabilistic data structure that answers "is this key possibly in this SSTable?" A Bloom filter can produce false positives (report a key is present when it isn't) but never false negatives. For point reads, this eliminates disk reads for SSTables that definitely don't contain the key — reducing read amplification significantly.

```
For a point read of key K:
  For each SSTable (newest first):
    1. Check Bloom filter → no match: skip this SSTable entirely (no disk read!)
    2. Bloom filter match → read index block → seek to data block → check
```

**Skiplist**: the typical data structure for the memtable. A skiplist provides O(log N) search/insert/delete with lock-free concurrent access patterns — multiple readers and a single writer can operate concurrently without locks using atomic operations on the skip pointers.

## <Label color="teal">6</Label> Unordered LSM Storage

Two variants relax the sorted-order requirement for even better write throughput:

**Bitcask**: all writes are sequential appends to a single log file. An in-memory hash index maps every key to the latest record's offset in the log. Reads are: hash lookup → single disk seek → return value. Extremely fast writes and reads, but the entire key set must fit in memory.

**WiscKey**: separates keys from values in RocksDB-style leveled storage. Keys (small) are stored in a sorted LSM structure; values (large) are stored in a separate append-only value log. This drastically reduces write amplification for large values — the sorted LSM only sorts/compacts keys, not multi-KB values. Trade-off: range scans that also retrieve values require random reads into the value log.

<Callout color="teal">
The LSM vs B-Tree choice is not just about write throughput vs read throughput. It is also about operational characteristics: LSM Trees require compaction tuning, but are simpler to reason about for crash recovery (immutable files, WAL-only durability). B-Trees require vacuum and fragmentation management, but reads are simpler (one authoritative copy per key). Most production systems at write-scale choose LSM; most at read-scale or requiring predictable read latency choose B-Trees.
</Callout>
