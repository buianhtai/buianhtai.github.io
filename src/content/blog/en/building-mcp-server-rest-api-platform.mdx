I need to build an MCP service for an existing platform whose main interface is a REST API.
The tempting design is obvious: expose a generic `call_api(method, path, body)` tool and let the agent figure it out.

That is also the design I would avoid.

After looking at public MCP servers from Cloudflare, GitHub, and Microsoft, the pattern is clear:
the best MCP servers are not thin REST proxies.
They are **agent-facing product surfaces**.
They curate what the agent can see, make dangerous actions explicit, hide low-level API friction, and turn platform workflows into well-named tools.

<Callout color="teal">
An MCP server should not expose your API structure. It should expose the tasks an agent is allowed to perform safely.
</Callout>

---

## <Label color="teal">1</Label> MCP Changes the Shape of an API

REST APIs are usually built around resources:

- `GET /projects/{id}`
- `POST /documents`
- `GET /reports/{id}`
- `POST /tickets/{id}/comments`

Agents do not naturally think in endpoint paths.
They think in tasks:

- find the project related to this ticket
- explain why this report generation failed
- validate this document payload before submission
- summarize recent changes for this account
- create a safe draft change, but do not apply it yet

That difference matters.

If we expose raw REST endpoints directly, the model has to solve too many problems at once:

Instead of exporting endpoints, we export tools with schemas, descriptions, scopes, and defaults.

## <Label color="green">2</Label> Cloudflare: Split by Domain, Not by Endpoint

Cloudflare's MCP repository is interesting because it does not present one giant "Cloudflare API MCP server."
It publishes multiple focused servers, each mapped to a product or capability area:

- Documentation
- Workers Bindings
- Workers Builds
- Observability
- Browser Rendering
- Logpush
- AI Gateway

That is the first important lesson.

<Callout color="green">
Large platforms should not start with one global MCP tool catalog. They should start with domain-focused surfaces.
</Callout>

For a generic REST platform, that suggests a shape like this:

The agent sees a smaller and more meaningful tool set.

This also helps humans.
When a product team owns `Document MCP`, it can evolve that surface without coordinating every other product area.

## <Label color="amber">3</Label> GitHub: Toolsets Are a Product Feature

GitHub's MCP server makes tool configuration a first-class concern.
It supports toolsets such as repositories, issues, pull requests, actions, and code security.
It also supports selecting individual tools and running in read-only mode.

This is a big design signal.

Tool visibility is not just configuration.
It changes model behavior.

If the model sees 100 tools, it has to choose among 100 tools.
If it sees 8 tools for the current task, the probability of a correct tool call goes up.

For our platform, I would make read-only the default:

```text
platform-mcp --toolsets projects,documents,reports --read-only
```

Then expose write tools only when explicitly enabled:

```text
platform-mcp --toolsets projects,documents --tools create_document_draft,submit_project_update
```

The rule is simple:

<Callout color="amber">
If a tool can change production state, it should not appear by accident.
</Callout>

## <Label color="rose">4</Label> Microsoft: MCP Is Not Only CRUD

Microsoft's MCP ecosystem shows a different lesson.
Some MCP servers are not wrappers around business APIs at all.

Microsoft Learn MCP focuses on trusted documentation and code samples.
Playwright MCP exposes browser automation.
Azure MCP groups operational Azure capabilities.

That widens the design space.

For a platform team, MCP should include both API tools and knowledge tools.

Useful non-CRUD tools might be:

- `search_platform_docs`
- `get_openapi_operation`
- `find_request_example`
- `explain_error_code`
- `summarize_rate_limit_policy`
- `generate_safe_api_plan`

These tools reduce the number of blind API calls the agent makes.
Before calling a write endpoint, the agent can inspect the docs, fetch an example, validate the input, and explain the plan.

## <Label color="teal">5</Label> Proposed Architecture for a REST Platform MCP

The architecture I would start with has five layers.

<ArchLayer badge="AUTH" badgeColor="green" label="Identity and Scope Layer" items={["User token", "Service token", "Account/project context", "Permission checks"]} />

<ArchLayer badge="API" badgeColor="amber" label="REST Client Layer" items={["Typed clients", "Pagination helpers", "Retries", "Rate-limit handling"]} />

<ArchLayer badge="SAFE" badgeColor="rose" label="Safety Layer" items={["Input validation", "Dry-run support", "Write confirmation", "Audit logging"]} />

<ArchLayer badge="OBS" badgeColor="cyan" label="Observability Layer" items={["Tool call logs", "Latency", "Failure classification", "Redacted payload traces"]} />

This keeps the MCP server from becoming a messy pile of endpoint wrappers.

The REST client layer knows HTTP.
The MCP tool layer knows agent tasks.
The safety layer decides whether a requested action is allowed.

## <Label color="green">6</Label> Tool Design Rules I Would Use

### 1. Prefer task names over endpoint names

Good:

```text
search_projects
summarize_project_history
validate_document_payload
explain_report_failure
```

Weak:

```text
get_project_by_id_endpoint
post_document_endpoint
call_report_status_api
```

The tool name should describe the job, not the route.

### 2. Return summarized results by default

REST APIs often return large JSON documents.
Agents do not always need the full object.

For example, `get_project` can support:

```json
{
  "projectId": "...",
  "includeRaw": false
}
```

Default response:

```text
Project summary, status, owner, key attributes, recent activity, last modified time.
```

Raw response only when explicitly requested.

### 3. Make pagination invisible when possible

Instead of forcing the model to manage `offset`, `limit`, `nextPageToken`, and partial results, expose tools like:

```text
search_reports(query, maxResults)
```

Internally the MCP server can page through the REST API safely up to a limit.

### 4. Normalize errors

Do not leak raw backend errors directly.
Return a consistent envelope:

```json
{
  "ok": false,
  "kind": "missing_permission",
  "message": "The token lacks document:read for this account.",
  "retryable": false,
  "nextAction": "Ask for a token with document:read or switch to an authorized account."
}
```

Agents recover better from classified errors than from random HTTP payloads.

### 5. Separate draft, preview, and apply

For writes, I would avoid tools that immediately mutate state when a safer staged workflow exists.

Better shape:

```text
create_document_change_draft
validate_document_change
apply_document_change
```

This gives the agent and human a checkpoint before production mutation.

## <Label color="amber">7</Label> Auth and Safety Model

The public examples all point toward the same principle:
MCP does not remove the need for authorization.
It makes authorization more important because the caller is now an agent.

For a production platform, I would separate four questions:

The MCP server should never rely on the model to obey policy from text alone.
Descriptions help the model choose tools.
Backend checks enforce the rules.

## <Label color="green">9</Label> Final Takeaway

The wrong way to build an MCP server for a REST API platform is to expose every endpoint and hope the agent behaves.

Cloudflare shows the value of domain-focused MCP surfaces.
GitHub shows the value of configurable toolsets and read-only modes.
Microsoft shows that MCP can expose documentation, workflows, and operational actions — not just CRUD.

The design principle I would keep in front of the team is this:

<Callout color="green">
Build the MCP server as a safe agent interface to the platform, not as a mechanical mirror of the REST API.
</Callout>

That means fewer tools, better names, scoped permissions, read-only defaults, normalized errors, summarized responses, and explicit write workflows.

For human developers, REST remains the system API.
For agents, MCP becomes the task API.
