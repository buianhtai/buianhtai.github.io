I used to think simplicity was mostly about fewer lines of code. Write less, make it simpler. The more I've maintained large codebases, the more I've come to see that this is wrong in an interesting way. The simplest version of something is usually the result of understanding the problem deeply enough to express it clearly — and that takes *more* work upfront, not less.

## <Label color="teal">1</Label> The Law of Simplicity

> **The ease of maintenance of any piece of software is proportional to the simplicity of its individual pieces.**

This completes the loop from the maintenance equation: the equation says reduce the effort of maintenance; the Law of Simplicity says how — make the individual pieces simpler.

The key word is *individual pieces*, not the system as a whole. No human can comprehend an entire real-world software system at once. What matters is that when you look at *one piece* — a function, a class, a module — you can understand it. Simpler pieces mean any given person is more likely to understand any given part of the system when they need to work on it. That's what reduces maintenance effort.

A 30-foot structure built from small, standard girders is easy to build, easy to maintain, and easy to repair by replacing one piece. A structure forged from three giant custom pieces is difficult to build correctly, impossible to fix without disassembling the whole thing, and impossible to replace if defective.

## <Label color="teal">2</Label> Simplicity Is Relative

Simplicity is not an absolute property of code — it's relative to the audience reading it.

What is simple to the author (who understands all the context) may be incomprehensible to a new team member. What is simple to an expert in the language may be cryptic to someone from another background. What is simple in one context (lots of explanatory text in a manual) is complex in another (that same text on a highway billboard).

The practical test: find some code you've never seen and try to understand it. Not just the individual lines — the whole intent, how you'd modify it, what assumptions are being made. That experience of struggling with unfamiliar code is exactly what other developers have when they read yours. Simplicity is measured from their perspective, not yours.

<Callout color="teal">
Most "simplicity vs complexity" debates in software are actually debates about familiarity. Neither Vim nor VS Code is objectively simpler — each is simpler for people who have invested in learning it. This is true of many technical choices. Context and audience are the variables that determine the answer.
</Callout>

## <Label color="teal">3</Label> Be Consistent

The most underrated tool for simplicity is consistency. Code that is inconsistent forces readers to re-examine every detail every time, because they can't rely on anything being the same as before.

**Consistency rule**: code that does similar things should look similar; code that does different things should look different.

This applies at every level:
- **Naming conventions**: if you use `getUser()` in one place and `fetch_user()` in another, readers have to figure out whether they're the same operation or subtly different ones
- **Formatting**: if indentation, brace placement, and spacing vary by file or by author, readers spend cognitive effort parsing layout instead of logic
- **Patterns**: if you solve the same class of problem three different ways in the same codebase, each instance has to be understood from scratch rather than recognized as a familiar pattern

The simplest consistency rule: pick one way of doing something and apply it everywhere. This costs almost nothing to implement and produces enormous readability gains.

## <Label color="teal">5</Label> Readability: Comments

- **Comment on purpose, not mechanism**. Code already shows the mechanism. Comments should explain *why* something is done, not *what* the code is doing.
- **Comments shouldn't be needed for simple code**. If your code is so complex it requires a comment to explain what it does, that is evidence the code should be simplified, not that you need a better comment.
- **Comments should be updated when code changes**. A comment that describes behavior the code no longer has is worse than no comment — it actively misleads.

The worst comment is the one that describes *how* a piece of clearly readable code works — it duplicates the code in English, adds maintenance burden, and provides no information the reader couldn't get from the code itself.

## <Label color="teal">6</Label> Simplicity Requires Design

Achieving simplicity requires *more* design effort, not less. The simple version of something is usually the result of understanding the problem deeply enough to express it cleanly.

You often can't get the simple version on the first attempt. You get a working version, then simplify. The incremental design process — design, implement, redesign before the next feature — is the mechanism. The "redesign" step is where simplicity is actively built rather than hoped for.

Simplicity is the most important investment in maintenance effort reduction. Every hour spent simplifying a piece of code reduces the maintenance cost of that piece for as long as it exists. Every hour spent adding complexity — even with good intentions — compounds that cost forward indefinitely.
