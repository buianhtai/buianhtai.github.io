Chapter 5 of *Head First Design Patterns* is deceptively short. The Singleton Pattern has the simplest class diagram in the book — one class, one field, one method. But the correct implementation is genuinely subtle: naive code breaks under multithreading in ways that are difficult to reproduce and easy to miss. HFDP works through the failure modes before arriving at the solutions.

## <Label color="teal">1</Label> When Exactly One Instance Is Required

Some objects must exist exactly once in an application's lifetime. Thread pools, logging systems, device driver proxies, registry-settings objects, and dialog boxes for exclusive resources are canonical examples. Having two thread pools means work queued to one pool is invisible to the other. Having two logging instances might mean log entries written to different files with no single coherent stream. Having two registry objects means settings written through one instance might not be visible through the other.

Global variables are the obvious first response. They do not solve the problem: nothing stops a second (or third) instantiation of the class. The global variable just provides access to *one* of the instances, not a guarantee of *only one*. A language convention (never instantiate it more than once!) is not a language enforcement.

Singleton enforces the constraint in code, at the class level, with zero reliance on developer discipline.

<Callout color="teal">
Singleton gives you global point of access — exactly like a global variable — but adds the structural guarantee that only one instance exists. It also supports lazy initialization: if the instance is never needed, it is never created, avoiding resource allocation for unused heavy objects.
</Callout>

## <Label color="teal">2</Label> Classic Singleton Implementation

The mechanism is straightforward once you see it: make the constructor `private`, hold the single instance in a `static` field, and expose it through a `static` factory method.

```java
public class Singleton {
    private static Singleton uniqueInstance;

    private Singleton() {}  // nobody outside this class can call new Singleton()

    public static Singleton getInstance() {
        if (uniqueInstance == null) {
            uniqueInstance = new Singleton();  // lazy: created only when first needed
        }
        return uniqueInstance;
    }

    // useful methods and fields here
}
```

- `private Singleton()` — the constructor is inaccessible from outside the class. No external code can call `new Singleton()`.
- `static Singleton uniqueInstance` — the one field that holds the instance. `static` means it belongs to the class, not to any object.
- `static getInstance()` — a class method, callable as `Singleton.getInstance()` without an existing instance. Creates the object the first time; returns the existing one on subsequent calls.

<FlowStep step="1" color="teal" title="First call: uniqueInstance is null">
No instance exists. The null-check passes. The private constructor is invoked — this is the only code path that can call it. The new instance is assigned to uniqueInstance.
</FlowStep>

<FlowStep step="2" color="green" title="Subsequent calls: uniqueInstance is not null">
The instance was created on the first call. The null-check fails. getInstance() goes directly to the return statement. No new object is created.
</FlowStep>

<FlowStep step="3" color="amber" title="Caller receives the singleton">
The caller gets the single shared instance and invokes whatever methods it needs. Every caller in every part of the application receives the same object.
</FlowStep>

This is lazy instantiation — the object is created on first request, not at class load time. For lightweight objects this does not matter. For resource-heavy objects (a connection pool, a cache populated from disk) lazy initialization is preferable: if the object is never used, it is never created.

## <Label color="teal">3</Label> The Multithreading Problem

The classic implementation has a race condition. Suppose two threads call `getInstance()` simultaneously when `uniqueInstance` is still `null`:

1. **Thread A** enters `getInstance()`, reads `uniqueInstance == null` → true.
2. **Thread B** enters `getInstance()`, reads `uniqueInstance == null` → true. (Thread A hasn't assigned yet.)
3. **Thread A** creates a new `Singleton` and assigns it to `uniqueInstance`. Returns instance-1.
4. **Thread B** creates a new `Singleton` and assigns it to `uniqueInstance`. Returns instance-2. **The previous assignment is overwritten.**

Now two objects exist. Any state thread A wrote to instance-1 is invisible to any code that received instance-2. The entire guarantee the pattern was supposed to provide is broken — and the bug is non-deterministic, timing-dependent, and likely absent in single-threaded tests.

The Chocolate Boiler example in HFDP makes this concrete: a boiler that should be the single controller of a 500-gallon industrial process creates two instances under multithreaded load. One instance drains the boiler while the other thinks it is still full. Disaster follows.

**Fix 1 — synchronized:**

```java
public static synchronized Singleton getInstance() {
    if (uniqueInstance == null) {
        uniqueInstance = new Singleton();
    }
    return uniqueInstance;
}
```

Correct, but synchronization is acquired on every call — including the 99.9% of calls where the instance already exists and no synchronization is needed. For a high-throughput application that accesses the singleton frequently, this is unacceptable overhead.

**Fix 2 — eager instantiation:**

```java
public class Singleton {
    private static Singleton uniqueInstance = new Singleton();  // created at class load

    private Singleton() {}

    public static Singleton getInstance() {
        return uniqueInstance;
    }
}
```

The JVM guarantees that class initialization is single-threaded. The instance is created exactly once, before any thread can call `getInstance()`. No synchronization required at runtime. The trade-off: the instance is created regardless of whether it is ever needed.

**Fix 3 — double-checked locking with `volatile`:**

```java
public class Singleton {
    private volatile static Singleton uniqueInstance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (uniqueInstance == null) {               // first check — no lock
            synchronized (Singleton.class) {
                if (uniqueInstance == null) {       // second check — inside lock
                    uniqueInstance = new Singleton();
                }
            }
        }
        return uniqueInstance;
    }
}
```

The outer null-check avoids synchronization on every call after the instance exists. The inner null-check inside the `synchronized` block handles the case where two threads both passed the outer check simultaneously. `volatile` is essential: without it, the JVM may reorder the instructions inside `new Singleton()` (allocate memory, publish reference, initialize fields) such that another thread sees a non-null but partially initialized object.

<Callout color="rose">
Double-checked locking without `volatile` was a known broken pattern before Java 5. The Java Memory Model prior to Java 5 did not guarantee the memory visibility semantics that DCL requires. On Java 5+, `volatile` provides those guarantees. Do not use DCL on pre-5 JVMs; use eager instantiation instead.
</Callout>

## <Label color="teal">5</Label> The Enum Singleton

Java 5 introduced a fourth approach that HFDP endorses as the simplest correct answer when lazy initialization is not required:

```java
public enum Singleton {
    INSTANCE;

    public void doSomething() {
        // ...
    }
}

// Usage
Singleton.INSTANCE.doSomething();
```

Enum values are instantiated exactly once by the JVM, thread-safely, at class load time. Serialization is handled automatically — enum values are serialization-safe by specification, which matters because the standard `Serializable` mechanism for regular classes will create a second instance upon deserialization unless you override `readResolve()`. The enum approach has none of these risks.

The enum Singleton is the right default for modern Java code when:
- Lazy instantiation is not needed.
- The singleton does not need to extend a superclass (enums cannot extend classes).
- Serialization correctness matters.

## <Label color="teal">6</Label> Class Loaders and Serialization Hazards

Two subtler failure modes exist beyond multithreading.

**Multiple class loaders.** In application servers and plugin systems, multiple class loaders may each load the same class independently. Each class loader gets its own version of `uniqueInstance`. Two separate "Singletons" exist — one per class loader. The fix is to specify a class loader explicitly: `Class.forName("Singleton", true, specificClassLoader)`. This is an uncommon problem for most developers but a real one in enterprise Java environments.

**Serialization.** If a Singleton implements `Serializable`, deserializing a previously serialized instance creates a new object — bypassing the private constructor and breaking the one-instance guarantee. The fix for non-enum Singletons is to implement `readResolve()`:

```java
protected Object readResolve() {
    return getInstance();
}
```

This causes the deserialization machinery to return the existing singleton rather than the freshly constructed object. The enum approach makes this unnecessary.

## <Label color="teal">7</Label> Known Criticisms

Singleton is one of the most criticized patterns in the GoF catalog, and the criticisms have merit in context:

**Global state.** A Singleton is a global variable dressed in OO clothing. Code that depends on a Singleton is implicitly coupled to global state. Any module anywhere can modify the singleton's state, and that modification is visible everywhere.

**Testability.** Unit tests that depend on a Singleton cannot easily substitute a test double. The Singleton controls its own instantiation; there is no injection point for a mock. Testing two scenarios that require different singleton states within the same JVM is structurally difficult.

**Single Responsibility Principle violation.** A Singleton manages its own lifecycle (ensuring one instance) *and* performs its domain function (connection pooling, logging, etc.). Two responsibilities in one class.

**Hidden dependencies.** A method that calls `Singleton.getInstance()` internally has a dependency that is invisible at the method signature level. Dependencies hidden this way are harder to find, document, and replace.

These criticisms do not mean the pattern is never appropriate. Thread pools and logging singletons are reasonable. The guidance is to apply the pattern where the one-instance constraint is a genuine domain requirement — not as a lazy substitute for dependency injection or proper module design.

---

**Key takeaways from Chapter 5:**

- Singleton enforces the one-instance constraint structurally: private constructor, static field, static accessor. Global variables do not enforce it.
- The classic lazy implementation is not thread-safe. Two threads can both observe `null` and each create an instance.
- Fix 1: `synchronized getInstance()` is correct but expensive on every call. Fix 2: eager instantiation is correct and fast but not lazy. Fix 3: DCL with `volatile` is correct, lazy, and fast — on Java 5+.
- The enum Singleton is the modern default: thread-safe, serialization-safe, zero boilerplate.
- Multiple class loaders and `Serializable` are two additional correctness hazards beyond multithreading.
- Singleton's criticisms — global state, testability, SRP violation — are real. Apply the pattern where one-instance is a domain constraint, not a convenience.
