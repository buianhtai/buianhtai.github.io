When an object's behavior depends on its current state — and it has several states — the naïve implementation is a nest of conditionals that punishes every future change. State pattern replaces those conditionals with a set of classes, one per state, that each know what to do when called.

## <Label color="teal">1</Label> The Conditional Explosion

A gumball machine has four states: `NO_QUARTER`, `HAS_QUARTER`, `SOLD`, `SOLD_OUT`. The first implementation uses integer constants and branches every action method across every state:

```java
public void insertQuarter() {
    if (state == HAS_QUARTER) {
        System.out.println("You can't insert another quarter");
    } else if (state == SOLD_OUT) {
        System.out.println("You can't insert a quarter, the machine is sold out");
    } else if (state == SOLD) {
        System.out.println("Please wait, we're already giving you a gumball");
    } else if (state == NO_QUARTER) {
        state = HAS_QUARTER;
        System.out.println("You inserted a quarter");
    }
}
```

Multiply four actions (`insertQuarter`, `ejectQuarter`, `turnCrank`, `dispense`) by four states and you have sixteen branches to maintain. Now a new requirement arrives: 1-in-10 chance of winning two gumballs — a fifth state (`WINNER`). Every existing method needs a fifth branch audited. The conditional approach doesn't just resist change — it punishes it.

## <Label color="teal">2</Label> The State Pattern

Extract each state into its own class. Define a `State` interface with one method per action. The context (`GumballMachine`) holds a reference to the current state object and delegates:

```java
public interface State {
    void insertQuarter();
    void ejectQuarter();
    void turnCrank();
    void dispense();
}

public class HasQuarterState implements State {
    private GumballMachine gumballMachine;

    public void insertQuarter() {
        System.out.println("You can't insert another quarter");
    }
    public void ejectQuarter() {
        System.out.println("Quarter returned");
        gumballMachine.setState(gumballMachine.getNoQuarterState());
    }
    public void turnCrank() {
        System.out.println("You turned...");
        Random random = new Random(System.currentTimeMillis());
        int winner = random.nextInt(10);
        if (winner == 0 && gumballMachine.getCount() > 1) {
            gumballMachine.setState(gumballMachine.getWinnerState());
        } else {
            gumballMachine.setState(gumballMachine.getSoldState());
        }
    }
    public void dispense() {
        System.out.println("No gumball dispensed");
    }
}
```

The `GumballMachine` context just delegates every action to the current state:

```java
public void insertQuarter() { state.insertQuarter(); }
public void ejectQuarter()  { state.ejectQuarter(); }
public void turnCrank()     { state.turnCrank(); state.dispense(); }
```

Adding `WinnerState` requires one new class — no edits to any existing state.

## <Label color="teal">4</Label> Formal Definition

> **State Pattern** — allows an object to alter its behavior when its internal state changes. The object will appear to change its class.

The appearance of changing class comes from the runtime dispatch: the same method call on the same object returns completely different behavior when the state field holds a different object.

<Callout color="teal">
State is the right tool when you have an object whose behavior changes predictably based on a lifecycle — orders, traffic lights, vending machines, workflows, document approval chains. If the object doesn't have a natural state lifecycle — it just needs a pluggable algorithm — Strategy fits better.
</Callout>
