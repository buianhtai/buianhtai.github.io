Some objects should only ever exist once — a thread pool, a logging service, a device driver, a configuration store. The Singleton pattern enforces that uniqueness at the class level and provides a single access point. The implementation is deceptively simple; the multithreading correctness is not.

## <Label color="teal">1</Label> The Basic Structure

The private constructor prevents external instantiation. The static `getInstance()` method is the only door in:

```java
public class Singleton {
    private static Singleton instance;

    private Singleton() {}  // no external instantiation

    public static Singleton getInstance() {
        if (instance == null) {             // lazy initialisation
            instance = new Singleton();
        }
        return instance;
    }
}
```

This works perfectly — in a single-threaded world. Two threads entering `getInstance()` simultaneously can each see `instance == null` and each call `new Singleton()`, producing two instances and violating the pattern's entire purpose.

## <Label color="teal">2</Label> Three Solutions for Thread Safety

<FlowStep steps={[
  { title: "Option 1: Synchronized getInstance()", body: "Add `synchronized` to `getInstance()`. Correct, but carries a lock acquisition on every call — even when the instance already exists. Fine if getInstance() is not called in a tight loop; expensive if it is." },
  { title: "Option 2: Eager initialization", body: "Create the instance as a static field initializer: `private static Singleton instance = new Singleton();`. The JVM class loader guarantees this runs exactly once before any thread can call getInstance(). Zero synchronization overhead at call time. Only drawback: the instance is created even if never used." },
  { title: "Option 3: Double-Checked Locking (DCL)", body: "Check once without locking, lock only when instance is null, then check again inside the lock. Requires the `volatile` keyword to prevent the JVM from reordering the assignment before the constructor finishes." },
]} />

```java
// Option 3: DCL with volatile — correct on Java 5+
public class Singleton {
    private volatile static Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                  // Check 1 — no lock
            synchronized (Singleton.class) {
                if (instance == null) {          // Check 2 — inside lock
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

Without `volatile`, the JVM may partially publish the `Singleton` object — a thread can observe `instance != null` while the object's fields are not yet fully initialized. `volatile` inserts a memory barrier, ensuring all writes complete before the assignment becomes visible to other threads.

## <Label color="teal">3</Label> The Enum Singleton (Recommended)

Java enum types are guaranteed by the JVM spec to be instantiated exactly once, thread-safely, without any synchronization code you have to write:

```java
public enum Singleton {
    INSTANCE;

    public void doSomething() {
        // singleton behavior here
    }
}

// Usage
Singleton.INSTANCE.doSomething();
```

This is not a hack. The JVM enforces enum uniqueness even across serialization/deserialization and even under reflection. No private constructor required. No volatile required. Joshua Bloch (Effective Java) named this the best Singleton implementation.

<Callout color="teal">
Singleton is often over-applied. The pattern is appropriate when one-and-only-one instance is a genuine system constraint — a device driver, a connection pool manager, a class loader. If the real requirement is "one instance per application" and you're using DI infrastructure, the container can enforce that without you writing a Singleton at all.
</Callout>

## <Label color="teal">5</Label> Multiple Class Loaders

In some Java environments (application servers, OSGi containers), the same class may be loaded by multiple class loaders, producing one `Singleton` instance per class loader. Each loader's `instance` is a separate static variable.

The fix: specify which class loader should load the Singleton class, or use a registry pattern where classes are looked up by name from a central location. This is rare in modern development but relevant in plugin-based architectures.
