The core problem in Chapter 6 is a home automation remote with seven slots, each mapped to a device from an assorted vendor library — `Light`, `CeilingFan`, `GarageDoor`, `Stereo`, `Hottub`. Every vendor exposes a different API surface. The remote should never know any of it. The Command Pattern solves this by inserting an object between the button press and the device: the invoker calls one universal method, the command object holds the vendor-specific knowledge.

## <Label color="teal">1</Label> The Problem: A Remote That Cannot Know Its Devices

The vendor classes on the CD-R have wildly inconsistent APIs. `Light` has `on()` and `off()`. `CeilingFan` has `high()`, `medium()`, `low()`, `off()`, `getSpeed()`. `GarageDoor` has `up()`, `down()`, `stop()`, `lightOn()`, `lightOff()`. `Stereo` has `on()`, `off()`, `setCd()`, `setVolume()`. If the remote's button handler dispatches directly to these classes, it becomes a chain of `if/else` checks that must be rewritten every time a new vendor device appears.

The requirement adds a further constraint: a global Undo button must reverse the last action. An `if/else` dispatcher has no clean way to remember what it just did, let alone reverse it.

The right decomposition separates three concerns entirely:

- **Who makes the request** (the remote, an operator pressing a button)
- **How the request is executed** (the vendor-specific device API)
- **What request to make** (the mapping, wired up at configuration time)

The Command Pattern gives each of those concerns its own home.

## <Label color="teal">2</Label> The Four Roles

<FlowStep steps={[
  { title: "Command interface", body: "Declares execute() and undo(). Every concrete command implements this contract. The invoker sees nothing else." },
  { title: "ConcreteCommand", body: "LightOnCommand holds a reference to a Light receiver. execute() calls light.on(). undo() calls light.off(). All vendor knowledge is encapsulated here." },
  { title: "Invoker", body: "SimpleRemoteControl (or the full 7-slot RemoteControl). Stores a Command in each slot. On button press, calls slot.execute(). On Undo, calls lastCommand.undo(). Never imports a vendor class." },
  { title: "Client", body: "Wires everything together: creates a LightOnCommand with a Light instance, loads it into slot 0. Only the client touches both sides of the wall." },

The invoker is intentionally kept ignorant. The client is the only code that bridges Invoker and Receiver — and that bridging happens once at configuration time, not at button-press time.

```java
// Client wiring
Light livingRoomLight = new Light("Living Room");
Command lightOn  = new LightOnCommand(livingRoomLight);
Command lightOff = new LightOffCommand(livingRoomLight);
remote.setCommand(0, lightOn, lightOff);

// Invoker usage — no vendor class in scope
remote.onButtonWasPushed(0);   // → light.on()
remote.offButtonWasPushed(0);  // → light.off()
remote.undoButtonWasPushed();  // → light.on()  (undo the off)
```

## <Label color="teal">4</Label> Undo: State Inside the Command

Undo is not a separate mechanism — it is a natural consequence of commands holding state. The `CeilingFanHighCommand` needs to remember the fan's speed *before* it executes, so it can restore it on undo.

```java
public class CeilingFanHighCommand implements Command {
    CeilingFan fan;
    int prevSpeed;   // state captured at execute() time

    public void execute() {
        prevSpeed = fan.getSpeed();   // remember
        fan.high();
    }

    public void undo() {
        switch (prevSpeed) {
            case CeilingFan.HIGH:   fan.high();   break;
            case CeilingFan.MEDIUM: fan.medium(); break;
            case CeilingFan.LOW:    fan.low();    break;
            case CeilingFan.OFF:    fan.off();    break;
        }
    }
}
```

The `RemoteControl` keeps a single `lastCommand` field. `undoButtonWasPushed()` calls `lastCommand.undo()`. For multi-level undo, replace the field with a stack of commands — the invoker stays the same.

<Callout color="teal">
Undo correctness depends on capturing state *before* mutation. Execute always saves first, then acts. Any command that mutates multiple fields must capture all of them, or undo leaves the receiver in a partial state.
</Callout>

## <Label color="teal">5</Label> Macro Commands and NoCommand

**Macro commands** group several commands into one button. The `MacroCommand` simply holds an array and iterates:

```java
public class MacroCommand implements Command {
    Command[] commands;

    public void execute() {
        for (Command c : commands) c.execute();
    }

    public void undo() {
        // Undo in reverse order
        for (int i = commands.length - 1; i >= 0; i--) {
            commands[i].undo();
        }
    }
}
```

A "Movie Night" macro could: dim lights → lower screen → turn on projector → set surround sound → start popcorn popper — five receiver calls, one button.

**NoCommand** is an instance of the Null Object pattern. Instead of initializing slots to `null` and checking before each call, every slot starts with a `NoCommand` whose `execute()` and `undo()` do nothing. The invoker's button handlers become unconditional — no null guards, no branches.

```java
public class NoCommand implements Command {
    public void execute() {}
    public void undo()    {}
}
```

## <Label color="teal">6</Label> Beyond the Remote: Real-World Applications

The Command Pattern appears far outside GUI remotes precisely because "encapsulate a request as an object" is a universally useful abstraction:

**Job queues and thread pools.** A `Runnable` in Java is a Command. Thread pools store a queue of `Runnable` objects and drain them onto worker threads. The thread pool (invoker) is completely decoupled from the work being done (receiver). You can add, reprioritize, cancel, or delay jobs without modifying workers.

**Transactional systems.** Database undo logs are sequences of Commands. Each write operation records enough information in the log to be reversed. Crash recovery replays or rolls back the log in order.

**Audit logging.** Because commands are objects, they can be serialized to disk as they execute. After a crash, the log can be replayed to reconstruct final state — or replayed selectively to debug what happened.

**GUI undo/redo stacks.** Every edit in a word processor or IDE is a command object pushed onto an undo stack. Ctrl+Z pops and calls `undo()`. Ctrl+Y calls `execute()` again (or pushes to a redo stack).

<Callout color="amber">
The diner analogy from the book maps cleanly: the Customer (client) creates an Order (command) for the Waitress (invoker) who calls `orderUp()` (execute) for the Short-Order Cook (receiver). The Waitress never needs to know how to cook — she just passes slips. This is precisely why the pattern is so useful: the invoker and receiver never speak directly.
</Callout>

## What the Pattern Gives You

- **Invoker stability.** The remote control code never changes as new vendor devices appear. New devices require new ConcreteCommand classes and client wiring — nothing else.
- **Undo is not an afterthought.** The architecture makes undo the natural state of affairs: every command knows how to reverse itself.
- **Testability.** A `LightOnCommand` can be tested with a mock `Light` receiver, entirely independently of any invoker or remote. Commands are pure units.
- **Composability.** `MacroCommand` demonstrates that commands can contain commands. The invoker does not change. Any level of nesting is possible.
- **Schedulability.** Once a request is an object, you can put it in a queue, delay it, log it, transmit it over a network, or replay it from disk. None of these capabilities require changes to the invoker or receiver.
