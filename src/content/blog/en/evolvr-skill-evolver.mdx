Once a lesson passes the confidence gate, it sits in the journal. The question is how it gets back to the agent that will benefit from it. In v0.1, the answer is the MCP server: the agent calls `evolvr_get_lessons` before starting work and receives the top relevant lessons as structured text. Simple, deterministic, no LLM required. The more ambitious self-modification pipeline — where evolvr autonomously writes patches to AGENTS.md, A/B tests them, and commits the results — is the v0.3 roadmap, described at the end of this post.

## <Label color="teal">1</Label> The MCP Server — Four Tools

<Card>

`@evolvr/mcp` is a lightweight MCP server built on `@modelcontextprotocol/sdk`. It exposes four tools that together form the read/write interface between agents and the evolvr journal.

```typescript
// The four MCP tool names
const TOOLS = [
  'evolvr_record_tool_call',  // write: log a tool invocation
  'evolvr_session_end',       // write: finalize session, run classifier
  'evolvr_get_lessons',       // read: get lessons for system prompt injection
  'evolvr_get_status',        // read: journal stats
] as const;
```

Agents that support MCP (Claude Code, Cursor, Windsurf, and others) can use all four tools. For agents that don't support MCP natively — or when you want lower-latency hook-based recording — the CLI `evolvr hook` command provides the same write path without MCP overhead.

</Card>

## <Label color="green">2</Label> evolvr_get_lessons — The Injection Tool

<Card>

`evolvr_get_lessons` is the tool the agent calls when it wants to know what evolvr has learned. The agent passes its current task description, and evolvr returns the top matching lessons.

**Input schema:**

```typescript
{
  text: string;       // task description or first message — used for keyword matching
  agent?: string;     // filter by agent type ('claude', 'opencode', 'codex', ...)
  limit?: number;     // default 5, max 20
}
```

**Output:**

```
[evolvr] Learned behaviors relevant to this task (3 lessons):

1. [exact_repeat_loop] confidence: 1.0 | evidence: 5 runs
   Trigger: Reading files in src/generated/ during refactoring tasks
   Recommendation: Files in src/generated/ are auto-generated and do not change
   during a session. Read each file at most once. Re-reading is never productive.

2. [same_result_cycling] confidence: 0.82 | evidence: 4 runs
   Trigger: Searching for a symbol with pattern variations that all return empty
   Recommendation: After 3 searches with different patterns return empty results,
   stop and ask the user to confirm the symbol name.

3. [read_only_streak] confidence: 0.8 | evidence: 3 runs
   Trigger: Long read streaks during database migration tasks
   Recommendation: Before writing any migration file, run the migration listing
   command first. Blind migrations cause version conflicts.
```

The output is plain text formatted for direct injection into a system prompt. The agent reads it as part of its working context for the session.

</Card>

<Callout color="teal">
The keyword matching in v0.1 is simple: lessons are filtered by agent scope and ranked by evidence count × confidence. Semantic similarity search (embedding-based retrieval) is planned for v0.2 when the stage 2 classifier is enabled.
</Callout>

## <Label color="amber">3</Label> The Other Three Tools

<Card>

**`evolvr_record_tool_call`** — The write path for agents that prefer MCP over CLI hooks. Accepts tool name, args hash, result hash, result summary, latency, and sequence number. Returns the updated task record.

```typescript
// MCP call
{
  "tool": "evolvr_record_tool_call",
  "arguments": {
    "task_id": "01HWXY...",
    "seq": 7,
    "tool_name": "read_file",
    "args_hash": "a3f9c2b1",
    "result_hash": "d8e4f7a2",
    "result_summary": "// auto-generated by build script\nexport const routes = ...",
    "latency_ms": 45
  }
}
```

**`evolvr_session_end`** — Finalizes the task record and triggers the failure classifier. Should be called when the agent's session completes (success or failure). Returns the classification result and any new lessons created.

```typescript
{
  "tool": "evolvr_session_end",
  "arguments": {
    "task_id": "01HWXY...",
    "outcome": "failed",           // "success" | "partial" | "failed"
    "outcome_detail": "read_only_streak detected: 14 consecutive reads"
  }
}
```

**`evolvr_get_status`** — Returns journal statistics: total tasks, failure rate by class, lesson count, pending review count. Useful for agents that want to surface evolvr health in status reports.

</Card>

## <Label color="rose">4</Label> Connecting Claude Code

<Card>

For Claude Code, the recommended integration uses CLI hooks (not the MCP record tools) for the write path, combined with the MCP server for the read path. This gives lower latency on writes (the hook command is a fast CLI invocation) while keeping lesson retrieval in-band as an MCP tool call.

**MCP config (`~/.claude/mcp.json`):**

```json
{
  "mcpServers": {
    "evolvr": {
      "command": "evolvr-mcp",
      "args": ["--project-root", "/path/to/your/project"]
    }
  }
}
```

**Hook config (`~/.claude/settings.json`):**

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "*",
      "hooks": [{
        "type": "command",
        "command": "evolvr hook --event pre-tool --task $CLAUDE_SESSION_ID --tool $TOOL_NAME"
      }]
    }],
    "PostToolUse": [{
      "matcher": "*",
      "hooks": [{
        "type": "command",
        "command": "evolvr hook --event post-tool --task $CLAUDE_SESSION_ID --tool $TOOL_NAME --args-hash $ARGS_HASH --result-hash $RESULT_HASH --latency $LATENCY_MS"
      }]
    }],
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "evolvr hook --event stop --task $CLAUDE_SESSION_ID --outcome success"
      }]
    }]
  }
}
```

With both configs in place, Claude Code calls `evolvr_get_lessons` at the start of each session and every tool call is recorded to the journal without any manual intervention.

</Card>

## <Label color="sky">6</Label> The v0.3 Roadmap — AGENTS.md Auto-Promotion

<Card>

The v0.1 MCP delivery model is intentionally conservative: lessons inform the agent at the start of a session but do not modify any files. The more powerful capability — autonomously writing lessons back into AGENTS.md — is planned for v0.3, with three safeguards:

**Evidence threshold** — A lesson must accumulate 3 or more separate Task records before a patch is drafted. One bad run triggers nothing.

**Review gate** — A human operator sees the diff before it is applied (unless `auto_evolve: true` is configured).

**A/B shadow test** — The patched AGENTS.md runs alongside the un-patched version for 10 similar tasks. The outcome delta determines whether the patch is promoted or reverted.

The patch format will be a clearly marked section in AGENTS.md:

```markdown
## evolvr — learned behaviors

### [exact_repeat_loop] Reading from src/generated/ directories

> Applies to: claude  
> Evidence: 5 instances  
> Last seen: 2026-05-02

Files in src/generated/ are auto-generated at build time and do not change
during a session. Read each generated file at most once. If you need its
content again, it is still in your context — do not re-read.
```

The section is evolvr-managed and clearly separated from human-written AGENTS.md content. Human-written content above the marker is never touched.

</Card>
