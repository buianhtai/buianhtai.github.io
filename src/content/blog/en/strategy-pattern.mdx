## <Label color="teal">1</Label> The Inheritance Trap

Consider a `Duck` base class with `quack()` and `display()`. You add `fly()` to the base class to make ducks fly. Now `RubberDuck` (which shouldn't fly) overrides `fly()` to do nothing. Then `DecoyDuck` needs to not fly *and* not quack. Two more overrides. Every new variant requires auditing every method in every subclass.

The problem is not "you forgot to override." The problem is that the base class is making a promise — *I fly, I quack* — that some subclasses cannot honestly keep.

Using interfaces (`Flyable`, `Quackable`) seems to help, but now every flying duck duplicates the same `fly()` body. You've traded a fragile inheritance hierarchy for fragile copy-paste.

The real diagnosis: flying and quacking are *behaviors that vary*. Inheritance bakes them into the type. The fix is to pull them out entirely.

These three principles work together: P1 identifies *what* to extract (`FlyBehavior` and `QuackBehavior`). P2 says to reference them as interfaces so the concrete implementation can swap at runtime. P3 says to put them in `Duck` as fields, not in a class hierarchy.

## <Label color="teal">3</Label> The Strategy Pattern Applied

```java
public abstract class Duck {
    FlyBehavior  flyBehavior;
    QuackBehavior quackBehavior;

    public void performFly()   { flyBehavior.fly(); }
    public void performQuack() { quackBehavior.quack(); }

    // Change behavior at runtime — impossible with inheritance
    public void setFlyBehavior(FlyBehavior fb)    { flyBehavior = fb; }
    public void setQuackBehavior(QuackBehavior qb) { quackBehavior = qb; }
}
```

`MallardDuck` is initialised with `FlyWithWings` and `Quack`. `RubberDuck` gets `FlyNoWay` and `Squeak`. A duck that starts grounded can be upgraded mid-simulation:

```java
Duck model = new ModelDuck();          // FlyNoWay by default
model.setFlyBehavior(new FlyRocketPowered()); // runtime swap
model.performFly();                    // → I'm flying with a rocket!
```

No subclass touched. No override written. The behavior swapped at the call site.

## <Label color="teal">4</Label> The Formal Definition

> **Strategy Pattern** — defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from clients that use it.

The pattern is not just about flexibility — it makes the code *testable*. Each strategy is a standalone unit. You can test `FlyWithWings` without touching a single duck.

## <Label color="teal">6</Label> What Makes Strategy Different from Simple Polymorphism

- **Behavior is a first-class object.** It can be stored, passed, returned, and swapped. Polymorphism via subclass cannot do that cleanly.
- **The context and the algorithm are separately evolvable.** Adding a new duck variant does not touch the fly hierarchy. Adding a new fly style does not touch the duck hierarchy.
- **Runtime reconfiguration.** An inheritance override is baked in at construction time. A Strategy setter fires at any point in the object lifecycle.
- **Test isolation.** Each concrete Strategy is a pure unit — just instantiate it and call the method.
- **Composition chains.** Strategies can wrap other strategies (a preview of Decorator and Chain of Responsibility).
