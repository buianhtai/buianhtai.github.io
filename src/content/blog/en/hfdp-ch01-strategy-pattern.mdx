## <Label color="teal">1</Label> The Inheritance Trap — SimUDuck

The duck simulator starts simply: a `Duck` base class with `quack()` and `display()`, a handful of subclasses (`MallardDuck`, `RedheadDuck`, etc.). Everything is clean until the product team asks for flying ducks. The obvious move is to add `fly()` to the base class.

The obvious move is wrong.

Adding `fly()` to `Duck` gives *all* subclasses a flying behavior — including `RubberDuck`, which now honks *and* flies. You `@Override` `fly()` in `RubberDuck` to do nothing. Then `DecoyDuck` needs to not fly *and* not quack. Another two overrides. A wooden `DecoyDuck3D` arrives. Then a `NuclearMissileDuck` that flies but shouldn't quack. Every new variant requires auditing every method in every subclass.

The problem is not "you forgot to override." The problem is that the base class is making a promise — *I fly, I quack* — that some subclasses cannot honestly keep.

<Callout color="amber">
Interfaces seem to help: define `Flyable` and `Quackable`, implement only what applies. But now every flying duck duplicates the same `fly()` body. You've traded a fragile inheritance hierarchy for fragile copy-paste. Change how flying works and you hunt down 48 identical methods.
</Callout>

The real diagnosis: flying and quacking are *behaviors that vary*. Inheritance bakes them into the type. The fix is to pull them out entirely.

These read like slogans until you see them applied together. Principle 1 identifies *what* to extract: `FlyBehavior` and `QuackBehavior`. Principle 2 says to reference them as interfaces so the concrete implementation can swap at runtime. Principle 3 says to put them in `Duck` as fields, not in a class hierarchy.

The `Duck` base class holds two fields — `FlyBehavior flyBehavior` and `QuackBehavior quackBehavior` — and delegates:

```java
public abstract class Duck {
    FlyBehavior  flyBehavior;
    QuackBehavior quackBehavior;

    public void performFly()   { flyBehavior.fly(); }
    public void performQuack() { quackBehavior.quack(); }

    // Change behavior at runtime — impossible with inheritance
    public void setFlyBehavior(FlyBehavior fb)    { flyBehavior = fb; }
    public void setQuackBehavior(QuackBehavior qb) { quackBehavior = qb; }
}
```

`MallardDuck` is initialised with `FlyWithWings` and `Quack`. `RubberDuck` gets `FlyNoWay` and `Squeak`. A `ModelDuck` that starts grounded can be upgraded mid-simulation:

```java
Duck model = new ModelDuck();          // FlyNoWay by default
model.setFlyBehavior(new FlyRocketPowered()); // runtime swap
model.performFly();                    // → I'm flying with a rocket!
```

No subclass touched. No override written. The behavior swapped at the call site.

## <Label color="teal">4</Label> The Formal Definition

> **Strategy Pattern** — defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from clients that use it.

The three moving pieces:

The pattern is not just about flexibility — it makes the code *testable*. Each strategy is a standalone unit. You can test `FlyWithWings` without touching a single duck.

## <Label color="teal">6</Label> OO Toolbox After Chapter 1

The book ends every chapter with an "OO Toolbox" summary. After Chapter 1 it reads:

- **OO Basics:** Abstraction, Encapsulation, Polymorphism, Inheritance
- **OO Principles:** Encapsulate what varies · Favor composition over inheritance · Program to interfaces, not implementations
- **OO Patterns:** *Strategy* — defines a family of algorithms, encapsulates each one, makes them interchangeable

That stacking — basics → principles → patterns — is the book's running thesis: patterns are not templates to memorize, they are *principles made concrete*. Understanding why SimUDuck breaks with inheritance, and precisely which principle is violated, is more durable knowledge than knowing the UML diagram.

## What Makes Strategy Different from Simple Polymorphism

- **Behavior is a first-class object.** It can be stored, passed, returned, and swapped. Polymorphism via subclass cannot do that cleanly.
- **The context and the algorithm are separately evolvable.** Adding a new duck variant does not touch the fly hierarchy. Adding a new fly style does not touch the duck hierarchy. The two axes of change are genuinely independent.
- **Runtime reconfiguration.** An inheritance override is baked in at construction time. A Strategy setter fires at any point in the object lifecycle.
- **Test isolation.** Each concrete Strategy is a pure unit. No test scaffolding needed to exercise `FlyRocketPowered` — just instantiate it and call `fly()`.
- **Composition chains.** Strategies can wrap other strategies (a preview of Decorator and Chain of Responsibility). Inheritance depth cannot.

The pattern is deceptively simple — two interfaces, a couple of fields — but it encodes a design philosophy that scales to every other pattern in the catalog. Every time the Gang of Four says "encapsulate what varies," this is what they mean.
