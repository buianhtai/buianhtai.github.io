Chapter 8 catalogued everything that can go wrong. Chapter 9 asks: given all those failure modes, what can we actually guarantee, and how? The central topic is **consensus** — getting all nodes to agree on a single value despite node crashes and network failures. Consensus sounds like one problem but it turns out to underlie leader election, atomic commit, total order broadcast, and distributed locking. Solve consensus, and many other problems become tractable.

## <Label color="teal">1</Label> The Consistency Guarantee Spectrum

Distributed databases don't offer a binary choice between "consistent" and "inconsistent." They offer a spectrum of models, trading safety guarantees for performance and availability.

**Eventual consistency** is the weakest practical guarantee: if writes stop, all replicas will eventually converge to the same value. It says nothing about *when* they converge. A read issued immediately after a write to a different replica may return a stale value. For many applications (social media timelines, shopping cart recommendations) this is acceptable.

**Linearizability** is one of the strongest. The goal: make a distributed system appear as if there is a single copy of the data, and all operations on it are atomic. If one client writes a value and receives a successful response, all subsequent reads from any node must return that value (or a later one).

## <Label color="teal">2</Label> Linearizability

Linearizability is a **recency guarantee** on individual objects (registers). In a linearizable system, once a write completes, all reads — from any replica, by any client — must see that value or a later one. There is no going back.

The canonical example: Alice tells Bob that the World Cup result has been announced. Bob hits reload on his phone. His request goes to a lagging replica that still shows "game in progress." This is a linearizability violation: Bob started his read *after* Alice successfully read the new value, so Bob's read must also return the new value.

**How it differs from serializability:**
- **Serializability** (Ch07) is about transactions operating on multiple objects — transactions may be reordered as long as the result is consistent with some serial execution
- **Linearizability** is about single-object recency — every read must reflect the most recent write

A database can be serializable but not linearizable (e.g., snapshot isolation with no recency guarantee). It can be linearizable but not serializable (single-register atomic operations, no multi-object transactions). Many databases (like Google Spanner) provide both — **strict serializability**.

**The cost of linearizability**: any system that provides linearizability must coordinate every read and write through a single leader or a consensus protocol. This coordination introduces latency proportional to network RTT and becomes unavailable when the network partitions (by the CAP theorem). Single-leader replication with synchronous reads from the leader is linearizable, but the leader becomes a bottleneck.

## <Label color="teal">3</Label> CAP Theorem (and Why It's Usually Misunderstood)

The CAP theorem says: a distributed system can provide at most two of:
- **C**onsistency (linearizability)
- **A**vailability (every request gets a response)
- **P**artition tolerance (system continues operating when network partitions occur)

Since network partitions are a reality (not optional), the meaningful choice is between consistency and availability *during a partition*. Most databases choose to sacrifice one or the other when a partition occurs.

<Callout color="amber">
CAP is a trilemma about behavior during a network partition, not a general system design tradeoff. "AP vs CP" is a shorthand that hides enormous complexity. The real question is: what does your system do when nodes cannot communicate?
</Callout>

In practice, most applications don't need full linearizability and can accept causal consistency — a weaker but still useful guarantee that preserves cause-effect ordering without the coordination cost of linearizability.

## <Label color="teal">4</Label> Causal Consistency and Ordering

**Causality** captures the "happened before" relationship. If operation A causally precedes B (A's result influences B), then any observer who sees B must also see A.

Causal consistency is weaker than linearizability (it doesn't require a total ordering of *all* operations, only causally related ones) but stronger than eventual consistency (it does require that causally related operations are seen in order).

**Capturing causality**:
- **Single-leader replication** automatically provides causal consistency: the replication log defines a total order that is consistent with causality
- **Lamport timestamps**: each node/client keeps a counter; every operation's timestamp is the max counter seen so far + 1. Operations from the same causal chain have increasing counters. Compact (a single integer) but can only provide total ordering after the fact — they cannot determine in real-time whether another operation has a causally-later value

**Total order broadcast** extends causal ordering to a full sequence: every message is delivered to every node, exactly once, in the same order. This is equivalent to consensus (decide on each message in the sequence). Single-leader replication implements total order broadcast — the leader's write log is the total order.

## <Label color="teal">5</Label> Two-Phase Commit (2PC) and Its Limitations

Two-phase commit is the classic algorithm for atomically committing a transaction across multiple nodes (distributed transactions). It uses a **coordinator** (transaction manager) and **participants** (database nodes).

**The fatal flaw of 2PC**: once a participant votes "yes," it cannot unilaterally abort — it must wait for the coordinator's decision. If the coordinator crashes after collecting votes but before sending the decision, participants are **in doubt** — they hold locks and cannot commit or abort. The system is blocked until the coordinator recovers. This is why 2PC is said to be a **blocking protocol**.

**Three-phase commit (3PC)** was proposed to avoid blocking, but it only works in synchronous networks (bounded delays) — in practice, it doesn't solve the problem in real distributed systems with network partitions.

**Why termination is hard**: FLP impossibility theorem (Fischer, Lynch, Paterson, 1985) proves that no deterministic consensus algorithm can guarantee both termination and the safety properties in an asynchronous system where a single node can crash. In practice, systems use timeouts (partial synchrony assumption) to achieve termination — consensus succeeds when the network is behaving well, and may stall during severe partitions or cascading failures.

## <Label color="teal">7</Label> Practical Consensus: Raft, Paxos, Zab

Real consensus algorithms don't directly implement the single-value consensus formalization. They implement **total order broadcast** — agreeing on a sequence of values (each round of consensus decides one message in the log). This is what Raft, Paxos, and Zab do.

**The key insight in all fault-tolerant consensus algorithms**: there cannot be two leaders simultaneously making conflicting decisions. But rather than guaranteeing uniqueness of leaders, these algorithms guarantee:
- Leaders have **epoch numbers** (term numbers in Raft, ballot numbers in Paxos)
- Higher epoch always wins
- Before a leader can make a decision, it must collect a **quorum vote** (majority of nodes) for that epoch
- This ensures: if a previous leader is still alive but partitioned, the new leader has a higher epoch — the old leader cannot commit anything that conflicts

**Total order broadcast ↔ consensus equivalence:**
- Total order broadcast requires: deliver each message exactly once, to all nodes, in the same order
- This is equivalent to repeated consensus rounds: each round decides which message is next in the sequence
- Raft/Zab implement total order broadcast directly (as replicated logs); single-leader replication is total order broadcast with human-in-the-loop leader election (not fault-tolerant consensus)

## <Label color="teal">8</Label> ZooKeeper and Coordination Services

ZooKeeper implements fault-tolerant total order broadcast (via Zab). Applications use ZooKeeper for:
- **Leader election**: the node that creates a ZooKeeper ephemeral node "wins"; ZooKeeper's linearizability ensures only one node can create it
- **Distributed locking**: acquire lock by creating ephemeral ZooKeeper node; lock released when node session expires
- **Service discovery**: nodes register their availability; clients watch for changes
- **Configuration distribution**: distribute config to all nodes with change notification

ZooKeeper provides the consensus primitive so application developers don't have to implement Raft themselves — which is notoriously hard to get right.
