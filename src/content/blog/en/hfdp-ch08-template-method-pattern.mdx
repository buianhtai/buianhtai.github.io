Chapter 8 opens with a problem that looks trivial — two similar recipes for coffee and tea — and uses it to expose a class of code duplication that cannot be fixed by ordinary refactoring. Extracting shared logic into a base class is the easy part. The harder part is locking the algorithm's *structure* so that subclasses can fill in steps without reorganizing the whole recipe. The Template Method Pattern is the mechanism that does this.

## <Label color="teal">1</Label> The Duplication Problem: Coffee and Tea

Here are the two recipes side by side:

| Step | Coffee | Tea |
|------|--------|-----|
| 1 | Boil water | Boil water |
| 2 | Brew coffee grinds | Steep tea bag |
| 3 | Pour into cup | Pour into cup |
| 4 | Add sugar and milk | Add lemon |

Steps 1 and 3 are identical. Steps 2 and 4 vary by beverage. The naive implementation gives each class its own `prepareRecipe()`, duplicating the boil and pour steps completely. Moving `boilWater()` and `pourInCup()` to a base class stops that duplication — but `prepareRecipe()` itself remains duplicated, because each subclass still overrides it with a different sequence.

The insight: steps 2 and 4 are not fundamentally different operations — they are *instantiations of the same abstract operations* (extract flavor from something, add something to customize). Rename them `brew()` and `addCondiments()`. Now the algorithm's structure can live in the base class.

```java
public abstract class CaffeineBeverage {

    // The template method — final so subclasses cannot reorder steps
    final void prepareRecipe() {
        boilWater();
        brew();
        pourInCup();
        addCondiments();
    }

    abstract void brew();           // subclass MUST implement
    abstract void addCondiments();  // subclass MUST implement

    void boilWater() {
        System.out.println("Boiling water");
    }

    void pourInCup() {
        System.out.println("Pouring into cup");
    }
}
```

`Coffee` implements `brew()` as "drip through filter" and `addCondiments()` as "add sugar and milk." `Tea` implements them as "steep tea bag" and "add lemon." Neither subclass touches `prepareRecipe()`. Neither can.

## <Label color="teal">2</Label> The Algorithm Skeleton: What Lives Where

The three method categories do different work:

- **Concrete steps** (boilWater, pourInCup): implemented once in the base class, used by all subclasses without any override. These represent the truly invariant parts of the algorithm.
- **Abstract steps** (brew, addCondiments): declared in the base class with no body. Subclasses are *required* by the compiler to provide an implementation. These represent the parts that genuinely differ between variants.
- **Hooks** (customerWantsCondiments): provide a default behavior (here: `return true`) that subclasses can optionally override. The template method calls the hook, and the subclass decides whether to intervene.

```java
// Hook in base class
boolean customerWantsCondiments() {
    return true;  // default: always add
}

// Template method uses it
final void prepareRecipe() {
    boilWater();
    brew();
    pourInCup();
    if (customerWantsCondiments()) {   // hook controls whether this step runs
        addCondiments();
    }
}

// Tea subclass optionally overrides
public class TeaWithHook extends CaffeineBeverage {
    public boolean customerWantsCondiments() {
        String answer = getUserInput();
        return answer.toLowerCase().startsWith("y");
    }
    // ... brew() and addCondiments() as before
}
```

The distinction between abstract and hook is a design decision: use abstract when every subclass *must* provide a meaningful implementation; use hook when the default behavior is sensible and subclasses override it only for specific cases.

<Callout color="teal">
The template method must be declared `final`. Without `final`, a subclass can override `prepareRecipe()` and bypass all the structure you just designed. The `final` modifier is not a restriction on the subclass — it is the guarantee that the pattern's invariant (the algorithm structure) holds.
</Callout>

## <Label color="teal">3</Label> Hollywood Principle: Inversion of Control

The Template Method Pattern exemplifies a design principle the book names the **Hollywood Principle**: *Don't call us, we'll call you.*

Without it, low-level components (the subclasses) control their own behavior — each subclass decides when to boil water, when to pour, when to add condiments. The high-level component (the base class) is passive. Extend it wrong and the algorithm structure drifts.

With Template Method, the base class (`CaffeineBeverage`) is the active party. It *calls* the subclass methods at the right moments. The subclass never calls the template method — it just supplies implementations of the steps it owns.

This inversion is pervasive in frameworks. `HttpServlet` from the Java EE specification is the canonical real-world example: the framework calls `doGet()` or `doPost()` on your servlet at the right moment in the request lifecycle. You do not override `service()` (the template method) — you override the specific hooks the framework provides. The framework's algorithm structure (parse request → dispatch to verb method → write response) is locked. Your code fills in only what varies.

Other instances in the Java standard library:
- `Arrays.sort()` uses `compareTo()` as a hook — the sorting algorithm is fixed, the comparison criterion varies
- `AbstractList` in Java Collections implements `iterator()` using abstract `get()` and `size()` — concrete list types fill in those two
- JUnit's `setUp()` and `tearDown()` are hooks called by the framework's test runner at fixed points in the lifecycle

## <Label color="teal">4</Label> Template Method vs Strategy vs Factory Method

All three patterns encapsulate variation. The differences are structural:

    { "Dimension": "Typical use", "Template Method": "Framework lifecycle hooks, algorithm families with shared structure", "Strategy": "Sorting comparators, payment processors, validation rules", "Factory Method": "Document creation, connection pooling, parser factories" },

/>

The key practical difference between Template Method and Strategy: if the algorithm's *structure* is fixed and you only need to vary *parts*, use Template Method (inheritance). If you need to swap the *entire algorithm* at runtime or want to avoid inheritance entirely, use Strategy (composition). Strategy's composition approach also makes the algorithm testable in isolation — you can exercise a sort comparator without constructing any surrounding class.

<Callout color="amber">
Template Method favors code reuse through inheritance, but it also introduces tight coupling between base class and subclass. If the base class evolves — say, adding a fifth step to the recipe — every subclass must be audited. Strategy avoids this coupling at the cost of more objects. Neither is universally better; the choice depends on how stable the algorithm structure is.
</Callout>

## <Label color="teal">5</Label> When to Use Template Method

Template Method fits when:

- Multiple classes share the *same algorithm structure* but differ in one or more steps — the duplication is in the skeleton, not just individual methods
- You want a framework or library to define a lifecycle that users customize at specific extension points without breaking the overall flow
- The variable steps are genuinely specific to the subclass and do not need to be swapped at runtime
- You want the compiler to enforce that certain steps are implemented (abstract methods) while leaving others optional (hooks)

Avoid it when:
- The algorithm structure itself varies between users — use Strategy
- The number of steps varies significantly between variants — the forced override of all abstract methods becomes a burden
- You need to compose multiple variations — inheritance depth makes that rigid

## What the Pattern Gives You

- **Single source of truth for the algorithm.** Change `prepareRecipe()` in one place and all beverages pick up the change. With independent subclass implementations, the same change requires editing N classes.
- **Compiler-enforced extension contracts.** Abstract method declarations in the base class mean a subclass that forgets `brew()` will not compile. No runtime surprises from missing implementations.
- **Controlled extensibility.** Hooks give subclasses opt-in customization without requiring them to override everything. The base class provides a sensible default; subclasses touch only what they need.
- **Framework inversion.** The Hollywood Principle makes it natural to build frameworks: the framework owns the lifecycle, the user fills in the extension points. This is how most web and test frameworks work under the hood.
