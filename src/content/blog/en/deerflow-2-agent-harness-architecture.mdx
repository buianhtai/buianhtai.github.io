**How do you actually build an AI agent?** Not a prompt that calls a search tool once, but an agent that plans a multi-hour task, explores a codebase, delegates independent subtasks, executes commands safely, remembers useful facts, and streams its work to a browser.

I read the [DeerFlow](https://github.com/bytedance/deer-flow) source to answer that question. The useful discovery is that **the model is only one part of the system**. Almost everything that makes an agent usable in practice is engineering around the model: controlled tools, state, execution environments, middleware, persistence, streaming, identity, and recovery.

This article examines **DeerFlow 2.0**, not the older 1.x Deep Research implementation. Version 2 is a ground-up rewrite. I reviewed repository `main` at [commit `1f15e0b`](https://github.com/bytedance/deer-flow/tree/1f15e0b43ca58b9601514f9f5c408fb032022833) on **October 12, 2026**. Architecture and class names can change after that commit. The pseudocode below explains the execution model; it is **not a verbatim copy** of the implementation.

<Callout color="teal">
  **Mental model:** DeerFlow is a *harness for agents*, not a magical model and not simply a predefined LangGraph flow. It assembles a language model, tools, instructions, state schema, and middleware into a runnable agent, then surrounds it with a Gateway, sandbox, persistence, and UI.
</Callout>

## <Label color="green">02</Label> What happens after a user sends a message?

Take a concrete request:

> “Investigate why this web service became slow, inspect the recent changes, and write a short report.”

That instruction is **not** hardcoded to run search, then shell, then a summary. Instead, the agent sees a set of available tool schemas, chooses the next action, receives its result, and repeats until it can answer or hits a limit.

<DeerFlowExecutionTrace />

**How to read the order:** steps **01–04** establish the request and agent execution context. Step **05** is the model decision point; steps **06–07** run only when the model selects a tool and can loop back to **05** multiple times. Step **08** illustrates the user-facing event stream, which begins **during** execution and ends with a terminal status—so the numbering is a guided walkthrough, *not* a claim that streaming waits for all tools to finish. The result depends on the model's next action, authorization, tool outcomes, and stopping limits.

The important answer to **“What triggers an agent?”** is: an external entry point creates a run. The LLM does not spontaneously start processes. The Gateway, an IM channel, an internal client, or a scheduled job initiates a run; **the agent determines the steps inside that run**. DeerFlow's scheduler reuses the Gateway run lifecycle rather than inventing a separate kind of AI execution.

Source: [Gateway runtime overview](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/docs/ARCHITECTURE.md), [runtime package](https://github.com/bytedance/deer-flow/tree/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/runtime).

## <Label color="teal">03</Label> The core: a model + graph + tool loop

The entry point is `make_lead_agent()` in [`lead_agent/agent.py`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/agents/lead_agent/agent.py). It delegates to an assembly path and eventually builds a LangChain agent using `create_agent`. DeerFlow adds a significant amount of configuration and middleware around that primitive.

A simplified conceptual equivalent looks like this:

<Card accent="teal" flush={true}>

```python
# PSEUDOCODE — conceptual model, not a DeerFlow API example
def build_agent(run_config):
    model = resolve_allowed_model(run_config)
    tools = discover_tools(run_config)
    tools = authorize_and_filter_tools(tools, run_config.identity)
    system_prompt = render_instructions(run_config)
    middleware = build_middleware_stack(run_config)

    return create_agent(
        model=model,
        tools=tools,
        system_prompt=system_prompt,
        middleware=middleware,
        state_schema=ThreadState,
        checkpointer=checkpointer,
    )
```

</Card>

Then the underlying graph behaves roughly like:

```text
                  +------------------+
                  |  Model invocation|
                  +--------+---------+
                           |
                 tool calls requested?
                   /               \
                  yes               no
                   |                 |
          validate / execute      final answer
                   |
             ToolMessages
                   |
              update state
                   |
                   +-------> next model invocation
```

This explains why the “agent” can adapt its execution order: **the model picks a tool based on the task and the schemas it can see**. But tool execution is not unrestricted. Middleware, authorization, budget controls, and the available tool registry constrain what the model can actually do.

The source additionally produces a `LeadAgentAssembly` descriptor describing the effective graph configuration. That makes assembly observable rather than assuming a graph with a familiar name was assembled identically on every run.

### Why middleware matters more than clever prompting

A practical agent needs behavior at multiple boundaries: before the first model call, before each model call, after a tool result, and on failures. DeerFlow's middleware stack includes thread setup, uploads, sandbox acquisition, summarization, title generation, todo planning, image handling, clarification and, in current source, controls such as loop detection, token budgets, tool filtering, model compatibility and terminal-response handling.

## <Label color="green">04</Label> Tools, Skills, MCP: three different things

These terms are often mixed up, but DeerFlow treats them as distinct mechanisms.

<DataTable
  caption="Three different extension surfaces"
  accent="teal"
  headers={["Mechanism", "What it provides", "Typical example", "Who controls execution?"]}
  rows={[
    { "Mechanism": "Tool", "What it provides": "A callable operation with arguments and a result", "Typical example": "read_file, bash, web search", "Who controls execution?": "Host tool implementation" },
    { "Mechanism": "Skill", "What it provides": "Reusable instructions and supporting workflow resources", "Typical example": "Investigate a repository and produce a report", "Who controls execution?": "Agent, through allowed tools" },
    { "Mechanism": "MCP server", "What it provides": "An external tool/resource integration protocol", "Typical example": "Issue tracker or document source", "Who controls execution?": "MCP connector + server + host policy" }
  ]}
/>

DeerFlow merges several sources into an available tool catalog: built-in tools, configured sandbox and web tools, MCP tools, and optional extension/subagent tools. The model sees their **descriptions and argument schemas**, not a general permission to invoke arbitrary functions.

A skill is closer to a **capability package or runbook** than a new execution engine. The harness discovers skills and loads instructions when relevant; those instructions can direct the agent to compose existing tools. It should not be interpreted as a security policy: a skill telling the agent not to run a dangerous command is weaker than blocking that command in the tool executor.

MCP is different: it exposes tools from another process or service. The external server does not need to know about DeerFlow's UI or chat messages. DeerFlow's adapter provides the model-facing schema and execution bridge.

### Keeping large tool catalogs affordable

Every tool schema included in a model request consumes context. The current lead-agent source contains **deferred MCP tool-schema filtering**, tool promotion and routing-related middleware. That is an important scaling idea: a platform with hundreds of integrations should avoid injecting every detailed schema into every model call. Discovery and selection can narrow what is visible, while execution still rechecks permission.

A recommended design for a configurable platform is:

```text
User input
  -> deterministic eligibility filter
  -> small relevant tool catalog
  -> model selects a tool
  -> server-side authorization
  -> execution adapter
  -> structured result
```

Do not confuse **tool discovery** with **tool authorization**. An LLM hiding or omitting a tool is not a substitute for a server-side deny.

Source: [tools registry](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/tools/tools.py), [lead-agent assembly](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/agents/lead_agent/agent.py).

## <Label color="teal">05</Label> How sub-agents really work

“Multi-agent” does **not** necessarily mean a swarm of agents permanently chatting with one another. In DeerFlow the lead agent can delegate a bounded task to a subagent, often through the `task` tool, and then use the result in its own reasoning.

Imagine a request to compare three candidate libraries. The lead agent can investigate one library itself or delegate independent investigations in parallel. The choice is a cost/latency trade-off, not an automatic requirement.

Key implementation details worth studying:

- The source tracks a **server-side `execution_id`** and correlates work back to the provider's `tool_call_id`. That matters for tool messages, lifecycle events and retries.
- Subagents have **separate execution context** so they need not carry the entire lead conversation. The parent can pass a task-specific snapshot.
- Built-in subagent types include **`general-purpose`** and **`bash`**. Additional types can be configured or managed.
- The system limits **concurrent** and **total** delegation, and supports per-subagent turn and timeout policies.
- The documented policy prefers *direct execution* unless parallel latency, specialization, or context isolation justifies delegation.

<Callout color="amber">
  **A subagent is not free concurrency.** Each child can pay for its own context, tool discovery, model turns, and summarization. Parallel calls can reduce elapsed time while increasing total tokens, external API requests, and side-effect risk.
</Callout>

For a platform with user-defined agents, I would separate **agent selection** from **subagent delegation**. A deterministic router can select the appropriate top-level agent. Once running, the lead agent may delegate bounded subtasks to specialists. Those are two different decisions and need separate authorization.

Source: [subagent executor](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/subagents/executor.py), [subagent package guidance](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/subagents/AGENTS.md).

## <Label color="green">06</Label> Why a sandbox is a security boundary, not a convenience

Giving the model a `bash` tool is easy. Giving it a safe place to use that tool is the hard part.

DeerFlow abstracts the execution environment behind a `SandboxProvider`. Local mode can execute directly for development; production-oriented configurations can use isolated Docker-based environments, with additional provisioner support for deployments that need managed sandboxes.

That abstraction allows the *tool interface* to remain stable even if the *execution environment* changes. Conceptually:

```python
# PSEUDOCODE: one tool contract, multiple backends
def run_command(command, execution_context):
    sandbox = sandbox_provider.acquire(execution_context.thread_id)
    return sandbox.exec(command, timeout=execution_context.command_timeout)
```

The tool sees a command and a context. The sandbox provider decides which filesystem, process namespace, network policy and runtime apply. DeerFlow also maps logical paths into its user-data workspace.

Do **not** treat sandboxing as complete multitenant authorization. A production system still needs tenant-scoped credentials, allowlisted network destinations, resource quotas, secret handling, execution timeouts, audit records, and explicit approvals for high-risk actions.

I particularly like the separation: tools are a *capability interface*, while sandbox providers are an *execution adapter*. This maps naturally onto local Docker, Kubernetes jobs, controlled remote workers, or tightly scoped third-party automation.

Source: [architecture security model](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/docs/ARCHITECTURE.md).

The [`ThreadState` implementation](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/agents/thread_state.py) extends LangGraph's `AgentState` with additional fields. It uses **reducers** to merge certain updates safely. This is not the same as adding arbitrary entries to a Python dictionary: for concurrent tool or subagent updates, merge semantics matter.

For longer sessions, summarization reduces context pressure. Long-term memory has a separate backend-neutral manager and tools such as `memory_search`, `memory_get` and `memory_add`. Its default local DeerMem backend stores a user-level summary and individual agent-scoped fact files, with optional alternative backends. The memory system has different passive-middleware and explicit-tool operating modes.

A useful operating principle:

> **Checkpoint to recover execution. Summarize to fit the context window. Store facts to remember across sessions. Save files to retain artifacts.**

These four concerns should not be implemented by the same unbounded message array.

### A less obvious detail: checkpoint storage cost

DeerFlow's runtime documentation covers both **full** and **delta** checkpoint channel modes. In full mode, repeated snapshots of a growing message history can become expensive. Delta mode stores incremental writes and periodic snapshots, trading off storage efficiency against more complex restore and branching semantics. The mode is process-frozen and requires compatible readers.

This is an especially useful lesson from a real codebase: durable execution isn't “add Postgres and forget it.” Message identity, reducers, checkpoint ancestry, branching and cancellation recovery require explicit design.

Source: [memory system](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/agents/memory/AGENTS.md), [checkpoint/runtime guidance](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/runtime/AGENTS.md).

## <Label color="green">08</Label> How does the result reach the UI?

The worker does not need a direct network connection to the browser. The **Gateway owns the run and streams its observable events**.

In the standard web path, the frontend uses `@langchain/langgraph-sdk` to open a thread, submit input, and subscribe to Server-Sent Events (SSE). The Gateway's `StreamBridge` adapts runtime events to the HTTP stream. The frontend reduces streamed messages, state snapshots, task progress and artifact changes into its thread UI.

The implementation distinguishes several stream modes:

- **`messages`** carry model-token or message deltas.
- **`values`** carry graph state snapshots.
- **`custom`** can carry explicit task or progress events.

Subgraph events may be **namespaced** so a child agent does not masquerade as the root thread. This is important for UIs that show subtask progress while preserving a coherent parent conversation.

**Product implication:** persist a run ID and thread ID, make events monotonic/idempotent where practical, and give the frontend a way to reload authoritative state after reconnecting. A token stream alone is insufficient for a long-running agent application.

## <Label color="teal">09</Label> Reliability, permissions and stopping conditions

Long-running agents need **mechanical stop conditions**, not only a prompt saying “be careful.”

From the current code and architecture guidance, notable controls include:

| Failure mode | DeerFlow mechanism to inspect | Broader lesson |
| --- | --- | --- |
| Model repeats a tool loop | Loop detection middleware | Put a hard guard around repetition |
| Run spends too many tokens | Token budget / usage middleware | Count across the execution, not only a single reply |
| Excessive child-agent fanout | Subagent concurrency and total limits | Bound parallelism and total work |
| Context becomes too large | Summarization middleware | Compact intentionally, preserving needed facts |
| Unsafe tool or model access | Authorization/filtering before model and execution | Enforce access outside the LLM |
| Tool execution fails mid-task | Run status, checkpoints, retries and explicit error outcomes | Distinguish retryable failures from uncertain side effects |
| Client disconnects | Gateway run lifecycle and persisted state | UI connection must not be the source of truth |

One especially valuable pattern in the architecture is the **run-context trust boundary**. Values provided by a client are not automatically trusted just because they have names like `user_id`, `non_interactive`, or `sandbox_id`. Server-authored identity and lifecycle fields must be established from authenticated context, not accepted from request JSON.

For external side effects—sending email, updating a record, executing an HTTP webhook—my additional recommendation is a **tool-operation ledger** with a stable idempotency key, approval state and possible `OUTCOME_UNKNOWN` status. That is **an architectural recommendation**, not a claim that every DeerFlow tool uses this exact ledger contract.

## <Label color="green">10</Label> How I would use these ideas to build a configurable agent platform

DeerFlow shows **how to build a powerful execution harness**. A configurable multi-tenant platform needs another layer: managing who defines agents, which version is published, what data they may reach, and whether a particular run is allowed.

I would split responsibilities into three layers:

**1. Control plane — define and govern.** Store `AgentDefinition`, `AgentRevision`, `ModelPolicy`, `SkillBinding` and `ToolBinding`. Validate configuration, permissions and schema compatibility before publishing. Pin a revision for each run so later edits cannot silently change an in-progress execution.

**2. Runtime plane — execute and recover.** Admit a run, obtain an allowed model, construct the agent, enforce budgets, track state, delegate bounded work, invoke tools and publish event streams. DeerFlow provides many useful patterns here.

**3. Integration plane — connect and enforce.** HTTP, MCP, SQL read-only connectors, workflow engines, and controlled shell execution should implement stable tool contracts. Always reauthorize at execution time. Keep credentials inside the integration service or broker, not the model prompt.

### How should requests select an agent?

Do not begin every request with an expensive supervisor model. A sensible default is:

```text
1. Authenticate caller; determine tenant/workspace permissions.
2. Filter agents by allowed workspace, status, revision and capabilities.
3. Check deterministic routing rules or explicit agent selection.
4. If ambiguous, compare intent with descriptions/example questions.
5. Use a small model only when the cheap router lacks confidence.
6. Admit the selected agent run with an explicit budget.
7. Delegate child tasks only when independent work justifies them.
```

This is **my recommended routing design**, not DeerFlow's claimed universal selection algorithm.

### Example: an extensible support investigation

Suppose a user asks, “Why did my order fail yesterday?”

A support agent may need an order lookup, an incident log search and a knowledge-base query. The platform can expose all three as authorized tools. A bounded agent chooses which to call, combines evidence and drafts an answer. Only if ambiguity remains should it escalate to a stronger model or a specialist. A refund or data mutation must go through deterministic authorization and approval.

This generalizes without hardcoding every possible workflow into Python, while keeping business-critical operations outside the model's discretion.

## <Label color="teal">11</Label> Cost and performance: what I would measure

A sophisticated agent is easy to make **expensive**. An agent that delegates five investigations may feel fast, but model calls can multiply while the parent still needs to synthesize the results.

Use the following as an engineering budget model, not as DeerFlow benchmark data:

```text
run_cost ≈ Σ(model input tokens × input price)
         + Σ(model output tokens × output price)
         + tool / search / sandbox / retrieval cost
         + delegated subagent cost
```

End-to-end latency is not just the sum of tokens, either. Independent subagents can overlap in wall-clock time, but their shared resource contention, tool dependencies and final synthesis remain. The best choice can be **one model call**, **deterministic code**, or **one direct agent**, not always a swarm.

### 13.2 What is stored in the database—and what is not?

The project has a **unified database selector** in [`DatabaseConfig`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/config/database_config.py): `memory`, `sqlite`, or `postgres`. SQLite places application tables and LangGraph checkpoint/store data in the same `{sqlite_dir}/deerflow.db` file, using WAL. PostgreSQL connects to one configured database, but the application ORM and LangGraph integrations own different connection pools. The in-memory option is not durable.

| Data / authority | Storage and code | Important fields or contract |
| --- | --- | --- |
| **Run lifecycle** | SQLAlchemy `runs` table — [RunRow](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/persistence/run/model.py) | `run_id`, `thread_id`, `assistant_id`, `status`, `model_name`, `metadata_json`, `origin_kind` |
| **Reliability and ownership** | Same `runs` row | `idempotency_key`, `owner_worker_id`, `lease_expires_at`, cancellation request and token-usage columns |
| **Durable run journal** | SQL `run_events` — [RunEventRow](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/persistence/models/run_event.py) | `thread_id`, `run_id`, `event_type`, `category`, `content`, `seq`; unique position per thread |
| **Graph state** | LangGraph-managed checkpoint tables, accessed via [checkpointer provider](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/runtime/checkpointer/provider.py) | Thread, message state and intermediate graph progress—not a replacement for the run journal |
| **Conversation / user metadata** | DeerFlow application persistence layer | Thread metadata, ownership, user/agent references and related application records |
| **Custom agent definitions** | Per-user `config.yaml` + `SOUL.md` on disk by default; optional SQL `agents` rows — [AgentRow](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/persistence/agents/model.py) | Unique user/name; config JSON document; distinct from conversation/checkpoint data |
| **Files, uploaded inputs, artifacts** | Per-thread user-data workspace and selected sandbox/blob storage | Files are **not** automatically copied into SQL run rows or embedded wholesale in checkpoints |
| **Agent memory** | Configured memory backend | Long-lived facts and recall are separate from conversation graph state |
| **Live SSE buffer** | In-process bridge or optional Redis Streams — [StreamBridge](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/runtime/stream_bridge/base.py), [RedisStreamBridge](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/runtime/stream_bridge/redis.py) | Delivery, replay cursor and heartbeats—not the authority for durable run history |

<Callout color="amber">
  **Important separation:** `runs` describes *whether* an execution is pending/running/finished. `run_events` describes *what happened*. LangGraph checkpoints describe *where graph state can resume*. Redis/memory streams deliver *what viewers see now*. File/blob storage keeps *actual artifacts*. These are not interchangeable, and a missing live event does not necessarily mean the underlying run or checkpoint disappeared.
</Callout>

Schema evolution is also implemented, not hand-waved: [`bootstrap_schema`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/persistence/bootstrap.py) chooses a fresh-database baseline path or Alembic upgrade path, with versioned migrations under [`migrations/versions/0001_baseline.py`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/persistence/migrations/versions/0001_baseline.py). LangGraph owns its **own** checkpoint-table migrations; the DeerFlow Alembic baseline explicitly excludes them. The SQL event store includes sequence assignment and concurrency safeguards rather than relying on a list in one process.

### 13.3 The actual HTTP and streaming contracts

The browser uses the **LangGraph JS SDK**, not a custom invented WebSocket protocol. Nginx maps the public `/api/langgraph/*` prefix to the Gateway's native `/api/*` endpoints. The main run paths include:

| HTTP method / path | Role |
| --- | --- |
| `POST /api/langgraph/threads/{thread_id}/runs` | Create a run; return run metadata immediately |
| `POST /api/langgraph/threads/{thread_id}/runs/stream` | Create and subscribe to SSE in one request |
| `POST /api/langgraph/threads/{thread_id}/runs/wait` | Create and wait for an outcome |
| `POST /api/langgraph/runs/stream` | Stream a run without requiring an existing thread; Gateway can create one |
| `GET /api/models`, `/api/agents`, `/api/mcp`, `/api/skills` | Application capability/configuration endpoints under the native `/api/*` route family |

[`RunCreateRequest`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/app/gateway/run_models.py) is the Pydantic boundary contract. The following request is a **minimal illustrative wire example**, not a substitute for the full schema:

```http
POST /api/langgraph/threads/{thread_id}/runs/stream
Content-Type: application/json

{
  "assistant_id": "lead_agent",
  "input": { "messages": [{ "role": "user", "content": "Investigate service latency" }] },
  "stream_mode": ["messages", "updates"],
  "on_disconnect": "continue",
  "multitask_strategy": "reject"
}
```

The real request schema also validates `command`, `config`, `context`, `checkpoint_id`, `stream_subgraphs` and other fields. **Compatibility is deliberately partial**: several LangGraph Platform options are only accepted as null/default placeholders, rather than being implemented. Inspect the Pydantic model before assuming full LangGraph Platform equivalence.

A streaming response uses `Content-Type: text/event-stream`, a canonical run `Content-Location`, and frames formatted by [`format_sse`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/app/gateway/services.py):

```text
event: <LangGraph-compatible-event-name>
data: <JSON payload>
id: <replay-cursor>

```

The bracketed tokens above are **placeholders**, not literal DeerFlow payloads. [`StreamBridge`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/packages/harness/deerflow/runtime/stream_bridge/base.py) defines `publish()`, `subscribe(last_event_id=...)`, and `publish_end()`. It supports heartbeats and an explicit replay-gap result when the requested cursor is no longer retained. For multi-worker topologies, the Redis implementation uses Redis Streams; an in-process bridge cannot serve another worker's active stream. On the browser side, [`api-client.ts`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/frontend/src/core/api/api-client.ts) handles rejoining/reload behavior and stream-gap recovery.

| **Configuration specification** | [`CONFIGURATION.md`](https://github.com/bytedance/deer-flow/blob/1f15e0b43ca58b9601514f9f5c408fb032022833/backend/docs/CONFIGURATION.md), `config.yaml`, `extensions_config.json` | Deployment-level model, DB, MCP, skills, permissions and runtime settings |

For example, the sandbox adapter contract is **not** equivalent to giving an LLM unrestricted shell access. A provider owns sandbox acquisition and identity-scoped retrieval; a sandbox implementation exposes the operations. Agent middleware and authorization decide whether tools should be visible and invoked. Local development execution and isolated/container-backed execution have different security properties.

The extension API has its own useful compatibility rule: plugin `Protocol` methods have default implementations and optional dataclass fields have defaults. That is a conscious attempt at additive compatibility, but the package's `api_version` should still be treated as a real release boundary.

### 13.5 Follow one request through named functions

This is the **source-code path**, complementary to the interactive numbered runtime walkthrough above:

```text
Next.js useStream / LangGraph JS SDK
  → Nginx: /api/langgraph/* → Gateway /api/*
  → app.gateway.routers.thread_runs.stream_run()
  → app.gateway.services.start_run()
  → RunManager: admit, persist and own the run
  → runtime.runs.worker: run graph via graph.astream(...)
      → lead_agent assembly: model / tool / middleware
      → LangGraph state and checkpoint provider
      → optional tools / MCP / sandbox / subagent execution
  → StreamBridge.publish(run_id, event, payload)
  → Gateway sse_consumer() → text/event-stream
  → frontend core/api + core/threads normalize events
  → React thread UI renders progress and artifacts
```

Branches matter: a run without a tool call skips sandbox/MCP execution; a run with tool calls can iterate many times; a delegated subagent can emit namespaced events; a client disconnect follows the configured `on_disconnect` policy. The run journal and checkpoints may be written while the SSE consumer is still connected. **This is one Python Gateway with background async agent tasks by default, not proof of a distributed queue-based worker fleet.**

### 13.6 What the design does *not* automatically guarantee

- **Multi-tenant isolation:** user/thread scoping and auth hooks exist, but the code does not by itself establish a product-grade tenant/workspace control plane. Treat that as a separate platform design.
- **Exactly-once tool side effects:** run admission idempotency and leases do not make arbitrary HTTP calls or shell commands exactly-once. External effects need operation keys, reconciliation and, when appropriate, approvals.
- **Durability of all live events:** Redis Stream retention and SSE cursor gaps are separate from SQL run events and LangGraph checkpoint history.
- **Safe plug-and-play:** arbitrary third-party tools or trusted in-process plugins should never be assumed safe solely because they implement the declared interface.
- **One shared source of truth for everything:** memory, model context, checkpoints, run/event SQL tables, artifacts and live streams have different ownership and recovery semantics.

**Implementation takeaway:** before building your own agent platform, decide which component owns run identity and admission, what the durable state contract is, how external tool effects are recorded, which interfaces customers can extend, what event protocol the UI consumes, and how revisions/permissions are enforced. DeerFlow provides strong implementation examples for several of those questions, but the source should be read as a *reference*, not copied as a complete multi-tenant platform.

## Conclusion: what DeerFlow gets right

The lesson is not “every product should adopt DeerFlow.” The lesson is that **the LLM decision loop is the simplest part of a robust agent**.

DeerFlow is a particularly useful reference for the runtime side: graph construction, middleware, tool extensibility, isolation, state, delegation and event streaming. Those systems allow a model to work for more than one or two turns without the application collapsing into an unobservable chain of API calls.

For a multi-tenant configurable agent platform, I would **borrow the architecture principles** while placing agent definitions, versioning, identity, routing, audit, budgets and tool policies in an explicit platform control plane. The model proposes actions; the platform owns the authority to execute them.

The next implementation exercise I would do is deliberately small: one support agent, three read-only tools, one versioned configuration, one SSE thread, one checkpoint store, a cost ceiling, and one explicit approval gate. If that works reliably, subagent delegation is an optimization to add—not the foundation to start with.
