Here is something most application developers never think about: in memory, you call `malloc`, get a pointer, write to it, and the runtime handles the rest. On disk, you have only `read` and `write` at byte offsets. There is no dynamic allocation. There is no garbage collector. You manage your own heap within fixed-size pages.

Moving from B-Tree theory to a real B-Tree implementation means confronting this gap directly.

## <Label color="teal">1</Label> Why Binary Encoding Matters

In memory: malloc/free, pointers, garbage collection. On disk: only `read` and `write` at byte offsets. No dynamic allocation — manage your own "heap" within fixed-size pages.

The consequences:
- All data must be serialized to bytes before writing; deserialized after reading
- Variable-size data (strings, arrays) requires explicit length tracking
- Pointers become byte offsets within files (or page IDs + offsets within pages)
- Fragmentation must be handled explicitly; the OS won't compact your pages

---

## <Label color="teal">2</Label> Primitive Type Encoding

Numeric types are straightforward — each has a fixed byte size:

```
byte:   1 byte  (8 bits)
short:  2 bytes (16 bits)
int:    4 bytes (32 bits)
long:   8 bytes (64 bits)
float:  4 bytes (IEEE 754)
double: 8 bytes (IEEE 754)
```

The critical decision for multibyte types: **endianness**. The same 32-bit integer `0xAABBCCDD` is stored differently depending on the platform:

- **Big-endian**: `AA BB CC DD` (most significant byte first, lowest address)
- **Little-endian**: `DD CC BB AA` (least significant byte first, lowest address)

Storage formats must commit to one byte order and use it consistently. Most network protocols use big-endian ("network byte order"). Most x86 platforms are little-endian. Databases typically pick one and document it — readers must know the format to decode correctly.

<Callout color="amber">
RocksDB detects host endianness and reverses bytes when needed, so the on-disk format is always little-endian regardless of the running platform. The cost: one byte-reversal per value on big-endian machines.
</Callout>

## <Label color="teal">3</Label> Variable-Length Data Encoding

Fixed-size types are trivial — offsets are predictable. Variable-length types require explicit length encoding:

**Length-prefixed string**: store the length as a fixed-size integer before the string bytes.
```
| 4-byte length | string bytes... |
```

**Null-terminated string**: append a zero byte after the string content. Simple but requires a scan to find the end — bad for seeking.

**Offset arrays**: for a record with multiple variable-length fields, store an array of offsets at the front of the record. Each offset points to the start of its field within the record body. This allows O(1) access to any field by index without scanning through preceding variable-length fields.

```
| offset[0] | offset[1] | ... | field_0_data | field_1_data | ... |
```

## <Label color="teal">4</Label> Page Structure

All on-disk B-Tree implementations organize storage into fixed-size **pages** (commonly 4KB, 8KB, or 16KB). A page is the unit of I/O — reads and writes always transfer complete pages.

A typical page has two regions:
1. **Header**: page ID, type (leaf/internal/overflow), free space offset, cell count, flags, checksum
2. **Body**: the actual data cells (key-value pairs or separator keys + child pointers)

The fundamental challenge: cells within a page may have different sizes (keys and values vary in length), but the page itself is fixed size. The **slotted page** format solves this.

---

## <Label color="teal">5</Label> Slotted Pages

The slotted page format is the standard solution to variable-size cell management within a fixed-size page:

```
+----------------------------------+
| Page Header                       |
+----------------------------------+
| Slot 1 offset | Slot 2 offset | ...|  ← slot array grows →
|                                   |
|          free space               |
|                                   |
| ← grows ← Cell 2 | Cell 1 |     |  ← cells grow backwards
+----------------------------------+
```

The key insight: the slot array gives stable O(1) access to any cell by slot index, even as cells are deleted and the page becomes fragmented. The physical position of a cell changes during compaction, but its slot index does not.

## <Label color="teal">6</Label> Checksums and Versioning

Two correctness mechanisms every on-disk format needs:

**Checksums**: A CRC or similar checksum stored in the page header over the page body. On read, recompute the checksum and compare. If they differ, the page was corrupted (partial write, bit flip, hardware failure). Allows the engine to detect and refuse to serve corrupt data rather than silently returning garbage.

**Versioning**: A format version field in the file header. When the on-disk format changes between software versions, the engine checks the version on open and either migrates the format, refuses to open an incompatible version, or applies compatibility shims.
