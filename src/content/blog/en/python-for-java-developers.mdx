This is Chapter 1 of a series translating the Java mental model into Python. We will cover names and objects first, then functions and protocols, iterators and generators, exceptions, packaging, concurrency, and the parts of Python that become dangerous when Java assumptions stay hidden underneath.

The first lesson is deceptively small: **a Python variable is a name attached to an object**. Assignment attaches another name. It does not copy the object, call a constructor, or change the object's type.

## Explain it simply

Imagine a room full of labeled boxes. The label is a variable name. The box is an object. You can put a second label on the same box, remove one label, or move a label to a different box. The box itself does not know which labels point at it.

Java developers already use something close to this model for object references. The important difference is that Python makes the name/object relationship visible everywhere: even `int`, `str`, and `tuple` are objects, and the language does not give you a declaration that permanently binds a name to one class.

```python
items = ["java"]
alias = items

alias.append("python")
print(items)  # ['java', 'python']
```

`items` and `alias` are two names for one list. The append mutates that list, so both names observe the change.

## Find the crack in the Java intuition

In Java, this also aliases one mutable object:

```java
var items = new ArrayList<String>();
var alias = items;
alias.add("java");
System.out.println(items); // [java]
```

So far, there is no surprise. The trouble starts when a Python expression looks like a declaration but is not one:

```python
items = []
items = ["python"]
```

The second line does not mutate the old list. It moves the `items` name to a new list. Any other name still pointing at the old list keeps seeing the old object.

## Formalize it precisely

### 1. Names do not have declared types

Java declarations make the intended type visible at the binding site:

```java
List<String> names = new ArrayList<>();
```

Python binds a name at runtime:

```python
names = []
names = "not a list anymore"
```

This is legal because the name has no permanent declared type. The object currently referenced by `names` has a type; the name itself is just a lookup key.

That does not mean Python has no types. It means type checking happens through the object and the operations you perform, not through a declaration that prevents every later rebinding.

### 2. `is` and `==` answer different questions

Use `==` to ask whether two objects have equal values. Use `is` to ask whether they are the exact same object.

```python
left = [1, 2]
right = [1, 2]

print(left == right)  # True: equal contents
print(left is right)  # False: different list objects

alias = left
print(alias is left)  # True: same object
```

The practical rule is narrow: use `is None` for the singleton `None`; use `==` for ordinary value comparisons. Do not use `is` as a faster-looking spelling of equality.

### 3. Mutability is the boundary that matters

Immutable objects cannot be changed in place. An operation that appears to update them creates a new object and returns or rebinds it:

```python
count = 1
other = count
count += 1

print(count)  # 2
print(other)  # 1
```

The integer `1` was not modified. `count += 1` computes a new integer and points `count` at it. `other` remains attached to the old integer object.

Lists, dictionaries, and sets are mutable. Strings, integers, tuples, and booleans are immutable. A tuple can still contain a mutable object, so immutability is shallow with respect to its container:

```python
box = (["java"],)
box[0].append("python")  # allowed: the nested list is mutable
# box[0] = []             # TypeError: the tuple slot cannot be replaced
```

### 4. Function arguments pass object references

Python does not copy an argument just because it crosses a function boundary:

```python
def add_language(languages):
    languages.append("python")

languages = ["java"]
add_language(languages)
print(languages)  # ['java', 'python']
```

The function received another name for the same list. Rebinding the parameter would be different:

```python
def replace_languages(languages):
    languages = ["python"]

languages = ["java"]
replace_languages(languages)
print(languages)  # ['java']
```

The function's local `languages` name moved. The caller's name did not.

## The defensive-copy decision

A Java method often communicates ownership through conventions, interfaces, or explicit copying. In Python, decide deliberately when accepting a mutable value:

```python
def add_tag(tags, tag):
    """Mutates the caller's list — document that contract."""
    tags.append(tag)


def with_tag(tags, tag):
    """Returns a new list — leaves the caller's list alone."""
    return [*tags, tag]
```

Neither style is universally correct. Mutation is useful for a local builder with one clear owner. Returning a new value is safer at an API boundary, especially when callers may share the object.

## Edge cases that punish a shallow mental model

The rules above compose. The difficult bugs appear when mutation, operator dispatch, nested objects, and runtime optimizations overlap.

### `+=` asks the current object how to behave

For a list, augmented assignment normally calls `list.__iadd__`, mutates the existing list, and returns that same object:

```python
left = ["java"]
right = left

left += ["python"]

print(left)          # ['java', 'python']
print(right)         # ['java', 'python']
print(left is right) # True
```

For a tuple, there is no in-place mutation. Addition creates a new tuple and rebinds only `left`:

```python
left = ("java",)
right = left

left += ("python",)

print(left)          # ('java', 'python')
print(right)         # ('java',)
print(left is right) # False
```

The syntax is identical, but the object protocol is not. Read `x += y` as “ask `x` for in-place addition; otherwise compute addition and rebind `x`,” not as a universal mutation operator.

### A shallow copy creates a container, not a new object graph

```python
original = [["java"], ["rust"]]
copied = original.copy()

copied.append(["python"])
copied[0].append("kotlin")

print(original)  # [['java', 'kotlin'], ['rust']]
print(copied)    # [['java', 'kotlin'], ['rust'], ['python']]
```

The outer lists are different objects. Their nested lists are still shared. Use a deep copy only when duplicating the entire reachable graph is truly the contract; deep copying arbitrary domain objects can duplicate identities, locks, file handles, caches, or ORM state that should never be cloned.

### Identity can look stable until an optimization changes

CPython may intern some integers and strings. That can make incorrect identity comparisons appear reliable:

```python
a = 257
b = int("257")

print(a == b)  # True
print(a is b)  # False on normal CPython runs
```

The language promises value equality here, not shared identity. Literal folding, interactive shells, Python versions, and implementations may produce a different identity result. Use `is` for deliberate singleton checks such as `value is None`; use `==` for values.

### Mutation can survive a failed augmented assignment

```python
box = (["java"],)

try:
    box[0] += ["python"]
except TypeError:
    pass

print(box)  # (['java', 'python'],)
```

This expression has two stages:

1. `list.__iadd__` mutates the nested list.
2. Python tries to assign the result back into `box[0]`.

The tuple rejects stage 2, but Python does not undo stage 1. An exception means the overall expression failed; it does not guarantee that every earlier side effect was rolled back.

## Production risks

These rules become operational problems at API boundaries:

- **Leaking internal state:** returning an internal list lets callers mutate an object's private state without using its methods.
- **Cross-request contamination:** module-level containers and mutable defaults can retain data between requests, tests, tasks, or tenants.
- **Broken dictionary and set membership:** an object used as a key must keep a stable equality/hash relationship. Mutating fields that participate in hashing makes lookups unreliable.
- **Shallow configuration copies:** modifying a nested dictionary in one request can change the supposedly independent configuration used by another.
- **Misleading annotations:** `items: list[str]` helps tools and readers, but does not make the binding final or the list immutable at runtime.
- **Concurrent aliases:** the GIL does not turn a multi-step mutation into a business-level transaction. Threads and async tasks can still observe partially updated shared state across suspension points or compound operations.

At public boundaries, make ownership visible. Return immutable views or fresh values when callers should not mutate your state. If mutation is intentional, name and document it as part of the API contract.

## Advanced internals: what Python actually dispatches

The data model turns syntax into protocol calls:

`id(obj)` identifies an object only for that object's lifetime. After the object is destroyed, a later object may reuse the same identity value. Never store `id()` as a durable identifier.

CPython primarily frees unreachable objects through reference counting and supplements it with a cyclic garbage collector. Other Python implementations may manage memory differently. Code should rely on language-level lifetime rules and context managers—not CPython's usual timing for finalization.

Equality and hashing form another invariant: objects that compare equal must have the same hash. Mutable value objects are therefore usually unhashable. A tuple is hashable only when every contained value is hashable; being a tuple does not automatically make an object graph safe as a dictionary key.

## Teach it back

You should now be able to answer these without looking back:

1. Why do `alias.append("x")` and `items = ["x"]` have different effects on aliases?
2. Why can the same `+=` syntax mutate a list but rebind a tuple name?
3. Why does a shallow copy still share nested objects?
4. When should you use `is None` instead of `== None`, and why are integer/string identity experiments misleading?
5. How can `box[0] += value` mutate a nested list and still raise `TypeError`?
6. Why does rebinding a function parameter not rebind the caller's variable?
7. When should an API return a fresh or immutable value instead of exposing mutable state?
