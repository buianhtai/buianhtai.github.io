## <Label color="teal">1</Label> What Patterns Are (and Are Not)

A design pattern is a named solution to a recurring design problem in a given context. The **name** matters as much as the structure: calling something a "Strategy" tells every reader of the code exactly what the intent is — algorithmic encapsulation, family of interchangeable behaviors, client configures which one runs.

What patterns are *not*:

- **Not a law.** No codebase is required to use patterns. Simple problems deserve simple solutions.
- **Not a silver bullet.** Patterns solve specific classes of problems. The wrong pattern applied to a problem is worse than no pattern.
- **Not a substitute for understanding.** You can't look at a UML diagram for Observer and know when to use it. You need to understand the coupling problem it solves to recognize when you have it.

<Callout color="teal">
Patterns are a shared vocabulary for experienced designers. The value of calling something a Facade is that every team member immediately knows: this is a simplified interface over a complex subsystem. The vocabulary compresses design discussions. That's the primary value — not the structure itself.
</Callout>

## <Label color="teal">4</Label> Principles vs. Patterns

Design principles are more durable than patterns because they explain *why* patterns work, not just *what* they are:

| Principle | What it prevents | Patterns that embody it |
|---|---|---|
| Encapsulate what varies | Tight coupling of variable parts to stable parts | Strategy, State, Template Method |
| Program to interfaces | Concrete-class coupling | Almost every pattern |
| Favor composition | Fragile inheritance hierarchies | Decorator, Strategy, Composite |
| Strive for loose coupling | Change propagation through object graphs | Observer |
| Open-Closed | Modification risk when extending | Decorator, Observer, Strategy |
| Depend on abstractions | High-level code coupled to low-level details | Factory Method, Abstract Factory |
| Single Responsibility | Mixed concerns colliding when one changes | Iterator, Command |

When you understand the principles, you can derive appropriate structures for problems that don't match any named pattern. The patterns are the examples; the principles are the lesson.

## <Label color="teal">5</Label> How to Think About a Design Problem

A diagnostic flow for deciding whether and which pattern applies:

1. **Name the pain.** What is actually hard to do? Change, test, extend, understand?
2. **Identify the coupling.** What depends on what that shouldn't? What changes together that should change independently?
3. **Look for the principle.** Which design principle — encapsulate what varies, program to interfaces, etc. — is being violated?
4. **Find the pattern.** Which pattern was designed to resolve this violation in this type of context?
5. **Verify the fit.** Does the pattern's intent description match your problem's structure? If not, keep looking.
6. **Weigh the cost.** Are the added classes / indirection / vocabulary worth the coupling reduction? For a three-class utility used in one place: probably not. For a thirty-class system with five extension points: probably yes.

## <Label color="teal">6</Label> The Growth Trajectory

A healthy relationship with patterns evolves:

| Stage | Behavior | Risk |
|---|---|---|
| Novice | Doesn't know patterns exist | Reinvents solutions from scratch; misses well-known traps |
| Pattern enthusiast | Applies patterns everywhere; looks for excuses to use them | Over-engineering; code harder to read than if patterns were absent |
| Experienced | Uses patterns where they fit; prefers simplicity otherwise | None — this is the target |
| Expert | Derives patterns from principles; adapts or combines them for novel problems | None |

The enthusiast stage is the dangerous one. It's also the most common for developers who've just learned patterns for the first time. The solution is the same question: *What problem does this pattern solve here?*

<Callout color="teal">
Simplicity is not the absence of craft — it's the highest form of it. A solution that requires no patterns because the problem genuinely doesn't need them is better than the same solution wrapped in unnecessary abstraction. Patterns are for the problems that are actually hard. Keep them in reserve for those.
</Callout>
