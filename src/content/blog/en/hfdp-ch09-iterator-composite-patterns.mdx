Chapter 9 pairs two patterns that solve different problems but compound well in practice. The Iterator Pattern answers the question: how does a client traverse a collection without knowing whether it is an `ArrayList`, an `Array`, a `Hashtable`, or anything else? The Composite Pattern answers: how do you treat a single leaf object and a whole tree of objects uniformly, so that clients do not need to know which one they have? The menu system from the Diner and Pancake House merger drives both.

## <Label color="teal">1</Label> The Problem: Two Menus, Two Implementations

The Pancake House stores menu items in an `ArrayList`; the Diner stores them in a fixed-size `MenuItem[]` array. When the two restaurants merge, the Waitress must print all items from both menus. Here is what happens without an abstraction:

```java
PancakeHouseMenu pancakeMenu = new PancakeHouseMenu();
ArrayList breakfastItems = pancakeMenu.getMenuItems();   // ArrayList

DinerMenu dinerMenu = new DinerMenu();
MenuItem[] lunchItems = dinerMenu.getMenuItems();        // Array

// Two separate loops — implementation bleeding into client
for (int i = 0; i < breakfastItems.size(); i++) {
    MenuItem item = (MenuItem) breakfastItems.get(i);
    // print item
}
for (int i = 0; i < lunchItems.length; i++) {
    MenuItem item = lunchItems[i];
    // print item
}
```

Three problems crystallize immediately:
1. The Waitress is coupled to both concrete collection types
2. Every new method (`printVegetarianMenu`, `printLunchMenu`) duplicates both loops
3. Adding a third restaurant (using a `Hashtable`) adds a third loop everywhere

The iteration logic — how to move through a collection — should not be the Waitress's concern.

---

## <Label color="teal">2</Label> Iterator Pattern: One Interface, Any Collection

The fix is to give each menu the responsibility of producing its own `Iterator`, and to write the Waitress against that interface alone.

```java
// The Iterator interface (or use java.util.Iterator)
public interface Iterator {
    boolean hasNext();
    Object  next();
}

// DinerMenu creates its own Iterator over the array
public class DinerMenuIterator implements Iterator {
    MenuItem[] items;
    int position = 0;

    public boolean hasNext() {
        return position < items.length && items[position] != null;
    }
    public Object next() {
        return items[position++];
    }
}
```

Both menus now expose `createIterator()`, which returns an `Iterator`. The Waitress collapses to a single loop regardless of what sits underneath:

```java
public void printMenu(Iterator iterator) {
    while (iterator.hasNext()) {
        MenuItem item = (MenuItem) iterator.next();
        System.out.println(item.getName() + " $" + item.getPrice());
    }
}
```

The Waitress no longer imports `ArrayList` or knows that one menu uses an array. She interacts only with the `Iterator` interface. The concrete collection is fully hidden.

## <Label color="teal">3</Label> Single Responsibility Principle

The book uses Iterator to introduce the **Single Responsibility Principle**: a class should have only one reason to change.

Before Iterator, the Waitress had two reasons to change: if menu content changed, and if menu *storage* changed (ArrayList → Array → Hashtable). After Iterator, menu storage change affects only the menu class and its Iterator — not the Waitress at all.

The same principle applies to the menu classes themselves. A `DinerMenu` has one reason to change: the menu's content (add, remove, update items). If it also contained the iteration logic, it would have a second reason to change: whenever the iteration strategy changed. Extracting `DinerMenuIterator` separates these concerns.

<Callout color="teal">
Every class should have only one reason to change. "Reason to change" is a proxy for "axis of responsibility." When you find yourself saying "this class changes when X changes OR when Y changes," you have two responsibilities — extract one.
</Callout>

**Internal vs External Iterators.** Java's `Iterator` interface is an *external* iterator: the client controls the traversal by calling `hasNext()` and `next()` explicitly. An *internal* iterator hands control to the iterator itself — you pass it a function (lambda) and it calls the function on each element. Java's `forEach` with a lambda is internal. External iterators are more flexible: the client can pause, skip, or stop iteration mid-stream. Internal iterators are simpler but require the iterator to handle all traversal logic.

## <Label color="teal">4</Label> Composite Pattern: Trees of Objects

The next problem arrives when the Diner wants to add a dessert sub-menu, and the Pancake House wants a weekend special menu nested inside the breakfast menu. Now the menu is a *tree*, not a flat list. A `MenuItem` is a leaf. A `Menu` can contain both `MenuItem`s and other `Menu`s.

The Composite Pattern's goal: a client that iterates a menu should not need to check whether each element is a leaf item or a sub-menu. Both should respond to the same operations.

The pattern introduces a `MenuComponent` interface that both `MenuItem` (leaf) and `Menu` (composite) implement:

```java
public abstract class MenuComponent {
    // Leaf operations — override in MenuItem
    public String getName()        { throw new UnsupportedOperationException(); }
    public String getDescription() { throw new UnsupportedOperationException(); }
    public double getPrice()       { throw new UnsupportedOperationException(); }
    public boolean isVegetarian()  { throw new UnsupportedOperationException(); }

    // Composite operations — override in Menu
    public void add(MenuComponent c)    { throw new UnsupportedOperationException(); }
    public void remove(MenuComponent c) { throw new UnsupportedOperationException(); }
    public MenuComponent getChild(int i){ throw new UnsupportedOperationException(); }

    // Shared — both leaf and composite override this
    public void print()            { throw new UnsupportedOperationException(); }
}
```

`MenuItem` extends `MenuComponent` and overrides the leaf operations. `Menu` extends `MenuComponent` and overrides the composite operations plus `print()`, which recurses into children:

```java
public class Menu extends MenuComponent {
    List<MenuComponent> components = new ArrayList<>();
    String name;

    public void add(MenuComponent c)    { components.add(c); }
    public void remove(MenuComponent c) { components.remove(c); }
    public MenuComponent getChild(int i){ return components.get(i); }

    public void print() {
        System.out.println("\n" + getName());
        for (MenuComponent c : components) {
            c.print();    // polymorphic — works for both MenuItem and nested Menu
        }
    }
}
```

The Waitress's `printMenu()` method now takes a `MenuComponent` and calls `print()`. Whether that component is a single item or a tree of menus containing sub-menus, the call is identical.

## <Label color="teal">5</Label> Transparency vs Safety: The Tradeoff

Putting both leaf operations (`getPrice()`, `isVegetarian()`) and composite operations (`add()`, `remove()`, `getChild()`) on the single `MenuComponent` interface is a design choice the book calls the **transparency** approach: a client can treat every node uniformly without casting or type-checking.

The cost is **safety**: a client can call `add()` on a `MenuItem` (which throws `UnsupportedOperationException`). The interface promises more than every implementation can deliver.

The alternative — separate `LeafComponent` and `CompositeComponent` interfaces — is safer: the compiler prevents calling `add()` on a leaf. But now the client must check types and cast, which is exactly the coupling the Composite Pattern aims to eliminate.

For most menu and tree use cases, the transparent approach is the pragmatic choice: clients rarely call `add()` on arbitrary nodes — they traverse using `print()` or iterators, which both `MenuItem` and `Menu` support meaningfully.

## <Label color="teal">6</Label> Composite Iterator: Traversing a Tree

When the Waitress needs to find all vegetarian items across all menus and sub-menus, a flat `Iterator` over a single collection is insufficient. The tree requires a recursive traversal.

The Composite Iterator uses a `Stack` of iterators: when it encounters a `Menu` node, it pushes that node's child iterator onto the stack. When a child iterator is exhausted, it pops back to the parent. The client still sees a flat stream of `MenuComponent` objects via the standard `hasNext()` / `next()` interface.

```java
public class CompositeIterator implements Iterator {
    Stack<Iterator> stack = new Stack<>();

    public CompositeIterator(Iterator iterator) {
        stack.push(iterator);
    }

    public Object next() {
        if (hasNext()) {
            Iterator iterator = stack.peek();
            MenuComponent component = (MenuComponent) iterator.next();
            if (component instanceof Menu) {
                stack.push(component.createIterator());
            }
            return component;
        }
        return null;
    }

    public boolean hasNext() {
        if (stack.isEmpty()) return false;
        Iterator iterator = stack.peek();
        if (!iterator.hasNext()) {
            stack.pop();
            return hasNext();   // recurse — check the parent
        }
        return true;
    }
}
```

This is the Iterator and Composite patterns composing: Composite creates the tree structure, Iterator provides the traversal abstraction, and the combination gives clients a uniform way to walk an arbitrarily deep hierarchy without knowing its shape.

<Callout color="amber">
The Null Iterator is the leaf's implementation of createIterator(): return an iterator over an empty collection, or an iterator that always returns hasNext() = false. This avoids null checks in the CompositeIterator and keeps the traversal code branch-free.
</Callout>

## What the Patterns Give You

- **Iterator** makes collection implementation irrelevant to clients. ArrayList, Array, LinkedList, Hashtable — the Waitress calls `hasNext()` and `next()` on all of them identically. Adding a new collection type requires only a new Iterator class; client code is unchanged.
- **Single Responsibility** is enforced structurally: the menu manages its items, the Iterator manages traversal. Two separate reasons to change, cleanly separated.
- **Composite** eliminates `instanceof` checks in client code that traverses trees. The same `print()` call works on a single `MenuItem` and on a `Menu` containing a hundred nested sub-menus.
- **Recursive tree operations** become trivial to add: `print()`, `findVegetarian()`, `countItems()`, `calculateTotal()` — all follow the same recursive delegation pattern, each implemented once in `Menu`.
- **Composability**: the two patterns combine naturally. A `CompositeIterator` uses Iterator to expose a tree built with Composite as a flat sequence. Neither pattern needs to know about the other; they cooperate through the shared `MenuComponent` interface.
