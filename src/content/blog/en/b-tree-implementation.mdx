## <Label color="teal">1</Label> Page Header Fields in Detail

Beyond the basic fields from the slotted page format, a B-Tree page header contains implementation-specific fields:

    { "Field": "Rightmost pointer", "Purpose": "Internal nodes only: the child page ID for keys greater than all separator keys in this node" },
    { "Field": "Node high key",     "Purpose": "Maximum key for this node; used during concurrent access to detect if a search is on the right page" },
    { "Field": "Overflow page ptr", "Purpose": "Pointer to overflow page for cells too large to fit in one page" },
  ]}

**Sibling links** are the key implementation detail for range scans. Once a range scan reaches the first matching leaf, it can traverse to the right sibling directly — without climbing up to the parent and back down. This turns a range scan over K results from O(K × log N) into O(K + log N).

**Overflow pages** handle values or keys that are too large for one page. A cell stores a pointer to an overflow chain of pages; the actual data spans multiple pages. This is how databases store large TEXT or BLOB columns.

## <Label color="teal">2</Label> Binary Search with Indirection Pointers

Within a page, finding the right cell for a given key requires a binary search. The naive approach — binary search directly over the sorted cells — is complicated by variable-length cells: you can't compute cell offsets by index without scanning from the start.

The slotted page solves this: the **slot array** stores (offset, length) pairs in key-sorted order. Binary searching the slot array (fixed-size entries) is O(log(cells per page)) and always efficient. Once the right slot is found, jump to the cell's offset for the actual key comparison.

```
Binary search on slot array → slot index → cell offset → key comparison
```

This indirection is why deletion can mark a slot "empty" without compacting: the slot array stays sorted, and deleted slots are simply skipped.

## <Label color="teal">3</Label> Propagating Splits with Breadcrumbs

When an insert causes a leaf to split, the split must propagate upward — the parent gains a new separator key and child pointer. But when a top-down lookup reaches the leaf, it doesn't have a reference to the parent.

**Breadcrumbs** (the parent stack) solve this. During the top-down lookup phase, each visited node is recorded in a stack. When a split occurs at the leaf:

  { title: "Pop the parent from breadcrumb stack", body: "The stack contains the path from root to leaf. Pop the immediate parent." },
  { title: "Insert separator key into parent", body: "Add the median key and the new sibling's page ID to the parent's slot array." },

  { title: "Handle root split", body: "If the split reaches the root, allocate a new root with one separator key and two children. Tree height increases by 1." },
]} />

Without breadcrumbs, propagating splits would require re-traversing the tree from the root — doubling the I/O cost of split operations.

## <Label color="teal">4</Label> Rebalancing

An alternative to immediate splitting: **rebalancing**. When a node fills up, instead of splitting, attempt to redistribute keys between siblings if a sibling has available space.

```
[leaf1: A B C D E full] [leaf2: F G _ _ _ has space]
```

If leaf2 has spare capacity and shares a parent, rotate one or more keys through the parent separator: move key E from leaf1 to leaf2, update the separator in the parent from E to F.

Rebalancing delays splits (keeping tree height lower) and improves page fill rate (fewer wasted pages), but adds complexity. PostgreSQL's B-Tree implementation does not rebalance; InnoDB does under certain conditions.

## <Label color="teal">5</Label> Right-Only Appends and Bulk Loading

A common workload: insert records with monotonically increasing primary keys (autoincrement IDs, timestamps). Every insert goes to the rightmost leaf. All splits happen on the rightmost path.

Many implementations detect this pattern and optimize: when the rightmost leaf fills, pre-split it in preparation for the next insert rather than waiting for an overflow. This avoids hot-page contention in write-heavy workloads.

**Bulk loading** builds the tree bottom-up:
1. Sort all records by key
2. Fill leaf pages to a target fill factor (e.g. 70%) from sorted input
3. For each completed leaf, produce one separator key
4. Build the level above by grouping separators and building internal nodes
5. Repeat upward until a single root is produced

This approach writes each page exactly once and produces a tree with predictable fill factor — ideal for read-heavy workloads that want maximum space utilization.

## <Label color="teal">6</Label> Vacuum and Storage Maintenance

Deletions and updates in a B-Tree leave fragmentation:

- Deleted cells leave gaps in their slotted page
- Updated cells that grow may require moving the cell and leaving a gap
- Obsolete version records (under MVCC) accumulate across pages

**Page defragmentation** (vacuum at the page level): compact live cells within a page, eliminating internal gaps and restoring contiguous free space.

**B-Tree vacuum** (vacuum at the tree level): merge underpopulated pages, reclaim freed pages back to the free page pool, update parent pointers after merges. This is more expensive and typically runs during low-activity windows.

<Callout color="teal">
Write amplification is the enemy of B-Tree maintenance. Every split writes at least two pages (the original and the new sibling) plus the parent. Every merge writes at least one page. A high-write workload in a B-Tree with aggressive vacuum will write significantly more data than the actual payload. LSM Trees take a different trade: defer all merging to compaction, writing data sequentially in bulk rather than randomly in place.
</Callout>
