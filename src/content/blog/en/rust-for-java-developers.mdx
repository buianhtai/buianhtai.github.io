This is Chapter 1 of a 9-chapter series translating the Java mental model into Rust, one concept at a time: ownership, borrowing, traits, enums, lifetimes, smart pointers, concurrency, async, and the parts Java has no equivalent for at all. We're using the Feynman method for each chapter — explain it simply, find where the simple explanation breaks, then formalize it precisely.

We start here because ownership is the one idea everything else in Rust is built on top of. Skip it, and every later chapter feels like arbitrary syntax. Understand it, and most of Rust's "weird" rules turn out to be one idea applied consistently.

## Explain it simply

Imagine a library with exactly one copy of a rare book. The book has a **library card** taped inside the back cover with one name on it — whoever's name is on the card is the person responsible for that book. If Alice's name is on the card and she hands the book to Bob, the librarian doesn't let two names stay on the card. She crosses out Alice's name and writes Bob's. From that moment, Alice doesn't have the book anymore — she can't check it out, can't return it, can't even claim it exists in her possession. Only Bob can.

If Alice wants her *own* copy so she can also use it, she can't just hand hers over — she has to go to the photocopier and make a full, independent copy. Now there are two books, two library cards, two owners, and the two copies have nothing to do with each other anymore.

That's it. That's the entire idea. **One value, one name on the card, and handing it off changes whose name is on the card.**

## Find the crack

If you've written Java for any length of time, your intuition says: "handing someone a reference doesn't take it away from me." In Java, references are more like *phone numbers to the book*, not the book's library card. Alice can give Bob her phone number and still dial it herself. Both of them can call the book, and whoever calls last mutates it for everyone.

```java
var first = new ArrayList<String>();
var second = first;

second.add("java");
System.out.println(first); // prints [java] — first still "has" it too
```

`first` and `second` are two phone numbers to the *same* object. Nothing was "handed off." The object just sits on the heap until Java's garbage collector notices nobody has the number anymore and reclaims it, on its own schedule, whenever it gets around to it.

This is exactly where the library-book analogy pays for itself: Rust does not hand out phone numbers by default. Assignment moves the library card.

## Formalize it precisely

## <Label color="teal">1</Label> Assignment moves the card, not a phone number

```rust
let first = vec![String::from("java")];
let second = first;

// println!("{first:?}"); // compile error: borrow of moved value: `first`
println!("{second:?}");   // fine — second is now the owner
```

The compiler will not let you use `first` after this. Not because the data was deleted — it's still there — but because letting two names stay valid on the same card is exactly the bug Rust is designed to prevent: two owners disagreeing about who's responsible for cleanup, or worse, both trying to clean it up (a double free, one of C++'s classic memory bugs).

## <Label color="green">2</Label> Some values are cheap enough to just duplicate

Not every type moves. Small, fixed-size values — integers, `bool`, `char`, and a few others — implement the `Copy` trait, meaning assignment just duplicates the bits instead of moving the card:

```rust
let a = 42;
let b = a;
println!("{a} {b}"); // both valid — i32 is Copy, no card to move
```

Java has a rough parallel here: primitives (`int`, `boolean`) are copied by value, while objects are handled by reference. Rust's rule is really the same instinct, just applied to every type based on whether copying is cheap and safe, not just to primitives.

## <Label color="amber">3</Label> Cloning is the photocopier, and it's always explicit

```rust
let first = vec![String::from("java")];
let second = first.clone();

println!("{first:?}");  // still valid — second is an independent copy
println!("{second:?}");
```

`.clone()` is Rust saying "yes, I really do want a second, fully independent copy, and I'm willing to pay for it." There's no accidental deep-copying happening behind your back, and no accidental aliasing either — every value's ownership status is visible in the code, not something you have to trace through the whole call graph to figure out.

## <Label color="rose">4</Label> Cleanup is deterministic, not garbage-collected

```rust
struct LoudDrop(&'static str);

impl Drop for LoudDrop {
    fn drop(&mut self) {
        println!("cleaning up {}", self.0);
    }
}

fn main() {
    let _a = LoudDrop("a");
    {
        let _b = LoudDrop("b");
        println!("b is alive here");
    } // "cleaning up b" prints exactly here, not "eventually"
    println!("a is still alive here");
} // "cleaning up a" prints exactly here
```

Whoever owns a value when it goes out of scope runs its `Drop` implementation *immediately* — not at some future garbage-collection pause. This is why Rust programs don't need a GC: the compiler already knows, at compile time, the exact single moment a value's owner disappears.

## Teach it back

Before moving to Chapter 2, you should be able to answer these without looking back up:

1. Why does `let second = first;` invalidate `first` for a `Vec<String>`, but not for an `i32`?
2. What's the actual bug Rust is preventing by refusing to let two variables "own" the same value at once? (Hint: think about what happens if both try to clean it up.)
3. If you wanted a Java `ArrayList` copy that's fully independent of the original — not just a second reference — what would you have to call, and how is that similar to `.clone()`?
4. In the `LoudDrop` example, why does "cleaning up b" print *before* "cleaning up a", even though `_a` was created first?
