# Agent Execution Platform

**Status: target logical architecture.** This system documents platform responsibilities; service names do not require one deployment per box.

## What the system does

An authenticated caller, verified integration, or schedule can request a run of a published AgentVersion. The control plane authorizes and durably admits the request; workers execute bounded model-and-tool loops with independent gateway checks; users or integrations consume ordered results through stable APIs. No model can directly grant itself permissions, launch scripts or choose an arbitrary external endpoint.

## Architecture layers

| Layer | Responsibilities | Invariants |
| --- | --- | --- |
| Experience & ingress | Chat/API, Agent Studio, external triggers | Authenticate caller and source before admission |
| Control plane | Registry, policy, run admission, decisions and approvals | Immutable version pinning; transactionally durable acceptance |
| Execution plane | Dispatcher, workers, runtime, model gateway | Bounded attempts, leases, budgets and concurrency |
| Integration plane | Tool gateway, MCP/HTTP/job adapters, delegation | Per-operation authorization, fixed reviewed targets |
| State and audit | Run store, events, checkpoints, artifacts | Replayable events; tenant-scoped access; reconciliation |

## Operational design

The Run Service is authoritative for public run status; the workflow adapter may own its own internal checkpoints. Workers use fenced leases. Side effects have idempotent invocation records; ambiguous results enter reconciliation rather than blind retry. Event streaming is driven from a durable store, so reconnecting a browser does not restart execution. Limits apply per principal, tenant, agent version and adapter.
