# Agent Platform — living architecture reference

**Status: proposed, generic reference architecture.** No catalog resource by itself proves a running service, deployed agent, production event, or executable workflow. All examples use fictional SaaS data without private customer or product details.

This catalog explains **what happens between incoming input and a completed response**: how an agent is configured, selected, admitted, scheduled, executed with controlled tools, reviewed for side effects, and returned to the caller.

## High-level architecture

~~~mermaid
flowchart TB
  C["Chat UI / Agent Studio / Public API"] --> API["Platform API"]
  S["Schedules / Email / Webhooks"] --> TR["Trigger Gateway"]
  TR --> API
  API --> REG["Agent Registry: published versions"]
  API --> RUN["Run Service: policy + durable state"]
  RUN --> Q["Dispatcher / workflow adapter"]
  Q --> W["Worker + Runtime Adapter"]
  W --> M["Model Gateway"]
  W --> T["Tool Gateway: auth + audit"]
  T --> EXT["Reviewed MCP / HTTP / external-job adapters"]
  T --> APPROVAL["Approval Service: gated writes"]
  W --> DELEG["Delegation Gateway: bounded child runs"]
  DELEG --> RUN
  RUN --> EV["Event Stream API: SSE + replay"]
  EV --> C
~~~

**Control plane** comprises API, registry, run/admission, policy and approval. **Execution plane** comprises dispatch, workers and runtime. **Integration plane** comprises tool, model, trigger and delegation adapters. These are logical component responsibilities, not a mandate for twelve microservices.

## Domain model: definition versus execution

~~~mermaid
erDiagram
  AgentVersion ||--o{ ToolBinding : grants
  ToolDefinition ||--o{ ToolBinding : referenced_by
  AgentVersion ||--o{ AgentRun : pinned_by
  TriggerBinding ||--o{ AgentRun : starts
  AgentRun ||--o{ ApprovalRequest : may_require
  AgentRun ||--o{ DelegationRequest : may_create
  AgentRun ||--o{ AgentRun : parent_child
~~~

- **AgentVersion** — immutable, published configuration digest, not a runtime process.
- **ToolDefinition** — reviewed versioned capability; **ToolBinding** — narrower grant for a specific agent revision.
- **TriggerBinding** — verified event-to-fixed-target mapping; distinct from a skill or a tool.
- **AgentRun** — durable logical execution with user-facing state; attempts and checkpoints are implementation detail.
- **ApprovalRequest** — exact side-effect intent with human consent, expiry and revalidation.
- **DelegationRequest** — scoped parent-to-child run with reserved budget and lineage.

Select the entity resources in this domain for properties, invariants and worked examples.

## Five platform design invariants

1. **Explicit agent selection skips routing.** If auto-routing is enabled, eligibility filtering precedes any cheap model-based ranking; an ambiguous route returns a safe clarification.
2. **No model self-authorizes tools or external actions.** A model proposes a reviewed tool; the Tool Gateway checks schema, principal/tenant, binding, resource ACL, quota and approval.
3. **Durable admission before acknowledgment.** The platform stores run, pinned manifest and outbox intent before returning HTTP 202; duplicate dispatch cannot create duplicate logical runs.
4. **Approved intent is not completed effect.** Side effects use idempotency/correlation and distinguish success, failure, denial and unknown remote outcome.
5. **Budgets are enforced outside prompts.** Hard limits apply to model tokens, turns, tool calls, elapsed time, child runs and spend.

## MVP versus target

| Capability | MVP | Target evolution |
| --- | --- | --- |
| Invocation | Explicit UI selection; direct POST /runs | Auto-routing, API/webhook/schedule bindings |
| Registry | Pinned agent revision with fixed read-only tools | UI-controlled versioned model/skill/tool catalog and publisher workflow |
| Execution | One bounded worker/runtime and read-only KB | Durable parallel/deep agents, multiple worker pools |
| Integration | Registered MCP/read-only API adapters | Approved HTTP/workflow/job adapters, human-gated writes |
| Delivery | HTTP 202 + persisted status / SSE | Replay, reliable callbacks, multi-channel delivery |
| Operations | Per-run audit and token/latency metering | Tenant QoS, escalation evaluation, cost dashboards and chaos testing |

### Reference contracts

The [Platform API](/architecture/docs/services/PlatformAPI/0.1.0/) now contains an **illustrative OpenAPI 3.1 specification** for the public `/v1/runs` and version-publication endpoints. The [Run Service](/architecture/docs/services/RunService/0.1.0/) contains an **illustrative AsyncAPI 3 specification** for lifecycle notifications. Event and command pages continue to have separately versioned JSON Schemas.

**Contract distinction:** `StartAgentRun` is the catalog's internal *command intent*, while `POST /v1/runs` is the proposed external wire API. They can differ structurally: the public `target`/`input` request is authenticated, resolved and normalized into the internal admission command. Do not treat their JSON Schemas as interchangeable or assert a deployed endpoint exists.

Review the [Governance and Contract Authoring Guide](https://github.com/buianhtai/buianhtai.github.io/blob/main/docs/agent-platform/eventcatalog-poc/GOVERNANCE.md) for ownership changes, compatibility rules and CI controls.
