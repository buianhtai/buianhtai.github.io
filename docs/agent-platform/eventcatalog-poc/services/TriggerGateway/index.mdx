# Trigger Gateway

**Status: proposed logical service.** The responsibility may live in a module rather than its own process.

<NodeGraph />

<CustomProperties title="Architecture governance" />

## Ownership

A trigger **starts** a run; a skill or model does not subscribe to mailboxes or schedulers. Approved adapters normalize provider-specific schedules, webhooks, and mailbox deliveries, verify authenticity and map events through a TriggerBinding.

## Normalized intake

| Input | Validation | Deduplication | Target resolution |
| --- | --- | --- | --- |
| Webhook | Signature, timestamp, origin allowlist | Source event ID | Reviewed binding |
| Email poll | Connector identity, mailbox subscription and account scopes | Message ID + mailbox ID | Fixed support workflow |
| Schedule | Schedule ID, tenant and service principal | Occurrence ID | Fixed workflow or agent |

Persist a source-event receipt and an idempotent admission intent before acknowledging successful intake. Tenant and target must derive from binding configuration, not untrusted incoming fields.

## Failure handling

Missing or disabled bindings return a safe rejection. Invalid signatures cannot trigger runs. Duplicate source events reuse the existing logical run. Backpressure and throttling protect tenant quotas; a failed downstream admission is retried only with the same idempotency identity.

The Trigger Gateway can be a module in an existing integration service and does **not** need to duplicate scheduling or polling capabilities offered by Kestra or another provider.
