## Interpretation

**The browser is a consumer, not the execution plane.** Frontend can cache a session cursor or render approval forms, but token scopes, agent eligibility, run pinning and side-effect permissions are enforced in the backend. The UI can reattach to a durable run using its runId and cursor after disconnect. A named frontend module does not imply a separate microfrontend deployment.

## Frontend contracts

| Component | Input | Backend interaction | Failure state |
| --- | --- | --- | --- |
| Chat & agent picker | Text, selected eligible deployment | POST /v1/runs | 409 idempotency conflict, 403 denied, 429 quota |
| Agent Studio | Draft, model/skill/tool refs | Registry-backed validate/publish | Typed draft diagnostics; never client-side authoritative validation |
| Approval Inbox | Authorized exact intent | Approval Service via API | Expired/hash-mismatch -> reject and refresh |
| Run History | runId, workspace | GET /v1/runs/:runId | Revocation -> no longer show protected artifacts |
| SSE client | Authorized run and cursor | GET events + Last-Event-ID | Reconnect same run; fallback to status snapshot |

## Security / accessibility

Use stable focus and keyboard access for approval forms; label pending and terminal status updates appropriately. Never expose provider credentials or unrestricted tool arguments to frontend state. Treat rendered model content as untrusted output; prevent arbitrary embedded script execution.
