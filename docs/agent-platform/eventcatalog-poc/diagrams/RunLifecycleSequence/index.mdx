# Run Lifecycle — Request-to-Result Sequence

**Status: proposed design.** Fictional, domain-neutral, and implementation-neutral; not evidence of deployed cloud infrastructure or an approved technology stack.

## Diagram

~~~mermaid
sequenceDiagram
  autonumber
  actor User
  participant UI as Chat UI
  participant API as Platform API
  participant REG as Registry / Router
  participant RUN as Run Service
  participant Q as Dispatcher
  participant W as Agent Worker
  participant M as Model Gateway
  participant T as Tool Gateway
  participant EVT as Event Store
  User->>UI: Ask a question
  UI->>API: POST /v1/runs (target, input)
  API->>REG: Authorize selection
  alt Target auto
    REG->>REG: Filter eligible versions then rank
  else Explicit agent
    REG->>REG: Resolve selected published version
  end
  alt Ambiguous or unauthorized
    REG-->>API: Rejected / ask to select
    API-->>UI: Typed error or clarification
  else One authorized agent
    API->>RUN: Admit run + pinned manifest + outbox
    RUN->>EVT: Persist accepted event
    RUN-->>API: runId
    API-->>UI: HTTP 202 and events URL
    UI->>API: GET events with cursor (SSE)
    RUN->>Q: Dispatch committed intent
    Q->>W: Lease attempt with fencing token
    W->>M: Prompt with bound tool schemas
    opt Model proposes tool call
      M-->>W: Tool arguments
      W->>T: Invoke reviewed binding
      T-->>W: Allowed/denied result
      W->>M: Grounded evidence or safe denial
    end
    M-->>W: Final answer
    W->>EVT: Commit result + usage + events
    API-->>UI: Stream persisted progress and completion
  end
~~~

## How to read it

REST admission acknowledges **durable work**, not the completion of inference. A worker never streams directly to the browser. Tool arguments generated by a model are only a proposal until schema, policy, tenant/resource ACL and spending checks pass. SSE reconnect replays the same logical run.
